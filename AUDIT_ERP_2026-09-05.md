## 1.2 Comment les modules se connectent réellement

**Il n'y a pas de registre de modules.** Le couplage est celui d'un monolithe de fichiers :

1. `server.ts` instancie **une** fois `new AyroviDatabase(path)` (ligne ~217) et le passe
   explicitement à chaque `createXxxRouter(db, …)`. Aucun conteneur, aucun DI, aucun bus d'événements.
2. Un module = un dossier dans `src/` + son fichier `routes.ts`. Il reçoit `db` nu et écrit son SQL
   soit dans le handler (`src/admin/routes.ts`, `src/customer/routes.ts`), soit dans ses services
   (`src/arrival-ingestion/*Service.ts`).
3. La **seule** frontière appliquée par un outil est celle de l'IA (`tests/ai-architecture-boundaries.test.ts`).
   Aucune équivalent n'existe pour CRM, Finance, CMS, Commerce.
4. `QatafoDatabase` est **la** dépendance partagée : 2 883 lignes où cohabitent schéma, migrations,
   seeds, règles métier (checkout `createOrderFromCart`, `confirmCardTransaction`, `reviewDepositProof`,
   `issueOrderInvoice`, `getFinancialReport`) et SQL générique (`get/all/run/transaction`).
   Un module qui veut toucher aux commandes doit passer par cette classe → tout le monde y écrit.

**Où est la business logic — trois endroits différents :**

| Endroit | Contenu | Exemple vérifié |
|---|---|---|
| `src/db/database.ts` méthodes publiques | checkout, acompte, vérif carte, révision justificatif, émission facture, rapport financier | `createOrderFromCart` (2397), `reviewDepositProof` (~2835), `issueOrderInvoice` (2858), `getFinancialReport` (1837 av.) |
| Handlers de routes | machine à états de commande, validation des méthodes de paiement, recompute prix produit, réordonnancement, upload | `transitions` codé en dur dans `PUT /orders/:id/status` (`src/admin/routes.ts:1391-1406`) ; `recomputeProductPricing` appelé par le CRUD générique (1297) |
| Services métier (`src/arrival-ingestion/*`) | extraction, normalisation, classification, gating, dispatch, cartons | `categoryClassificationService.ts` (357+), `shipmentService.ts` |

→ Le module **le plus récent** (`arrival-ingestion`) est le seul à respecter `routes = HTTP only` +
`service = métier` + `audit canonique`. C'est le patron à généraliser, pas celui d'`admin/routes.ts`.

## 1.3 Doublons et chevauchements réels (les 10 qui comptent)

1. **Deux audititeurs** : `audit()` local à `src/admin/routes.ts:271` (37 appels) et
   `recordAdminAudit()` de `src/admin/audit.ts` (76 appels). Même table `audit_logs`,
   deux INSERT écrits à la main, même format `audit_${randomUUID()}`. Deux sources de vérité sur la
   sémantique de `action`/`module` et sur le troncature (`slice(0,160)`, `slice(0,100)`).
2. **Deux identités client** : `customers` (9 col., PK TEXT, `phone UNIQUE`) pour le CRM/OMS et
   `customer_accounts` (13 col., email/phone vérifiés) pour le site. `orders` porte **les deux**
   (`customer_id` RESTRICT + `account_id` SET NULL). Aucun lien dur entre les deux : le rapprochement
   se fait par `normalizeCustomerPhone()` (regex sur `+216`/`00216`) dans `createOrderFromCart` et dans
   `arrivalClientService.createAndAdd` (ligne ~322). **Deux implémentations distinctes de la même règle.**
3. **Deux entités « arrivage »** sans rapport : `arrivals` (CMS vitrine, 14 col., `type STANDARD|EXPRESS`)
   et `crm_arrivals` (CRM opérationnel, 7 col., `status DRAFT|PROCESSING|REVIEW|CONFIRMED`).
   `orders.arrival_id → arrivals(id)` (la vitrine) alors que `crm_extracted_products.arrival_id → crm_arrivals(id)`.
   Le mot « arrival » désigne deux choses différentes dans le même système.
4. **Deux systèmes éditoriaux** : `stories`/`news_items` (CMS, CRUD générique admin) et
   `publications`/`reels`/`story_publishers`/`story_interactions` (social). `news_items` sert l'onglet
   « مجلتي » ; `magazine_drafts` est une troisième couche de brouillons qui **écrit dans** `news_items`
   (`target_resource`/`target_id`) — boucle CMS ← IA ← CMS sans ligne de propriété claire.
5. **Quatre tables pour le Hero** : `hero_slides`, `hero_visuals`, `hero_content_settings`,
   `lens_hero_settings` (+ `home_blocks`, `trust_bar_items`, `trust_bar_settings`). 4 endpoints admin
   distincts, 4 styles de validation.
6. **Deux générateurs de numérotation** sans séquence : `AYR-<randomInt(100000,1000000)>` pour les
   commandes (`database.ts:2403`), `PAY-/TXN-<année>-<randomInt>` avec boucle d'essai jusqu'à 20,
   et `INV-<année>-<COUNT+1>` pour les factures (`2651-2659`) — **le numéro de facture dépend d'un COUNT**,
   donc trous, et collisions après annulation.
7. **Duplication des données de prix** : `products` stocke `converted_price`, `customs_fee`, `shipping_fee`,
   `service_fee`, `final_price` (recalculés à chaque PUT admin) alors que la source de vérité est
   `pricing_config` + `customs_categories` et que `orders`/`order_items` gardent un `pricing_snapshot` JSON.
   Trois représentations du même prix, aucune contrainte d'unicité entre elles.
8. **Colonnes fantômes** : `orders.invoice_number` + `orders.invoice_path` doublonnent la table `invoices` ;
   le code les garde « read-compatible » (`database.ts:2874` : `UPDATE orders SET invoice_number=?, invoice_path=''`)
   → deux endroits où « la commande a une facture ».
9. **Deux racines d'uploads** : `src/server.ts:167` sert `process.cwd()/data/uploads` (public `/uploads`)
   alors que `src/services/invoice.ts:14-24` calcule `dirname(DATABASE_PATH)/uploads` et que
   `src/services/heroVisual.ts:136` écrit dans `process.cwd()/data/uploads/hero`.
   Sur Render (base dans le projet) les trois tombent au même endroit ; sur tout autre hébergeur avec
   `DATABASE_PATH=/var/data/...` les factures échappent à la sauvegarde et au disque monté.
10. **Un schéma hors de `database.ts`** : `ayrovix_review_requests` est créé/modifié par
    `ensureAyrovixReviewRequestsTable()` (`src/ayrovix/reviews.ts:22-62`), avec son propre
    `ALTER TABLE … ADD COLUMN` et un cache `WeakSet`. Toute génération de dictionnaire de données
    à partir de `database.ts` le rate.

## 2.1 Ce qui existe, exactement

Un seul acteur humain côté back-office : **`admin_users`** (9 colonnes, `src/db/database.ts`)

```text

email TEXT UNIQUE COLLATE NOCASE               ← identifiant de connexion
name  TEXT                                     ← nom affiché (160 car. tronqué à l'audit)
password_hash TEXT                             ← 'scrypt$<salt>$<hash>' (auth.ts:24-27)
role  TEXT CHECK IN ('SUPER_ADMIN','ADMIN','CONTENT_MANAGER','ORDER_MANAGER')
active INTEGER 0/1
last_login_at / created_at / updated_at
```

**Absent du vocabulaire et de la structure** : `employee`, `employee_code`, `department`, `team`,
`branch`, `organization`, `position`, `shift`. Vérifié par grep sur `src` + `client/src` : **4 hits**,
tous non pertinents (variable `branch` dans un parseur `schemaLimits.ts`, `PAYMENT_METHODS`, `messages.unshift`).
Il n'y a **ni** table de départements, **ni** rattachement hiérarchique, **ni** fiche de poste, **ni** statut RH.

### Authentification (solide, et c'est à conserver)

`src/admin/auth.ts` (169 lignes) :
- `scryptSync` sel 16 octets, 64 octets, `timingSafeEqual` (`hashPassword`/`verifyPassword` L24-36).
- Cookie `ayrovi_admin_session`, `Path=/api/admin`, `HttpOnly`, `SameSite=Strict`, `Secure` en prod (L44-46).
- Session stockée **hachée SHA-256** côté base (`admin_sessions.id = hashToken(token)`) → un vol de base
  ne donne pas de session réutilisable.
- TTL 8 h fixe (`SESSION_TTL_MS` L7), pas de « remember me », pas de renouvellement glissant d'expiration
  (seul `last_seen_at` est touché à chaque requête, L128).
- CSRF : jeton séparé, **haché en base**, vérifié sur toutes méthodes non-GET (L143-152),
  rotatif à `GET /auth/me` (`rotateCsrfToken`, utilisé routes.ts:380).
- Anti-énumération : `POST /auth/login` + 4 tentatives max ? → UNKNOWN (le code de login est à L339-373,
  seul le rate-limit global `admin-login` 10/5 min est vérifié, `server.ts:89`).
- `ensureBootstrapAdmin` : crée `SUPER_ADMIN` si 0 admin, ou **réinitialise le mot de passe** si
  `ADMIN_BOOTSTRAP_RESET=yes` (L54-84) — pratique de secours puissante, dangereuse si la variable
  reste définie (le code avertit de la retirer, sans la désactiver).
- Verrou anti-suicide : un compte ne peut pas se désactiver ni se rétrograder lui-même (routes.ts:1855).

### Autorisation (faible, à étendre)

`src/admin/permissions.ts` — **tout le fichier fait 38 lignes** :

```ts
4 rôles → Set de 12 permissions {module}:{action}
SUPER_ADMIN      : les 12
ADMIN            : 11 (sans users:write)
CONTENT_MANAGER  : dashboard:read, content:read, content:write
ORDER_MANAGER    : dashboard:read, commerce:read, orders:write, payments:write
```

`hasPermission(role, permission)` → une seule table en mémoire. `requireAdmin(db, permission?)` est le
seul point d'application (une seule implémentation, cohérente). `GET /auth/me` renvoie la liste des
permissions du rôle pour filtrer le menu (`AdminApp.tsx:720`).

### Réponse aux 5 questions posées

| Question | Réponse vérifiée |
|---|---|
| Que voit un employé ? | **Par module seulement.** `content:read`, `commerce:read`, `dashboard:read`, `audit:read`, `reports:read`. Pas de portée d'enregistrement : un `ORDER_MANAGER` voit **toutes** les commandes, tous les clients (`GET /customers`, `GET /customer-accounts`) |
| Que peut-il modifier ? | `content:write`, `orders:write`, `payments:write`, `pricing:write`, `settings:write`. Pas de distinction création/modification/suppression sur plusieurs modules : `content:write` autorise à la fois POST, PUT **et** le soft-delete d'ARCHIVE |
| Que peut-il créer ? | Impossible à dire finement — même permission que la modification |
| Que peut-il supprimer ? | `content:write` ⇒ suppression **logique** (softDelete du descriptor `resources`) ; le seul `DELETE` physique côté admin est `expenses/:id` (`reports:write`). **Aucun dur-cutover, aucune corbeille, aucune restauration** |
| Que peut-il approuver ? | **Non modélisé.** Il n'y a pas de permission `*:approve`. Les approbations sont branchées sur `orders:write` (`/arrivals/:id/confirm`, `/products/:id/approve`, `approve-all`) ou `payments:write` (révision du justificatif, émission de facture) |

**La permission est-elle extensible à tous les modules ?** Mécaniquement oui — `requireAdmin(db, 'x:read')`
est un paramètre de fonction et le descripteur `resources` (`src/admin/routes.ts:1261+`) génère déjà
5 routes par ressource avec `config.permission` — donc la **plomberie** est bonne. Le **modèle** ne l'est pas :
`role → Set<permission>` statique, sans table, sans `action`, sans `resource`, sans `branch`.
Le frontend, lui, n'a qu'un `permission: Permission` par entrée de nav (`AdminApp.tsx:140-162`) :
aucune notion d'action par bouton. Les pages ne reverrouillent pas les actions (`users:write` sert de
garde à `GET /users`, signe que les noms sont déjà détachés du sens).

## 2.2 Verdict Employees

```text
Classification : EXTEND  (pas REBUILD, pas REPLACE)
```

**Pourquoi EXTEND et pas REBUILD :** la couche sécurité est correcte, homogène et déjà testée —
scrypt + timing-safe, cookie cloisonné par `Path`, jetons et sessions hachés en base, CSRF à rotation,
verrou d'auto-rétrogradation, destruction de session à désactivation/changement de mot de passe
(`routes.ts:1857` : `DELETE FROM admin_sessions WHERE user_id=?`). Reconstruire cela serait perdre
un acquis vérifiable et introduire des régressions d'authentification pour aucun gain.

**Pourquoi pas KEEP :** il n'y a pas d'« employé ». `admin_users` est un compte de connexion, pas une
ressource d'organisation. Un ERP a besoin de : identifiant humain stable lisible (`EMP-000123`),
rattachement `organization → branch → department → team`, poste, statut RH (actif/congé/sortant),
date d'entrée/sortie, supérieur hiérarchique, et surtout une **table de permissions par enregistrement**
au lieu d'une map en mémoire.

**Chemin concret, sans rupture :** ne rien renommer. Ajouter `erp_employees` (ou `employees`) avec
`id`, `code`, `admin_user_id` (→ `admin_users.id`, 1:1), `first/last_name`, `department_id`, `branch_id`,
`manager_id`, `status`, `hired_at`, `terminated_at`. `admin_users` garde **exclusivement** le rôle de
credential/seed de session. `audit_logs.user_id` continue de pointer `admin_users.id` (déjà le cas)
et l'JOIN vers l'employé se fait par `admin_user_id`. Aucune migration des mots de passe, aucune
toucher aux cookies, aucune réécriture de `requireAdmin`.

## 4.2 Ce qui est bon et ne doit surtout pas être reconstruit

`src/arrival-ingestion/` apporte des briques que 95 % des ERP n'ont pas :

- `crm_arrival_sources` : `(arrival_client_id, source_hash)` UNIQUE → **un document ne peut pas être importé deux fois** (`source_hash` SHA-256, `README.md` §Idempotency) ;
- `crm_extraction_jobs` : 25 colonnes, `state`, `worker_id`, `heartbeat_at`, `lease_expires_at`, `attempt`, `retry_at` → **job durable avec lease et reprise** (`extractionJobService.ts:216-251` `recoverPending()`, timer recalculé sur le lease minimum) ;
- `crm_extracted_products` : `is_current`, `superseded_at`, `superseded_by_job_id`, `manual_edits`, `field_evidence`, `review_reasons` → **chaque ligne garde son histoire de ré-extraction** (pattern SCD-2, rare et précieux) ;
- `categoryClassificationService` + `crm_categories` : taxonomy importée (jamais codée en dur), AI **re-vérifié** serveur, gate durci par `classification_required` pour ne pas casser les lignes antérieures ;
- `warehouseDispatchService` : `card_id = card_${arrivalClientId}` = **clé d'idempotence stable des deux côtés**, `idempotency-key` envoyé en HTTP, `attempts`, `payload_summary`, `SEND_FAILED` rejouable (`routes.ts` remonte les échecs en 502, jamais 401 — commit `4d85940`).

→ **Décision explicite : ne pas « refactoriser » `arrival-ingestion` dans un cadre ERP générique.**
Ce module devient le **modèle de référence** des nouveaux modules ERP (`routes.ts` mince, `*Service.ts` épais,
`errors.ts` typé, `recordAdminAudit` canonique), pas une cible de réécriture.

## 4.3 Duplication / chevauchement côté CRM

- `crm_arrival_clients.display_alias` (alias d'affichage par arrivée) vs `customers.name` : deux noms pour la même personne ; aucun arbitrage documenté dans le code sur lequel est canonique.
- `crm_stores` (magasins sources : SHEIN, AMAZON…) est **appelé** « supplier » dans l'enveloppe d'extraction (`storeExtractionStrategy.ts:12` : *"WHO ordered, from WHICH store/supplier"*) — un seul concept porte deux rôles, alors qu'un ERP doit séparer **Marketplace source** (où l'on achète) de **Fournisseur/logistique** (qui livre/facture).
- `crm_arrival_client_stores` (multi-store) est l'historique de relation client↔store, mais il n'existe **aucune** vue « ce client a N commandes au total, M arrivées, X CA » : `orders` n'est pas relié à `crm_*`. L'agrégat `lifetime_value` vient des `orders` du site, pas du CRM.

## 5.2 Classification demandée

```text
Basic Finance
```

Ni `Finance Module`, ni `Accounting-capable`. Justification sans appel :
une seule écriture comptable implicite (la ligne `payments`), zéro partie double, zéro compte, zéro période,
zéro journal, zéro facture multi-lignes, zéro avoir, zéro fournisseur, `profit` = soustraction de deux SUM.

## 5.3 Risques

1. **Immutabilité nulle** : un admin (`reports:write`) supprime une dépense sans trace réversible — l'`audit()`
   garde `old_value` (donc rattrapable) mais la table, elle, est détruite. Aucune table `*_history`.
2. **Numérotation légale fragile** : `INV-<année>-<COUNT+1>` → si une facture est `VOID`ée, le COUNT baisse,
   les suivantes peuvent réutiliser/raté le numéro ; aucun contrôle de continuité. **Risque comptable/fiscal direct.**
3. **Real pour les montants** : `REAL` partout + arrondis `Math.round(x*1000)/1000` (millimes). Marchera tant
   que tout passe par `millimes()`/`*1000/1000`, mais aucun `CHECK` ne garantit la cohérence
   `orders.total_tnd = subtotal + customs + shipping + service + express − discount`.
4. **1 paiement / commande** : incompatible avec acompte + solde + avoir, donc avec toute la comptabilité client.
5. **Facture = 1 par commande, sans lignes** : `invoices` ne porte que `order_id`. Le détail vient de
   `order_items`. Impossibilité de facturer une régularisation, un dégrèvement de douane, un port en sus.
6. **`payments.confirmed_by`** mélange un id admin et la chaîne `'KONNECT'` (`database.ts:2759`) — une colonne
   à deux sémantiques, inviolable à joindre proprement.

## 5.4 Verdict Finance

```text
KEEP     payments / payment_transactions / payment_proofs (le cycle « preuve → revue → confirm » est bon et sûr)
EXTEND   invoices (Draft→Sent→Paid→Void, multi-lignes, avoirs, numérotation par séquence)
EXTEND   expenses → table de dépenses avec FK created_by, soft delete, pièce jointe, rattachement fournisseur
NEW      accounts (plan), journal_entries + lines, periods, bank_statement + reconciliation,
         party_balances, supplier_invoices, taxes
REMOVE   (rien à supprimer — les legacy orders.invoice_number/invoice_path passent en lecture seule, pas en suppression)
```

   aucune raison de les contenir. Aucune conséquence fonctionnelle, mais c'est le symptôme du schéma sans
   baseline versionnée.
4. `promotions.usage_count` est incrémenté… **nulle part trouvé** dans le code admin (UNKNOWN : je n'ai pas
   localisé d'incrémentation ni de consommation de `promo_code` dans le checkout). Un champ de campagne

5. `settings` (catégories `GENERAL|COMMERCE|DELIVERY|PAYMENT|CHANNELS|DESIGN|INTERFACE`) : `PUT /settings/:id`

## 6.3 Verdict CMS — et la question « faut-il un CMS séparé ? »

```text
KEEP + EXTEND, et surtout : PAS de second CMS.
Le CMS doit rester un MODULE de /admin, à côté des modules ERP, avec le même requireAdmin(),
la même table d'audit, la même session.
```

Réponse argumentée à la consigne n° 8 : `ayrovi.com` (site public, consommateur d'API) et
`ayrovi.com/admin` (Back Office unique, contenant **CMS + CRM + Sales + Finance + …**) est
**exactement** ce que le code fait déjà. `main.tsx:8` décide sur `window.location.pathname`, un seul

`crm_arrivals` (ERP opérationnel) portent le même mot, et `products` est à la fois un produit catalogue
CMS **et** la table tarifée (`final_price` calculée). Il faut décider la propriété (§ 9) avant d'ajouter un
module Inventory : sinon la donnée produit se scinde en trois.

## 8.2 Problèmes d'API (format WHERE/WHY/IMPACT/DEPS/SOLUTION/PRIORITY)

**A1 — 16 écritures admin non journalisées** *(déjà détaillé §3.2)*
- WHERE : `src/admin/routes.ts:993,1007,1018,1024,1039,1051,1060,1073,1083,1223,1424,1534,1538,1774,937,967`
- WHY : ces pages ont été ajoutées après coup avec leur handler dédié, sans passer par le `resources` générique qui audite automatiquement.
- IMPACT : pas de réponse possible à « qui a publié/supprimé cette story ? » ; incohérence avec le reste du back-office ; audit ERP incomplet dès le départ.
- DEPENDENCIES : aucune (ajout d'un appel `audit()` par handler) ; si on passe par un `recordAdminAudit` unique, il faut éliminer l'`audit()` dupliqué.
- SOLUTION : (1) rendre `recordAdminAudit` l'unique writer, supprimer le doublon local ; (2) un middleware/`res.on('finish')` d'audit pour les mutations admin **non** couvertes ; (3) `action_code` contrôlé.
- PRIORITY : **Critique** (c'est la condition n°1 de votre cahier ERP).

**A2 — `GET /admin/users` exige `users:write`**
- WHERE : `src/admin/routes.ts:1826`
- WHY : aucune permission `users:read` n'existe dans les 12 (`permissions.ts`).
- IMPACT : un rôle ne peut pas **consulter** l'annuaire sans pouvoir **créer/modifier** des comptes. Empêche tout rôle « HR read-only » ou « manager ».
- DEPENDENCIES : frontend `AdminApp.tsx:608` (page Users) suppose l'accès global.
- SOLUTION : ajouter `<module>:read` par module dans la table de permissions (additif, pas de renommage) — déjà nécessaire pour l'ERP.
- PRIORITY : Élevé.

**A3 — `ai-knowledge` : lecture gardée par `settings:write`**
- WHERE : `src/admin/routes.ts:1262` et `1286`
- WHY : rustine d'époque pour éviter d'ouvrir le contenu éditorial à `content:read`.
- IMPACT : `CONTENT_MANAGER` ne peut ni lire ni écrire la base de connaissances de l'assistant → fonctionnalité inaccessible à son rôle naturel ; l'admin doit tout faire.
- DEPENDENCIES : descriptor `resources` + nav frontend (`assistant` sous `settings:write`, `AdminApp.tsx:160`).
- SOLUTION : permission dédiée `assistant:read`/`assistant:write`.
- PRIORITY : Moyen-Élevé (bug d'UX-permission, pas de sécurité).

**A4 — `PUT /orders/:id/payment` est un 409 permanent**
- WHERE : `src/admin/routes.ts:1424-1430`
- WHY : choix délibéré de sécurité (aucune écriture financière manuelle, seul Konnect ou la revue de justificatif peut confirmer).
- IMPACT : **empêche** la saisie d'un paiement en espèces/chèque/virement entrant, donc bloque le recouvrement client, le solde partiel, les remboursements, la comptabilité fournisseurs → c'est LE verrou à faire sauter pour un ERP, et il faudra le faire avec un workflow de validation, pas en retirant le refus.
- DEPENDENCIES : `payments` UNIQUE(order_id) (D7) ; le statut `PARTIALLY_PAID` existe mais n'est atteignable que par la passerelle ; `reviewDepositProof`/`confirmCardTransaction` dans `database.ts`.
- SOLUTION : `finance_payments` (n lignes, multi-montants) + `finance_payment_allocations` + route `POST /finance/payments` protégée par `finance:approve` + double validation (un enregistre, un valide) + écriture de journal.
- PRIORITY : Critique pour l'ERP.

**A5 — `GET /api/ready` expose l'état de capacité non authentifié**
- WHERE : `src/server.ts:203-240`
- WHY : healthcheck de plateforme (Render `healthCheckPath: /api/ready`).
- IMPACT : divulgue `capabilities` (quel AI/OAuth/mail/gateway est configuré, seuils de migration `arrivalMultistore`) à un attaquant non authentifié → cartographie des surfaces attaquables.
- DEPENDENCIES : `render.yaml:9` s'appuie sur `/api/ready`.
- SOLUTION : `/api/ready` minimal public (`status`) + `/api/admin/ready` détaillé sous `dashboard:read`.
- PRIORITY : Élevé (faible coût de correction).

**A6 — 9 endpoints Lens/AYROVIX publics sans auth ni propriété**
- WHERE : `src/ayrovix/routes.ts:145-464` (`analyze-image` 167, `analyze-url` 290, `analyze-code` 368, `analyze-barcode` 392, `review-request` 416, `history` 145)
- WHY : produit grand public orienté caméra ; seul garde-fou = `rateLimit('ayrovix', 12, 10 min)` (`server.ts:118-123`).
- IMPACT : **coût AI direct** : un bot peut consommer le quota payant (12/IP/10 min ≈ 1 728 j-1 par IP, multi-IP trivial). `GET /history` n'est **pas** compté dans le quota (`server.ts:120`) → fuite d'énumération : la récupération d'historique par `session_id` n'est **pas** journalisée ni cloisonnée par utilisateur (à confirmer, voir UNKNOWN U3). `POST /review-request` crée des tickets sans compte.
- DEPENDENCIES : quota fournisseurs (Anthropic/Groq/Gemini/OpenAI/SerpAPI), `ayrovix_review_requests` hors schéma central (D12).
- SOLUTION : compteurs par (IP + browser session) déjà partiellement fait pour le social (`socialMutationRateLimit` L112-124) → **le même patron** pour Lens ; plafond quotidien global + kill-switch admin ; `GET /history` rattaché à un hash de session.
- PRIORITY : Élevé (argent).

**A7 — Logique SQL dans les handlers (150 occurrences dans `admin/routes.ts`)**
- WHERE : `src/admin/routes.ts` (111 SELECT + 17/29/10), `src/customer/routes.ts` (79 + 14/34/21), `src/public/routes.ts` (34 + 4/2/1)
- WHY : historique — ces fichiers ont grandi avant l'arrivée du pattern service.
- IMPACT : impossible de réutiliser une opération hors HTTP (job planifié, import, CLI, réconciliation), testable seulement en HTTP ; la machine à états de commande vit dans le handler (`1391-1406`) au lieu d'un module `sales/workflow`.
- DEPENDENCIES : tout `client/src/admin/*` qui appelle ces routes ; `tests/ayrovi.test.ts` (41 cas) les exerce **via** HTTP, donc un déplacement propre est possible sans casser les tests si les routes restent inchangées.
- SOLUTION : **ne pas « refactoriser en grand »**. Extractions ciblées, module par module, en gardant les endpoints tels quels (`routes.ts` → appel service). Premier candidat : `sales` (état machine + transitions), second : `finance` (paiement/facture).
- PRIORITY : Élevé pour l'ERP, Faible en risque immédiat.

**A8 — Incohérences de contrat d'API**
- Les erreurs : admin retourne `{success:false,error:'…'}` (messages utilisateurs, en français) alors qu'`arrival-ingestion` retourne `{code:'ARRIVAL_CLIENT_DUPLICATE',error:…}` ; le 404 global API renvoie `code:'API_NOT_FOUND'` (`server.ts:249`). Aucun catalogue d'erreurs partagé : seuls 3 codes sont centralisés (`src/arrival-ingestion/errors.ts` : `AI_EXTRACTION_NOT_CONFIGURED`, `ARRIVAL_INGESTION_FAILED`, `EXTRACTION_RESPONSE_INVALID`).
- Le verbe : `PATCH` utilisé par `arrival-ingestion` (29 routes dont PATCH) et `PUT` ailleurs ; les mêmes notions (`/arrivals/:id/confirm`, `/clients/:id`) ont un style REST pour l'un et RPC pour l'autre.
- L'enveloppe : `{success,data,pagination}` pour admin/public, mais `/api/ayrovix` renvoie un objet nu.
- PRIORITY : Moyen (coûte à changer plus tard, gratuit à normaliser en écrivant les modules ERP).

**A9 — Logique métier dans le frontend (violations de la règle « backend unique »)**
- `client/src/components/CartDrawer.tsx:40,65` : `{percent: 20}` en dur puis `estimatedDeposit = round(total*percent/100*1000)/1000` → **re-calcul côté client d'une formule serveur**.
- `client/src/components/CheckoutModal.tsx:114,135-137,259-261` : `TUNISIAN_GOVERNORATES_FR` (24 lignes codées en dur dans le composant) utilisé comme état initial **et** comme fallback si le backend n'en renvoie pas ; `depositInfo` par défaut `{percent:20, cardDiscountPercent:5, companyName:'AYROVI'}` puis recompte de l'acompte et de la remise carte.
- IMPACT : le README énonce l'inverse (*« Les tarifs, moyens de paiement, gouvernorats … ne doivent pas être dupliqués dans le frontend »*) ; un changement de politique d'acompte doit être patché à 3 endroits. **Le serveur recalcule au checkout** (donc pas d'impact financier direct vérifiable) — le risque est l'affichage incohérent et la divergence de règles.
- PRIORITY : Moyen.

# PARTIE 12 — TRANSFÉRABILITÉ VERS UN ERP

**Réponse directe : on développe l'existant, on n'annule rien, et on reconstruit peu de choses à zéro — mais il manque tout un tiers du périmètre.**

```text
KEEP      45 %   (identité/permissions/CMS/Arrival-CRM/IA/checkout/OAuth — solides et testés)
EXTEND    25 %   (audit, employees→organisation, factures, dépenses, tickets, settings)
REFACTOR  15 %   (extraction de la logique hors des 4 gros routers, en gardant les endpoints)
REBUILD   10 %   (modèles impossibles à étendre proprement : parties, products/inventory, finance ledger)
REMOVE     5 %   (doublons à déporter : second audit writer, colonnes legacy de facture,
                  générateurs randomInt de numérotation, routes plates à renommer en namespace)
```

**Pourquoi 45 % de KEEP :** le socle d'accès (`auth.ts` + `permissions.ts` + `requireAdmin`) est réutilisable
**tel quel** comme porte d'entrée de chaque module ERP — il suffit de lui donner des permissions par action.
`arrival-ingestion` est déjà un module ERP (documents → extraction → revue → approbation → dispatch → idempotence
→ audit) : c'est 21 fichiers de bonne plomberie métier qu'on ne réécrira pas mieux. Le CMS sous
descriptor (`resources`) génère 9 écrans admin pour ~0 code d'UI spécifique. `ai-core` est protégé par un test
d'architecture. 323 tests existent, dont le socle d'intégration HTTP : la régression est mesurable.

**Pourquoi 10 % de REBUILD :** trois modèles ne peuvent pas être « étendus » sans devenir illisibles —
(a) l'identité (2 tables de client, aucun modèle de partie), (b) le catalogue/stock (aucune notion de
quantité, d'emplacement ou de mouvement ; `stock_status` n'est pas un stock), (c) la comptabilité
(pas de journal, 1 paiement et 1 facture par commande, `payments.order_id UNIQUE` est une contrainte de
**modèle**, pas un réglage). Les reconstruire **à côté**, puis basculer, est plus sûr que de les tordre.

**Pourquoi seulement 5 % de REMOVE :** rien n'est mort (§ 7.3). Les doublons réels sont soit des legacy
volontaires (`orders.invoice_*`, commentaires explicites) soit des chemins à renommer, pas à supprimer.
Supprimer aujourd'hui reviendrait à casser des tests et l'historique.

**Architecture cible : `Modular Monolith`.**
Pourquoi **pas** de microservices : un seul SQLite (`better-sqlite3`, fichier unique, `foreign_keys=ON`,
transactions synchrones) — un découpage réseau nécessiterait de casser les transactions qui font aujourd'hui
la fiabilité (checkout + journal + notifications + audit dans un même `db.transaction`, `confirmCardTransaction`,
`reviewDepositProof`). Pourquoi **pas** un monolithe de fichiers : c'est l'état actuel et c'est ce qui produit
les 150 SQL dans les handlers et les 2 writers d'audit. Le monolithe modulaire (un process, un `db`,
des modules `src/modules/<x>/{routes,schema,services,permissions,tests}` + un `registry.ts`) garde les
transactions et impose la frontière qui n'existe que pour l'IA aujourd'hui.

## 13.3 Modèle de permission cible (remplace sans casser)

boutons et champs — corrigera au passage § 11 « actions cliquables qui renvoient 403 ».

# PARTIE 14 — MIGRATION SANS PERTE DE DONNÉES

**Principe directeur : uniquement additif. Aucune `DROP`, aucun `RENAME` de table, aucune suppression de colonne.**
L'existant (`erp_*`, tables actuelles) reste **fonctionnel et écrit** pendant la phase de transition ;
les nouvelles tables sont alimentées par double-écriture puis par backfill, et la bascule se fait à la lecture.

```text
EXISTING DATA  (73 tables, SQLite du disque persistant Render)
   │  1. Backup complet validé : scripts/backup-sqlite.mjs (PRAGMA integrity_check) — déjà en place, L235/L281
   │     + snapshot daté conservé AVANT toute phase (politique actuelle du disk `ayrovi-data`)
   ▼
CLEANING       (rapports SQL en lecture seule, aucune correction directe)
   │  • customers vs customer_accounts : doublons par phone / normalized_phone / email
   │  • orders : account_id NULL (GUEST) → volume à chiffrer
   │  • produits CMS vs crm_extracted_products : SKU/réf en doublon, `stock_status` sans quantité
   │  • factures : cohérence orders.invoice_number vs invoices.invoice_number
   │  • numéros : trous/dupliquats potentiels nés de randomInt + COUNT → à inventorier, pas à corriger à chaud
   ▼
TRANSFORMATION (script de mapping, idempotent, ré-exécutable, par lot, dans une transaction par lot)
   │  parties / party_contacts  ← union(customers, customer_accounts)
   │  erp_employees            ← admin_users (code EMP-<n> = nouvelle séquence, admin_user_id lié)
   │  role_permissions          ← seed de la table `permissions.ts` (les 12 existantes, sans en retirer une)
   │  products (+variants)     ← produits CMS + lignes `crm_extracted_products` CONFIRMED
   │  inventory_items/movements ← ouverture de stock **initiale** = 0 / à définir ; jamais inventée par l'IA
   │  finance.accounts/entries  ← écriture d'OUVERTURE par période dérivée de `payments`+`expenses`
   │  sequences                ← seed next_value = max(existant)+1 pour AYR/PAY/TXN/INV/SHP/CTN
   ▼
MIGRATION      (double écriture : les routes actuelles écrivent l'ancien + le nouveau via les mêmes transactions)
   │  • aucune fenêtre d'arrêt si possible ; sinon maintenance courte (une seule instance, cf. S2)
   ▼
VALIDATION     (par lot, chiffrée, versionnée dans le repo)
   │  • totaux : Σ orders.total_tnd  vs  Σ sales_orders.amount
   │  • caisse : Σ payments.amount_tnd WHERE PAID  vs  Σ journal_lines (compte 512)
   │  • résultat : getFinancialReport(from,to).profit vs P&L de la période
   │  • intégrité : PRAGMA foreign_key_check + integrity_check ; compte de lignes par table (aucune perte ± 0)
   │  • audit : 100 % des mutations admin avec un audit_events (couverture > 99 % contre 69 % aujourd'hui)
   ▼
NEW ERP        (bascule lecture → nouvelles tables ; les anciennes passent en lecture seule, puis archive)
```

**Rollback.** (1) la copie pré-migration (pattern **déjà validé** par `crm_schema_migrations.backup_status='VERIFIED'`
+ `findVerifiedArrivalMultistoreBackup()`, `database.ts:1871-1876` : si le backup est introuvable, le process
**refuse** d'appliquer la migration — ce réflexe est exactement celui à généraliser) ; (2) un flag applicatif
`ERP_READ_LEGACY=1` pour relire les tables d'origine sans redéploiement ; (3) jamais de `DROP` avant la fin de
la période de garantie (à fixer, ex. 2 versions majeures).

**Intégrité.** `ensureColumn` reste le **seul** mécanisme autorisé pour ajouter une colonne (il est idempotent,
déjà éprouvé sur ~40 colonnes, y compris toutes les colonnes `classification_*`). Pour les tables neuves :
un `erp_migrations(id, applied_at, checksum, backup_status)` **généralisé** depuis `crm_schema_migrations`
(aujourd'hui une seule clé → il devient multi-clés), avec `checksum` de script pour détecter la dérive.
