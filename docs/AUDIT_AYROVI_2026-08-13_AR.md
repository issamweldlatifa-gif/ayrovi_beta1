## تحديث الإصلاحات — المرحلة 1 مكتملة

## 1. الخلاصة التنفيذية عند بدء الفحص (خط الأساس)

> يوثق هذا القسم وما يليه حالة المستودع لحظة الفحص الأولى؛ تحديثات المراحل الأربع أعلاه هي الحالة الحالية وتلغي النتائج القديمة التي عولجت.

المنصة الأساسية منظمة جيدًا نسبيًا، وتحتوي على فصل واضح بين جلسات العميل والإدارة، CSRF، RBAC، SQLite مع WAL وفهارس، وتسعير مركزي يُعاد حسابه على الخادم. الواجهة العامة وواجهات CMS سريعة محليًا، ونجح فحص TypeScript والبناء.

لكن **Lens ليست جاهزة للإنتاج في وضعها الحالي**. البطء ليس سببه عامل واحد، بل سلسلة متتابعة من عمليات مكلفة وغير محدودة بمهلة نهائية: اكتشاف نماذج AI، محاولات متعددة لنماذج ونقاط API، OCR كامل لكل صورة، ثم بحث خارجي متسلسل وإثراء صفحات النتائج. كما أن الوضع المحلي الحالي لا يحلل الصورة فعليًا عند غياب مفاتيح AI، بل يعيد نتيجة عامة بثقة `0.25` ثم يبحث بكلمات عامة.

الأخطر: تم إثبات أن ملفًا يحمل `Content-Type: image/jpeg` لكنه ليس صورة صحيحة يمكنه:

1. أن يُكتب داخل `data/uploads` بامتداده الذي يختاره المرسل.
2. أن يؤدي إلى **انهيار عملية Node بالكامل** داخل Tesseract.
3. أن يبقى قابلًا للنشر من `/uploads` لو استمرت العملية.

هذا يجمع بين خطر تعطيل الخدمة، رفع ملفات عامة غير موثوقة، ومخالفة صريحة للنص المعروض للمستخدم بأن الصور «لا تُحفظ بعد التحليل».

**القرار المقترح:** لا تُطلق Lens للعامة قبل إصلاح بنود P0 أدناه. باقي المنصة يمكن مواصلة تطويرها، لكن بوابة CI حاليًا حمراء بسبب اختبارين مكسورين في Lens.

## 3. لماذا Lens بطيئة وغير كفؤة؟

### 3.1 مسار الطلب الحالي ينتظر كل شيء

في `src/ayrovix/routes.ts` تنتظر الاستجابة:

1. تعريف المنتج عبر AI.
2. OCR عبر Tesseract بالتوازي مع AI، حتى لو كانت الصورة صورة منتج عادية بلا سعر.
3. بعد انتهاء الاثنين، يبدأ البحث في الكتالوج والويب.
4. ثم تنتظر نتائج البحث وإثراء الصفحات قبل إرسال أي نتيجة للمستخدم.

الـ AI وOCR متوازيان، لكن البحث لا يبدأ إلا بعدهما، والعميل لا يحصل على نتيجة جزئية أو تدريجية.

### 3.2 Tesseract يُنشأ من جديد لكل صورة

في `src/services/vision.ts` يُستدعى `Tesseract.recognize(..., 'eng+fra')` لكل طلب. هذا يعني تحميل/تهيئة worker ولغتين وتشغيل OCR كامل على كل صورة. لا يوجد:

- worker pool قابل لإعادة الاستخدام؛
- حد للتوازي؛
- timeout خاص بـ OCR؛
- تصنيف أولي يحدد هل الصورة Screenshot تحتوي نصًا أصلًا؛
- إلغاء حقيقي عند إغلاق Lens.

في القياس المحلي، ومع غياب AI حقيقي، استغرق المسار 2.231 ثانية؛ الجزء المفيد من تعريف المنتج كان fallback فوريًا، لذلك معظم الزمن كان OCR والبحث.

### 3.3 Gemini لديه waterfall ضخم جدًا

في `src/ayrovix/services/ai.ts`:

- اكتشاف النماذج يُنفذ لكل صورة على `v1beta` ثم `v1`، حتى 8 ثوان لكل طلب.
- بعد ذلك توجد حلقة: كل نموذج × ثلاث نقاط Interactions × مهلة 35 ثانية.
- عند الفشل، توجد حلقة legacy: كل نموذج × نسختين API × 30 ثانية.
- لا يوجد deadline إجمالي للعملية.
- حالة quota 429 يمكن أن تستمر في تجربة نماذج ونقاط إضافية بدل فتح circuit breaker.
- قائمة النماذج المكتشفة غير مخزنة في cache.

حتى مع تسعة نماذج fallback فقط، الحد النظري للمهل المتراكمة يتجاوز 24 دقيقة، قبل إضافة النماذج المكتشفة والبحث الخارجي. غالبًا تفشل بعض المحاولات بسرعة، لكن التصميم نفسه يسمح بزمن سيئ جدًا وغير متوقع.

### 3.4 مزودو AI الآخرون يعيدون المحاولات أيضًا

- OpenAI قد يجرب عدة نماذج، كل واحد بمهلة 30 ثانية.
- Anthropic يجلب قائمة النماذج لكل طلب ثم يجرب القائمة المكتشفة وfallbacks.
- لا توجد cache، circuit breaker، أو ميزانية زمنية موحدة بين المزودين.

### 3.5 البحث الخارجي متسلسل وهش

في `src/ayrovix/services/search.ts`:

- Brave API: حتى 10 ثوان.
- عند الفشل يبدأ DuckDuckGo، وليس بالتوازي معه.
- DuckDuckGo يجرب 3 endpoints بالتتابع، كل واحد حتى 12 ثانية.
- ثم Brave scraping حتى 8 ثوان.
- عند وجود نتائج، تُجلب صفحات أفضل 3 نتائج لإثرائها، حتى 6 ثوان إضافية.
- لا توجد cache للبحث أو deduplication على مستوى الطلبات المتزامنة.

المسار المجاني وحده قد يضيف قرابة 44–50 ثانية في الحالة السيئة، وهو يعتمد على scraping HTML وRegex قابلة للكسر عند أي تغيير خارجي.

### 3.6 Puppeteer يُشغّل متصفحًا جديدًا لكل رابط

في `src/scraper/scraper.ts` يتم `puppeteer.launch()` لكل تحليل URL ثم إغلاق المتصفح. هذا مكلف في CPU والذاكرة وزمن التشغيل، ولا توجد browser pool. أثناء الاختبارات المحلية فشل Chromium بسبب غياب `libnss3`، ثم انتقل النظام إلى fallback. هذا يعني أن مسار الرابط قد يكون أبطأ أو غير متاح حسب بيئة النشر.

### 3.7 local fallback لا يحلل البكسلات

عند غياب المفاتيح، `localFallbackIdentification()` يعيد دائمًا تقريبًا:

- `category: product`
- `description: Produit détecté via analyse locale...`
- `confidence: 0.25`

لا يوجد نموذج محلي أو تحليل للصورة. الواجهة تعتبر النتيجة قابلة للاستخدام لأن الثقة أكبر من صفر، ثم تبحث بعبارة عامة. في القياس الفعلي حصلنا على **صفر مرشحين**. لذلك Lens قد تبدو وكأنها نجحت تقنيًا بينما لم تُعرّف المنتج.

### 3.8 كلفة زائدة على الهاتف

- الكاميرا تلتقط حتى 1920×1080 بجودة JPEG `0.92`.
- `prepareImage` يعيد الرسم والتشفير مرة أخرى حتى 1400px بجودة `0.88` مع filter لوني؛ أي double encoding.
- QR fallback يرسم frame كامل الدقة ويعمل `getImageData` و`jsQR` كل 240ms. على هواتف متوسطة هذا يستهلك CPU والبطارية وقد يجعل Lens نفسها متقطعة.

### 3.9 لا يوجد إلغاء حقيقي للطلبات

`abortRef` في `LensLauncher.tsx` يمنع تحديث الواجهة من نتيجة قديمة، لكنه لا يستخدم `AbortController` لإلغاء `fetch`. عند الإغلاق أو بدء تحليل جديد يستمر الخادم في OCR والـ AI والبحث، ويستهلك quota وCPU بلا فائدة.

## 4. مشكلات حرجة P0

### P0-1 — ملف مزيف كصورة يُسقط الخادم بالكامل

التحقق يعتمد على `mimetype` المرسل فقط. في اختبار محلي مضبوط أُرسل ملف نصي مع `Content-Type: image/jpeg`. Tesseract أصدر خطأ قراءة داخل worker ثم خرج Node برمز `1` مع:

```text
Error attempting to read image.
... tesseract.js/src/createWorker.js
Node.js ... process exited 1
```

`try/catch` في route لم يمنع الانهيار لأن الخطأ خرج من worker كحدث غير معالج.

**الإصلاح المطلوب:**

- تحقق magic bytes وفك الصورة فعليًا عبر `sharp` أو مكتبة موثوقة قبل أي OCR.
- أعد ترميز الملف إلى JPEG/WebP آمن في الذاكرة.
- شغّل OCR داخل worker pool مع معالجة أخطاء وحدود زمنية وعزل للعملية إن لزم.
- أضف اختبار regression يرسل MIME صحيحًا ومحتوى فاسدًا ويتوقع `415/422` مع بقاء health endpoint حيًا.

### P0-2 — رفع امتدادات يختارها المستخدم ونشرها من نفس الأصل

`VisualProductExtractor` يأخذ `path.extname(originalFilename)` ثم يكتب الملف داخل `data/uploads`. لذلك اسم مثل `payload.js` مع MIME مزيف ينشئ ملفًا مثل `shot_xxxxx.js`. المجلد كله منشور عبر:

```text
/uploads → express.static(data/uploads)
```

هذا يفتح باب رفع محتوى نشط من نفس أصل التطبيق، إضافة إلى DoS أعلاه.

**الإصلاح المطلوب:** لا تستخدم امتداد المستخدم إطلاقًا. بعد decode موثوق، اختر امتدادًا ثابتًا من الخادم، ويفضل عدم نشر ملفات Lens أصلًا.

### P0-3 — الصور تُحفظ خلافًا لسياسة الواجهة

واجهة Lens تقول: «الصور لا تُحفظ بعد التحليل». فعليًا كل صورة OCR تُكتب في `data/uploads` ولا يوجد `unlink` أو retention job. في Render هذا المجلد على disk دائم. كما يعاد رابط الصورة في النتيجة ويُخدم بذاكرة cache سبعة أيام.

**الإصلاح المطلوب:**

- OCR من buffer دون حفظ، أو ملف مؤقت داخل `try/finally` يُحذف فورًا.
- إذا كان الاحتفاظ ضرورة تجارية: موافقة واضحة، مدة retention، وصول موقّع، حذف آلي، وتحديث سياسة الخصوصية.

## 5. أمان المنصة

### نقاط جيدة

- جلسات Admin وCustomer منفصلة.
- Cookies هي HttpOnly، وSecure في production.
- CSRF إلزامي للتعديلات المصادق عليها.
- RBAC واضح ومغطى بالاختبارات.
- كلمات مرور Admin تستخدم `scrypt` و`timingSafeEqual`.
- session tokens عشوائية ومخزنة كـ hash.
- الأسعار يعاد حسابها على الخادم بدل الثقة في `priceTND` القادم من العميل.
- SQLite يستخدم WAL وforeign keys وbusy timeout وفهارس كثيرة.
- توجد حدود حجم وrate limits أساسية.
- اختبارات الملكية تفصل بيانات العملاء والسلات والطلبات.

### P1 — SSRF غير مكتمل

فحص URL يمنع `localhost` وعناوين IP الخاصة المكتوبة مباشرة، لكنه لا:

- يحل DNS ويتحقق من كل IP ناتج؛
- يعيد التحقق بعد redirects؛
- يمنع Puppeteer من الوصول إلى عناوين داخلية أثناء subrequests؛
- يثبت DNS لمنع rebinding.

نطاق عام يمكن أن يشير إلى private IP أو يعيد redirect إلى metadata/internal service. كما أن إثراء نتائج البحث يجلب URLs دون نفس طبقة الحماية.

**الإصلاح:** resolver آمن لكل hop، منع private/reserved ranges IPv4/IPv6، حد redirects، request interception في Puppeteer، ويفضل egress proxy/allowlist.

### P1 — أربع ثغرات dependencies عالية

`npm audit` أبلغ عن 4 High مرتبطة بسلسلة Puppeteer / `@puppeteer/browsers` / `puppeteer-core` / `extract-zip`. لا تستخدم `npm audit fix --force` مباشرة لأن الاقتراح قد يغير إصدارًا رئيسيًا أو يخفضه. راجع advisory وثبّت نسخة مصححة ومختبرة، أو استبدل Puppeteer بمسار أخف إن أمكن.

### P2 — rate limiting محلي في الذاكرة

الحدود تضيع عند restart ولا تتشارك بين نسخ الخدمة. `/api/ayrovix` له bucket واحد يشمل analyze وbarcode وchoose. هذا غير مناسب للتوسع وقد يحجب مستخدمًا شرعيًا أو يسمح بتجاوز الحد عبر عدة instances.

**الإصلاح:** Redis-backed limiter، مفاتيح منفصلة حسب endpoint/user، وحد concurrency خاص للـ OCR/AI.

### P3 — روابط Admin تفتح تبويبًا بلا `rel=noopener`

يوجد عدد قليل من روابط `target="_blank"` في Admin بلا `rel="noopener noreferrer"`. الخطر منخفض لكنه سهل الإصلاح.

### نظافة المستودع

- ملف `.sudo_as_admin_successful` متتبع بلا حاجة.
- build assets داخل `public/assets` متتبعة؛ البناء يغيّر hashes ويجعل working tree متسخًا.
- لا توجد أسرار حقيقية واضحة داخل الكود الذي فُحص، و`.env` متجاهل.

## 6. أداء الواجهة والمنصة العامة

### 6.1 Bundle كبير وغير مقسم

البناء أعطى:

- JavaScript قرابة 643KB قبل الضغط؛ 189KB gzip حسب Vite.
- CSS قرابة 135KB قبل الضغط؛ 23KB gzip.
- تحذير Vite: chunk أكبر من 500KB.

`main.tsx` يستورد `App` و`AdminApp` بشكل ثابت، و`App` يستورد Lens والحساب وcheckout والمساعد بشكل ثابت. بذلك يحمل زائر الصفحة العامة كود الإدارة وLens وواجهات ثقيلة لا يستخدمها فورًا.

**الإصلاح:** `React.lazy`/dynamic import حسب المسار وعند فتح drawer: Admin، Lens، CustomerAccount، Checkout، Assistant.

### 6.2 لا يوجد ضغط من Express

القياس مع `Accept-Encoding: gzip, br` أعاد `Content-Length` كاملًا بلا `Content-Encoding`. JavaScript وCSS انتقلا محليًا بحوالي 766KB. قد يضغط reverse proxy في بعض البيئات، لكن التطبيق نفسه لا يضمن ذلك.

**الإصلاح:** Brotli/gzip عند CDN أو reverse proxy، أو middleware `compression`، مع إبقاء assets hashed وimmutable.

### 6.3 طلبات CMS مكررة

عند تحميل الصفحة:

- `App` يجلب commerce config.
- `Footer` يجلب commerce config مرة أخرى.
- `HeroSlider` يجلب hero slides.
- `PartnerBrandsSlider` يجلب brands.
- `PublicCmsSections` يجلب `/api/public/home` الذي يحتوي أصلًا hero وbrands وباقي الأقسام.

**الإصلاح:** Home bootstrap واحد في context/store، أو endpoints منفصلة دون `/home` المكرر. استخدم request cache/deduplication.

### 6.4 صور Hero كلها موجودة في bundle/runtime

السلايدر يرسم جميع الصور في DOM فورًا بلا `loading="lazy"` للصور غير النشطة ولا `srcset/sizes`. الأحجام الحالية معقولة نسبيًا، لكن يمكن تحسين LCP عبر preload للصورة الأولى وlazy للشرائح التالية وتحويل WebP/AVIF.

### 6.5 SEO محدود بطبيعة SPA

يوجد title وdescription جيدان، لكن لا يوجد SSR/prerender، canonical، Open Graph/Twitter cards، structured data، sitemap/robots ضمن النطاق المفحوص. صفحات CMS dialogs وليست URLs قابلة للفهرسة والمشاركة.

## 7. صحة الوظائف والعمارة

### نقاط قوية

- التسعير مركزي في `src/services/pricing.ts` ويُستخدم عند السلة والدفع.
- snapshot تسعير الطلبات واختبارات عدم تغييره بعد تعديل الأسعار.
- دورة حياة الطلب، إثبات العربون، المراجعة، الفاتورة والتتبع مغطاة.
- حسابات OTP وGoogle وربط الطلبات القديمة واختبارات منع الاستيلاء على البريد.
- CMS وOMS وRBAC وaudit logs موجودة ومختبرة.
- public APIs سريعة جدًا محليًا.
- قاعدة البيانات تحتوي فهارس مناسبة وتستخدم معاملات للأجزاء الحساسة.

### مشكلات تحتاج معالجة

1. **مصدران قديمان للأسعار:** `VisualProductExtractor.RATES_TO_TND` و`SmartLinkScraper.RATES_TO_TND` يحويان أسعارًا ورسومًا ثابتة، رغم وجود مصدر DB مركزي. بعض routes تعيد التطبيع لاحقًا، لكن بقاء المنطق المكرر خطر صيانة واختلاف.
2. **الفواتير تعتمد على Chromium ثم fallback:** الاختبارات نجحت بفاتورة PDF مبسطة لأن Chromium لم يعمل. يجب اختبار شكل الفاتورة الفعلي في صورة/بيئة الإنتاج.
3. **SQLite على قرص واحد:** مناسب لبداية صغيرة، لكن يلزم backup فعلي واختبار restore ومراقبة حجم القرص. `render.yaml` يحدد 1GB فقط، بينما صور Lens الحالية يمكن أن تتراكم بلا حذف.
4. **لا توجد observability كافية:** لا توجد request IDs أو histogram للزمن حسب مرحلة Lens أو provider أو نسبة fallback. الـ logs نصية ومبعثرة.
5. **لا توجد E2E browser tests:** الاختبارات الحالية backend/integration. مسارات الكاميرا، permissions، drawers، responsive checkout وAdmin تحتاج Playwright على أجهزة/viewport متعددة.
6. **رسائل `alert()` داخل Lens:** توقف الواجهة وغير متناسقة مع UX؛ استبدلها بحالة inline/toast قابلة للوصول.
7. **الـ healthcheck سطحي:** يعيد `ok` دون التحقق من DB write/read، مساحة القرص، أو جاهزية الخدمات الحرجة.

## 8. خطة الإصلاح حسب الأولوية

### المرحلة P0 — قبل أي إطلاق Lens

1. تحقق وفك وإعادة ترميز الصور؛ لا تثق في MIME أو امتداد المستخدم.
2. أوقف حفظ صور Lens أو احذفها في `finally` فورًا.
3. امنع انهيار Tesseract: worker pool مع عزل أخطاء وtimeouts واختبار malformed image.
4. امنع نشر أي امتداد نشط من `/uploads`; استخدم أسماء وامتدادات ثابتة و`Content-Disposition`/`nosniff` وسياسة وصول.
5. اجعل CI خضراء وحدّث عقد السلوك والاختبارات.

### المرحلة P1 — جعل Lens سريعة وصحيحة

1. ميزانية إجمالية للتحليل 10–15 ثانية، لا مهلات متراكمة غير محدودة.
2. مزود AI أساسي واحد + fallback واحد فقط، مع circuit breaker.
3. cache لاكتشاف النماذج ساعة أو عند startup، والأفضل allowlist لنموذج معروف.
4. لا تشغل OCR إلا عند احتمال Screenshot/نص/سعر، أو اجعل Vision API تستخرج النص والسعر في نفس الاستدعاء.
5. cache حسب SHA-256 للصورة وcache لنتيجة البحث حسب query.
6. أرسل identification أولًا، ثم candidates تدريجيًا أو عبر job polling/SSE.
7. استخدم search API ثابت بدل scraping DuckDuckGo/Brave HTML.
8. browser pool أو lightweight metadata fetch؛ لا تطلق Chromium لكل رابط.
9. `AbortController` من العميل، وربطه بإلغاء العمل أو job timeout في الخادم.
10. إذا لم يوجد AI فعلي: أعد حالة واضحة غير مفعلة بدل نجاح وهمي بثقة 0.25.

### المرحلة P1 — الأمان والتشغيل

1. إصلاح SSRF مع DNS وredirect وPuppeteer request interception.
2. معالجة ثغرات Puppeteer dependencies بعد اختبار توافق.
3. Redis rate limiting + queue/concurrency limit للعمليات المكلفة.
4. backup يومي مشفر لقاعدة SQLite واختبار restore.
5. مراقبة: latency لكل مرحلة، provider success/failure، OCR queue، memory/CPU، disk، ونسبة النتائج ذات المرشحين.

### المرحلة P2 — أداء الواجهة

1. code splitting للإدارة وLens والحساب والدفع والمساعد.
2. Brotli/gzip.
3. توحيد bootstrap data ومنع fetches المكررة.
4. تصغير QR frames إلى 480–640px وخفض التكرار إلى 400–600ms عند fallback.
5. WebP/AVIF وresponsive images وlazy loading.
6. E2E + Lighthouse budgets على mobile 4G.
