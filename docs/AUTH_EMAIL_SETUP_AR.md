# بريد الترحيب واسترجاع الحساب — التنفيذ والتفعيل

**الحالة:** البرمجة مكتملة ومختبرة محليًا. الإرسال إلى صناديق بريد حقيقية **غير مفعّل بعد**؛ لم يُقدَّم مزوّد أو مفتاح بريد. لم تُنشر التغييرات على GitHub أو Render.

## 1. الوظائف المنفّذة

### عند إنشاء الحساب
- يُنشأ حساب البريد ورسالة الترحيب في معاملة قاعدة بيانات واحدة.
- الرسالة تحمل اسم المستخدم وتستخدم العربية أو الفرنسية بحسب لغة التسجيل.
- التسجيل لا ينتظر استجابة شبكة مزوّد البريد. عامل إرسال يراجع الطابور كل 15 ثانية.
- لا تُعاد رسالة الترحيب عند كل تسجيل دخول. الحسابات الجديدة عبر OAuth تُضاف لها رسالة عند وجود عنوان بريد في حسابها؛ حساب الهاتف دون بريد لا يُرسل له بريد افتراضي.
- لا تحتوي الرسائل على كلمة مرور أو رمز جلسة، ولا تتضمن اشتراكًا تسويقيًا.

### نسيت كلمة المرور
1. المستخدم يفتح شاشة طلب الرابط ويدخل بريده.
2. إذا كانت الخدمة غير معدّة، تظهر رسالة واضحة ولا يظهر نجاح إرسال وهمي.
3. الطلب الصحيح يعيد `202 accepted`؛ هذه **موافقة على معالجة الطلب، وليست ضمانًا بوصول الرسالة**.
4. للحساب النشط الذي يملك كلمة مرور، يُضاف رابط استرجاع إلى طابور الإرسال.
5. الرابط صالح 30 دقيقة، لمرة واحدة، ولا يُستهلك بمجرد فتح الرسالة أو فحص الرابط.
6. يفتح الرابط `/reset-password` ثم يطلب كلمة مرور جديدة وتأكيدها.
7. بعد الحفظ تُغلق كل الجلسات السابقة وتُبطل بقية روابط الاسترجاع، وتُضاف رسالة إشعار بالتغيير.
8. يعود المستخدم إلى شاشة الدخول، حيث تعمل كلمة المرور الجديدة ولا تعمل القديمة.

**حساب Google/Apple/Facebook دون كلمة مرور:** الدخول عبر المزود نفسه، وليس إنشاء كلمة مرور تلقائيًا من بريد قد يكون غير موثّق لدى ذلك المزود. الحساب المحظور لا يستعيد نشاطه عبر هذا المسار.

## 2. التفعيل على Render

اختر مزوّدًا مدعومًا: `resend` أو `brevo` أو `sendgrid`.

1. أنشئ حساب المزوّد وأضف دومينك/عنوان الإرسال.
2. نفّذ تحقق الدومين وسجلات DNS التي يطلبها المزوّد، مثل SPF وDKIM. لا تُخمّن قيمها؛ انسخها من لوحة المزوّد.
3. أنشئ مفتاح API للإرسال، واحفظه **في Render → Environment فقط**.
4. اضبط التالي؛ القيم أدناه أمثلة وليست إعدادًا مُنجزًا:

```env
MAIL_PROVIDER=resend
MAIL_API_KEY=<مفتاح الإرسال السري من المزود>
MAIL_FROM=AYROVI <no-reply@your-domain.example>
PUBLIC_BASE_URL=https://your-domain.example
CUSTOMER_AUTH_SECRET=<قيمة سرية ثابتة لا تقل عن 32 حرفًا>
```

- يمكن اختيار `brevo` أو `sendgrid` بدل `resend` دون تعديل الكود.
- `PUBLIC_BASE_URL` هو **أصل موقعك النهائي**، دون مسار إضافي أو query/fragment. الإنتاج يتطلب HTTPS.
- دومين الموقع يمكن أن يكون Render، لكن عنوان الإرسال يحتاج تحققًا لدى المزوّد. لا يمكن إرسال رسائل باسم `onrender.com` دون امتلاك إذن التحقق عليه.
- **لا تغيّر `CUSTOMER_AUTH_SECRET` الموجود** عند إضافة البريد؛ يستخدم أيضًا لتشفير طابور الرسائل.
- لا تضع `MAIL_API_KEY` داخل متغير `VITE_*` أو ملف frontend، ولا ترسله في المحادثة.
- يجب بقاء قاعدة SQLite على القرص الدائم حسب إعداد Render الحالي، ليبقى الطابور بعد إعادة التشغيل.
- لا تسمح بخدمة Worker أخرى بتكوين أسرار مختلف على نفس قاعدة البيانات.

5. انشر الإصدار الجديد وأعد تشغيل الخدمة بعد حفظ المتغيرات.
6. تحقق من `/api/customer/auth/config`: يجب أن تكون `passwordReset.enabled` مساوية لـ `true`.
7. سجل **حساب اختبار تملكه** وتحقق من رسالة الترحيب، ثم اطلب الاسترجاع وجرّب الدخول بكلمة المرور الجديدة.
8. راجع صندوق spam وسجل أحداث المزوّد. قبول API للرسالة لا يعني بالضرورة وصولها إلى inbox.

**المطلوب من صاحب المشروع الآن:** اسم الدومين وعنوان البريد الذي سيظهر كمرسل، ثم اختيار المزوّد. المفاتيح السرية تُضبط على Render ولا تُكتب هنا.

## 3. قائمة الأزرار ونطاق التحقق

| الزر / الرابط | التنفيذ | التحقق |
|---|---|---|
| إنشاء حساب | POST تسجيل حساب حقيقي + جلسة + طابور ترحيب | متصفح مع API وSQLite فعليين في بيئة اختبار |
| تسجيل الدخول | فحص كلمة المرور وإنشاء جلسة | نجح بالجديدة وفشل بالقديمة بعد الاسترجاع |
| نسيت كلمة المرور | يفتح نموذج طلب الرابط | متصفح فعلي |
| إرسال الرابط | POST مع تحقق الخدمة وحدود الطلبات | متصفح → خادم → طابور → محاكاة النقل الخارجي |
| إعادة المحاولة | يعيد جلب جاهزية البريد من الخادم | اختُبر الانتقال من غير معدّ إلى معدّ |
| إظهار/إخفاء كلمة المرور | تغيير نوع الحقول مع أسماء وصول صحيحة | اختُبر في الدخول والاسترجاع |
| حفظ كلمة المرور | تحقق الرابط والتأكيد وتغيير hash وإبطال الجلسات | اختبار دورة كاملة |
| طلب رابط جديد | يفتح نموذج طلب جديد عند انتهاء/استهلاك الرابط | متصفح فعلي |
| العودة للدخول | يعيد المستخدم لشاشة الدخول، لا إلى صفحة فارغة | متصفح فعلي |
| التبديل بين التسجيل والدخول | تغيير النموذج مع تنظيف كلمة المرور | اختبارات الهاتف وRTL |
| SMS | واجهة مرتبطة بمسار OTP الموجود | اختبارات API القائمة + فتح المسار بالمتصفح؛ لا SMS حقيقي في هذه البيئة |
| Google / Facebook / Apple | مسارات OAuth الحالية؛ تُخفى الأزرار غير المفعلة | لم يُجرَ تسجيل خارجي حقيقي لعدم وجود مفاتيح/حسابات مزودين |
| الشروط والخصوصية | صفحات HTML موجودة وليست روابط فارغة | استجابة HTTP 200 |

المراجعة تخص **الدخول والتسجيل والاسترجاع**، وليست ادعاءً بمراجعة كل أزرار المتجر أو لوحة الإدارة.

## 4. الحماية والتشغيل

- رمز عشوائي 256-bit، مع حفظ hash فقط في جدول الاسترجاع.
- الرابط يوضع في fragment (`#token=...`) فلا يدخل طلب HTML أو سجلات URL؛ يُزال من شريط العنوان بعد قراءته.
- إرسال الرمز للتحقق/الحفظ عبر POST JSON، مع `no-store` و`no-referrer` لصفحة الاسترجاع.
- النص الكامل للرسائل في الطابور مشفّر بـ AES-256-GCM، ويُمسح بعد قبول الرسالة أو إلغائها/فشلها النهائي.
- لا يُستخدم Host المرسل من العميل لصناعة روابط البريد؛ الروابط من `PUBLIC_BASE_URL` الموثوق.
- الاستجابة لا تكشف هل البريد مسجل أو محظور أو يعتمد OAuth فقط.
- حدود كل 15 دقيقة: 10 طلبات استرجاع لكل IP، و3 لكل بريد، و30 فحص رابط لكل IP، و15 محاولة حفظ لكل IP. حدود التسجيل: 10 لكل IP.
- ردود الخطأ لا تطبع محتوى البريد أو رابط الاسترجاع في logs.
- كلمة المرور بين 8 و100 حرف، وتُخزَّن بـ scrypt مع salt عشوائي كما في نظام الدخول الحالي.
- طلب الاسترجاع لا يحذف الروابط الأقدم فورًا لتفادي تعطيل رابط المستخدم بمجرد طلب جديد؛ **استهلاك أي رابط يبطل البقية**.
- تغيير بريد الحساب أو كلمة مروره أو حظره يجعل الرابط السابق غير صالح.

### الطابور ومراقبة الفشل

جدول `customer_auth_mail_jobs` يحتوي الحالة والمحاولات وسبب الخطأ، وليس واجهة عامة:
- `PENDING`: ينتظر الإرسال/إعادة المحاولة.
- `SENDING`: عامل إرسال حجز الرسالة بمهلة 60 ثانية.
- `SENT`: المزوّد قبل الطلب، وليس تأكيد قراءة أو تسليم inbox.
- `FAILED`: فشل نهائي أو مشكلة فك التشفير.
- `CANCELLED`: انتهت الصلاحية أو تغير الحساب/استهلك الرابط.

الأخطاء المؤقتة تُعاد حتى خمس محاولات بتأخير متزايد. الترحيب وإشعار التغيير ينتهيان بعد 7 أيام، ورسائل الرابط بانتهاء 30 دقيقة. السجلات النهائية تُحذف بعد 30 يومًا. الرموز المنتهية تُحذف بعد يوم إضافي.

مفتاح منع تكرار الطلب يُرسل إلى Resend. قاعدة البيانات تمنع تكرار **إضافة** الترحيب للحساب، لكن لا يمكن ضمان إرسال مرة واحدة تمامًا مع Brevo/SendGrid إذا تعطلت العملية بعد قبول المزوّد وقبل تحديث قاعدة البيانات.

للمشغّل المخوّل، استعلام لا يعرض الروابط أو الرسائل:

```sql
SELECT kind, status, COUNT(*) AS total
FROM customer_auth_mail_jobs GROUP BY kind, status;
SELECT id, kind, status, attempts, last_error, created_at
FROM customer_auth_mail_jobs
WHERE status='FAILED' ORDER BY created_at DESC;
```

## 5. الاختبارات وكيفية إعادتها

```bash
npm run typecheck
npm test
npm run build
# مع الموقع قيد التشغيل:
node verify/customer-auth-mobile.mjs
# اختبار مستقل: متصفح + خادم فعلي + قاعدة مؤقتة؛ النقل الخارجي للبريد محاكى فقط:
npx esbuild verify/customer-auth-functional.ts --bundle --platform=node --packages=external --outfile=.cache/auth-functional.cjs
node .cache/auth-functional.cjs
```

- نجح التحقق من الأنواع والبناء، و762 اختبارًا في 61 ملفًا.
- اختبارات وحدة وتكامل للترحيب والاسترجاع، التشفير، انتهاء الصلاحية، منع إعادة الاستعمال، إغلاق الجلسات، تغيير البريد/حظر الحساب، رفض مصدر خارجي، حدود الطلبات، وفشل/إعادة محاولة البريد.
- اختبارات عقود إرسال للمزوّدين الثلاثة، مع محاكاة HTTP؛ لم تُستخدم مفاتيح فعلية.
- 208 تحققًا لواجهة الهاتف على Chromium وFirefox.
- 23 تحققًا إضافيًا لدورة تسجيل → ترحيب → خروج → طلب استرجاع → تغيير → دخول جديد، عبر قاعدة بيانات وواجهات API فعلية مع محاكاة خدمة البريد الخارجية فقط.
- اللقطات الجديدة في `screenshots/auth-functional/`، ولا تعني أن المزوّد معدّ في بيئة المعاينة.

**قبل الإنتاج:** يلزم اختبار بريد حقيقي يملكه صاحب الموقع وتسجيل OAuth/SMS بمزوّداتهما الفعلية، ومراجعة تنبيهات الحزم الأمنية السابقة بشكل مستقل.
