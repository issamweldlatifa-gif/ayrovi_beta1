# مراجعة المشروع — ZAYROVI

**تاريخ المراجعة:** 2026-11-05
**الكود المراجع:** `a6874df5`، الفرع `arena/18ce2ed2-ayrovi-beta1`
**نوع العمل:** مراجعة واختبارات، دون تعديل وظائف التطبيق أو بياناته.

> **توضيح صاحب المشروع بعد المراجعة:** Stripe تجريبي وسيُزال قبل الإصدار، والتخزين الحالي للتجربة. لم يُطلب تعديل الدفع أو ترقية القرص؛ العمل التالي مقتصر على تنظيف الصور غير اللازمة. ملاحظات الدفع والتخزين أدناه تصف مخاطر الإعداد المراجع، وليست ادعاءً بأن بيئة التجربة تحتاج اشتراكًا أو تغييرًا فوريًا.

## الخلاصة التنفيذية

المشروع يملك تغطية اختبارية واسعة وبنية فعلية للتجارة، الحسابات، الإدارة، المخزون، الدفع، المحتوى، Lens وAYWEBs وClean. فحوص الأنواع والبناء والهوية نجحت، واختبارات تطبيق الهاتف نجحت كاملة. **لكن لا أوصي باعتبار المشروع جاهزًا لإصدار عام قبل معالجة النقاط عالية الأولوية أدناه.**

أهم المخاطر ليست كلها في الواجهة: إقرار webhook الدفع رغم فشل معالجته، تعارض ميزانية التخزين مع قرص النشر، وفشل مجموعة الاختبارات العامة. توجد كذلك مشكلات مثبتة في كاش الصور، ومخاطر تحميل عند زيادة المحتوى، ونقص في نطاق النسخ الاحتياطي الافتراضي.

هذه مراجعة موسعة بفحوص آلية كاملة ومراجعة يدوية للمسارات الحساسة، وليست ادعاءً بقراءة كل سطر أو اختبار كل تكامل خارجي. لم يثبت عيب P0 بهذه الفحوص؛ هذا لا يساوي شهادة خلو من الثغرات.

## 1. ما تم فحصه فعليًا

- الويب: البناء، TypeScript، الهوية والأيقونات، اختبارات الواجهات والعقود.
- الخادم: مجموعة الاختبارات العامة، middleware، CORS، معالجة الوسائط والكاش، استعلامات المحتوى، الدفع، إعدادات التخزين والنسخ الاحتياطي.
- الهاتف: TypeScript، جميع اختبارات المنطق، جميع اختبارات الواجهة، إعدادات API والمحاولات والتنقل وReels وأدوات الإصدار.
- الأمان: تدقيق npm للجذر والهاتف، وفحص عينات من حماية الحسابات والصلاحيات والروابط البعيدة وتوقيع الدفع.
- التشغيل: إعداد Render، وسير GitHub Actions ونتائج CI، وفحص التطابق مع إصدار Node المطلوب.
- تجربتان محليتان بحقن fetcher، دون شبكة خارجية، لإثبات سلوك كاش الصور.
- طلب OPTIONS محلي لإثبات عدم اكتمال قائمة ترويسات CORS.

## 2. النتائج مرتبة حسب الأولوية

**P1:** يعالج قبل إصدار عام. **P2:** عيب موثوقية أو توسع أو صيانة يستحق الإصلاح التالي. الأولوية لا تعني بالضرورة وجود استغلال أمني.

### R1 — P1: نجاح webhook الدفع يُقرّ رغم فشل التحقق أو تحديث الطلب

**المكان:** `src/customer/routes.ts:403–418` و`458–480`.

في مسار webhook الموقّع، إذا رمى `handleStripeWebhookByRef` خطأً، يُسجل الخطأ ثم يعاد `200` مع `received: true`. قد يكون الخطأ انقطاعًا مؤقتًا في استرجاع جلسة Stripe، أو فشلًا في قاعدة البيانات. لم أجد في المسار طابورًا دائمًا يُسجل الحدث الفاشل لإعادة معالجته؛ التعليق يعتمد على إمكانية تحقق العميل لاحقًا.

**الأثر:** قد يبقى طلب مدفوع بحالة معلقة إذا أغلق العميل التطبيق، لأن محاولة التسليم تلك أُقرت دون إنهاء المعالجة. هذا عيب موثوقية، وليس دليلًا على إمكانية تزوير دفع؛ المقارنة الفعلية للمبلغ والعملة والمرجع موجودة.

**الإصلاح المقترح:** حفظ الحدث في inbox دائم بمفتاح event ID ومعالجة idempotent وإعادة محاولة، أو إعادة رمز 5xx للأخطاء المؤقتة إذا لم يُحفظ العمل بشكل دائم. إضافة اختبار انقطاع Stripe/DB ثم التعافي دون فتح العميل.

**درجة الإثبات:** مراجعة مباشرة لمسار التحكم؛ لم يُنفذ دفع حقيقي.

### R2 — P1: ميزانية الكاش تقترب من كامل قرص الإنتاج

**المكان:** `render.yaml:10–20`؛ `src/services/cardNative.ts:282`؛ `src/services/imageIsolation.ts:421`؛ `src/services/imageComposition.ts:460`؛ `src/public/routes.ts:361`.

إعداد Render يخصص قرصًا بحجم **1GB**. الحدود المستقلة لأربعة أنواع كاش هي:

- بطاقات native: 192MiB.
- عزل الصور: 256MiB.
- تركيب الصور: 256MiB.
- proxy الصور: 256MiB.
- **المجموع: 960MiB**، قبل SQLite وWAL والمرفقات والنسخ اليومية.

هذه حدود قصوى مهيأة، وليست قياسًا لاستهلاك الإنتاج الحالي. لكن لا توجد ميزانية موحدة تترك حصة آمنة للبيانات الأساسية، والتنظيف لا يمنع تجاوزات لحظية بسبب الكتابات المتزامنة.

**الأثر:** خطر امتلاء القرص وفشل حفظ الطلبات أو الصور أو النسخ الاحتياطية عند نمو الاستخدام.

**الإصلاح المقترح:** حصة كاش إجمالية أصغر، حدود دنيا للمساحة الحرة، تنبيه امتلاء، وسياسة نقل الوسائط/النسخ إلى تخزين خارجي. لا يكفي تكبير القرص دون مراقبة.

### R4 — P1: النسخ التلقائي المرفق ليس استعادة كاملة للمشروع

**المكان:** `scripts/backup-sqlite.mjs:10–29,60–78`؛ `render.yaml:95–114`؛ `src/server.ts:601–630`.

السكربت ينسخ SQLite ويتحقق من سلامتها، وهذه نقطة جيدة. لكنه لا يأرشف `data/uploads` والمرفقات المشار إليها من قاعدة البيانات. النسخ المحلية تقع افتراضيًا على قرص البيانات نفسه، و`BACKUP_REQUIRE_EXTERNAL` مضبوط على `false` في إعداد النشر المرفق.

**الأثر:** استعادة ملف SQLite وحده بعد فقد القرص لا تستعيد صور المحتوى وإثباتات التحويل والمرفقات. وجود خيار S3 لا يثبت أنه مفعّل في الإنتاج؛ لم أفحص قيم الأسرار أو الوجهة الحقيقية.

**الإصلاح المقترح:** خطة استعادة تشمل DB والمرفقات، نسخة خارجية إلزامية في الإنتاج، تشفير وسياسة صلاحيات واحتفاظ، وتجربة استعادة على بيئة منفصلة. تسجيل عمر آخر نسخة خارجية ناجحة ومراقبته.

### R5 — P2: الفشل المؤقت للصورة يُخزّن دون انتهاء

**المكان:** `src/services/cardNative.ts:251–281`.

عند فشل fetch أو المعالجة، تُحفظ `{file:null,kind:'unreadable'}`. في الطلب التالي، `cached.file == null` يعيد النتيجة فورًا دون TTL أو إعادة جلب.

**إثبات محلي:** طلبان متتابعان للصورة نفسها مع fetcher يرمي خطأ شبكة مؤقتًا أنتجا:

```json
{"first":{"file":null,"kind":"unreadable"},"second":{"file":null,"kind":"unreadable"},"fetchCalls":1,"metadataFiles":1}
```

**الأثر:** المسار السريع يبقى معطلًا لهذا المفتاح إلى أن تُزال البيانات الوصفية. قد تنجح مسارات fallback؛ لذلك لا يعني ذلك أن الصورة ستظل مكسورة دائمًا، لكنه قد يثبت استخدام المسار الأبطأ بعد عطل عابر.

**الإصلاح المقترح:** التمييز بين نتيجة تحليل مستقرة وعطل خارجي مؤقت، مع TTL قصير للأخطاء المؤقتة وإعادة محاولة مضبوطة، واختبار fail ثم recover.

### R6 — P2: طلبات الصورة الباردة المتزامنة لا تتشارك العمل

**المكان:** `src/services/cardNative.ts:241–282`؛ `src/public/routes.ts:342–365`؛ `src/services/imageIsolation.ts:385–421`.

المسارات تفحص وجود الكاش ثم تجلب وتعالج وتكتب. لا يوجد في هذه الدوال single-flight موحد أو حد عام للعمل المتزامن. محدد معدل الطلبات لا يعادل حد المعالجات المتزامنة.

**إثبات محلي لمسار native:** تشغيل طلبين متزامنين للمفتاح نفسه أعطى `fetchCalls: 2`.

**الأثر:** تنزيل وفك صور ومعالجة مكررة عند الطلب البارد؛ وقد يرتفع استهلاك CPU والذاكرة ويتأثر باقي API. لم يُنفذ اختبار ضغط إنتاجي، لذلك لا أنسب إليه وحده البطء المبلغ عنه على الهاتف.

**الإصلاح المقترح:** Promise map حسب مفتاح الكاش، semaphore محدود، كتابة ذرية للملفات، ومؤشرات queue time/cache hit/processing time.

### R7 — P2: Reels والمنشورات تُجلب بلا pagination، والعدادات تقف عند 60

**المكان:** `src/public/routes.ts:838–857,900–906`؛ `apps/mobile/src/api/hooks.ts:111–121`؛ `src/services/contentProducts.ts:173–211`.

واجهتا Reels والمنشورات تعيدان جميع العناصر المنشورة. Reels يحسب عدادي views/likes لكل صف، ثم تُجلب روابط المنتجات لكل المجموعة. واجهة counts تقطع IDs إلى 60، بينما الشاشات تمرر IDs المجموعة كاملة.

**الأثر:** زيادة حجم الرد والعمل على الخادم والهاتف مع نمو المكتبة؛ وعدم اكتمال رد العدادات بعد أول 60 ID. ليس هذا قياسًا بأن مكتبة الإنتاج تجاوزت الحد الآن.

**الإصلاح المقترح:** cursor pagination وحد أقصى للصفحة، تجميع العدادات للدفعة المرئية، وAPI لجلب Reel محدد عند فتح رابط مباشر. اختبار 61 عنصرًا ثم مكتبة كبيرة.

### R8 — P2: قائمة CORS لا تسمح بترويسة عميل الهاتف

**المكان:** `src/server.ts:284–288`؛ `apps/mobile/src/api/client.ts:76–83`؛ `apps/mobile/src/state/session.tsx:146`.

العميل يرسل `x-ayrovi-client`، لكن `allowedHeaders` لا تتضمنها.

**إثبات HTTP محلي:** preflight من origin مسموح، يطلب `x-ayrovi-client`، تلقى 204 لكن قائمة `Access-Control-Allow-Headers` لم تتضمن الترويسة المطلوبة.

**الأثر المشروط:** متصفح Expo Web عند استعمال API من أصل آخر قد يمنع الطلب حتى لو كان origin مسموحًا. تطبيق React Native الأصلي لا يخضع لـCORS المتصفح؛ هذا ليس تفسيرًا مثبتًا لفشل APK.

**الإصلاح المقترح:** توحيد عقد الترويسات وإضافة اختبار preflight بعميل حقيقي. عدم فتح جميع origins أو الترويسات دون حاجة.

### R9 — P2: سياسة إعادة المحاولة قد تطيل الانتظار وتكرر أخطاء نهائية

**المكان:** `apps/mobile/app/_layout.tsx:39–45`؛ `apps/mobile/src/api/client.ts:88,201–223`.

الإعداد العام `retry:2`، ومهلة الطلب الافتراضية 12 ثانية، دون predicate عام يستبعد 401/403/404 والإلغاء. بعض الشاشات قد تملك overrides؛ الملاحظة تخص الاستعلامات التي ترث الإعداد العام.

**الأثر:** إذا انتهت مهلة المحاولات الثلاث كلها، فمجموع مهل الشبكة وحده 36 ثانية، تضاف إليه فترات backoff. هذه نتيجة من الإعدادات، وليست قياس سرعة فعليًا.

**الإصلاح المقترح:** عدم إعادة الأخطاء النهائية أو الإلغاء، واحترام Retry-After، وتفريق أخطاء الشبكة/الخادم المؤقتة، وإظهار المحتوى المخزن أثناء التحديث بدل حجب الشاشة.

### R10 — P2: أداة فحص الإصدار تستهدف فرعًا قديمًا افتراضيًا

**المكان:** `apps/mobile/scripts/release-preflight.mjs:25–31,223–230,309–313`؛ `apps/mobile/README.md:115–119`.

الفرع الافتراضي في الأداة هو `arena/9fd9a9fc-ayrovi-beta1` وليس فرع العمل الحالي. تستخدم الأداة هذا الفرع لمقارنة النسخة المنشورة وجلب الرأس. توجد أيضًا أمثلة توثيق لعناوين API تختلف عن الأصل المعتمد في CI الحالي.

**الأثر:** نتائج فحص الإصدار قد تخص كودًا آخر أو تعطي إنذارات مضللة إذا نُفذت الأداة دون `--branch`.

**الإصلاح المقترح:** اشتقاق الفرع من checkout أو إلزام `--branch`، وإظهار الفرع وSHA وAPI origin بوضوح في ملخص الإصدار، وتوحيد أمثلة التشغيل.

### R11 — P2: تنبيهات تبعيات متوسطة ومنخفضة تحتاج معالجة واعية

**المكان:** ملفا lock للجذر والهاتف؛ `apps/mobile/scripts/patch-router-decoder.cjs`؛ `.github/workflows/security-review.yml`.

- الجذر: `glob` و`minimatch` و`rimraf` تظهر ضمن الحزم المتأثرة المتوسطة.
- الهاتف: سلسلة Expo/Jest تضم 8 حزم متأثرة متوسطة و6 منخفضة.
- يوجد backport لـdeepmerge واختبار جسر أمني ضمن الاختبارات الناجحة.
- بعض اقتراحات npm تتضمن تغييرًا رئيسيًا أو رجوع Expo إلى إصدار أقدم؛ ليست خطة ترقية مقبولة تلقائيًا.

**الإصلاح المقترح:** ترقية متوافقة أو override مدروس، وتوثيق التنبيهات المخففة بالـbackport، ثم إعادة اختبارات Router وMetro والتصدير والبناء. **لا تنفذ `npm audit fix --force` بشكل أعمى.** لم يثبت هنا استغلال فعلي لهذه التنبيهات.

## 3. نقاط جيدة ينبغي الحفاظ عليها

- اختبارات الهاتف واسعة، بما فيها التنقل، Clean، الكاميرا، Reels، الحسابات وتدفقات الشراء.
- SQLite مضبوط على WAL وforeign keys وbusy timeout، مع معاملات في المسارات المالية والمخزنية ومهاجرات بيانات أحادية التنفيذ.
- حماية الصلاحيات للإدارة وERP موجودة، ولم أجد في العينات المراجعة سببًا لإزالتها أو استبدالها بنظام موازٍ.
- استخدام scrypt وأملاح ومقارنة زمنية ثابتة لكلمات المرور، وحدود لمحاولات الدخول.
- توجد حماية للروابط الخارجية من SSRF والتحقق من redirects وقيود حجم/نوع الصور.
- الدفع لا يعتمد على حالة واردة من العميل فقط؛ توجد إعادة تحقق من المزود ومقارنة المبلغ والعملة والمرجع.
- توجد فحوص هوية وخطوط وأيقونات فعلية، ولا ينبغي تعطيلها لتجاوز إخفاقات اختبارات قديمة.
- تقسيم بعض حزم الويب موجود فعلًا؛ تحذير حجم الحزمة ليس دليلًا على تحميل لوحة الإدارة كاملة لكل زائر.

## 4. ترتيب العمل المقترح ومعيار القبول

1. **الدفع:** اختبار webhook يفشل مؤقتًا ثم ينجح لاحقًا، مع تسجيل المبلغ مرة واحدة ودون حضور العميل.
2. **التخزين والاستعادة:** ميزانية كاش موحدة وحيز آمن، وتجربة استعادة DB مع المرفقات من نسخة خارجية.
3. **CI:** تحديث العقود القديمة دون التراجع عن التصميم المعتمد، ومعالجة الاختبار الزمني، ثم تشغيل المجموعة الكاملة خضراء.
4. **الصور:** خطأ مؤقت يتعافى، وطلبات متزامنة للمفتاح نفسه تنفذ جلبًا/معالجة واحدة، مع قياس انتظار المعالجة.
5. **المحتوى:** صفحات محدودة، رابط Reel مباشر يعمل، والعدادات كاملة بعد العنصر 60.
6. **الاتصال:** اختبار CORS عبر المتصفح، وسياسة retry محددة بالخطأ، وفحص الإصدار يستهدف SHA الحالي.
7. **التبعيات:** تحديثات متوافقة مع إثبات بقاء الجسر الأمني أو الاستغناء عنه بأمان.
8. **الهاتف الحقيقي:** شبكة بطيئة/انقطاع، فتح Reels وسحب عدة فيديوهات، رجوع للشاشات، تسجيل دخول، لوحة مفاتيح وكاميرا، مع تثبيت رقم البناء الذي جُرب.

## 5. حدود المراجعة

- خادم Render ومزودو الدفع وAI والتسوق خارج قائمة الشبكة المسموحة لهذه البيئة؛ لم أقس زمن استجابة الإنتاج أو أتأكد من تهيئة أسراره.
- لم أطلع على بيانات العملاء الحقيقية، ولم أشغل دفعًا حقيقيًا أو استعادة على قرص الإنتاج.
- لا يوجد هاتف فعلي موصول هنا. نجاح UI tests أو تصدير سابق أو APK من CI ليس إثباتًا بأن عيب الهاتف زال.
- بعض اختبارات الجذر فشلت لأن العقود لا تتوافق مع التغييرات المعتمدة؛ لا تُختزل هذه النتيجة في أن كل إخفاق عيب تشغيل.
- بيئة Node المحلية أقل من الإصدار المثبت في المشروع؛ يجب اعتماد CI المطابق عند إغلاق الملاحظات.
- لم تُغيّر المراجعة ملفات وظائف المشروع. التغيير المقصود الوحيد داخل Git هو هذا التقرير؛ السجلات والتجارب المؤقتة في `.cache/`.
