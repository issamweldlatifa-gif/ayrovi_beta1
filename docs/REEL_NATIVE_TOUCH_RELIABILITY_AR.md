# موثوقية لمس Reel في تطبيق الهاتف

> تحديث لاحق: طلب المالك استبدال كل فيديوات Reels السابقة بخمسة ملفاته من Drive. حزمة الأمثلة والأداة اليدوية المذكورة تاريخيًا هنا أزيلتا؛ المرجع الحالي [فيديوات المالك](REEL_OWNER_COLLECTION_AR.md). لا تُعد إضافة عينات CC0 القديمة.

## بلاغ المالك والنطاق

البلاغ: الفيديو ثقيل، والضغط كان يفتح العارض وأصبح أحيانًا لا يعطي نتيجة. لم يُحسم هل كل الحالات من الرئيسية أو شاشة Reels، ولا توفّر تسجيل جهاز/اسم فيديو/قياس إطار أول. المالك قرر تعليق تحديثات واجهة الويب إلى قرار مستقل؛ هذه الدفعة تخص mobile فقط. لا تعديل backend أو client/ أو تخزين أو تحويل فيديوهات.

## ما ثبت من الكود وما هو محتمل

معاينة الرئيسية كانت داخل Pressable يضم VideoView أصليًا. مصدر expo-video المثبّت في Android (`VideoView.kt`) يوضح أن إضافة PlayerView تغيّر إرسال اللمس إلى JS وأن `onTouchEvent` يعيد true ويعيد إرسال أحداث يدويًا. لذلك الاعتماد على pointerEvents في VideoView وحده مع إحاطته بزر تنقل مسار هش محتمل. هذا دليل على مسار تداخل ممكن، وليس إعادة إنتاج مثبتة لكل ضغطة مفقودة على جهاز المستخدم.

## التعديل المحدود

- حاوية المرئيات في بطاقة الرئيسية أصبحت View غير تفاعلية (`pointerEvents=none`, `collapsable=false`).
- زر فتح العارض طبقة شقيقة absoluteFill بعد المرئيات، وليس أبًا لمشغل الفيديو. له نفس الدور والتسمية ومسار `/reels-viewer?id=...`؛ أزرار الخيارات بقيت منفصلة خارج الوسائط.
- أُضيف غلاف RN غير تفاعلي وغير قابل للإزالة حول VideoView في المعاينة والمشغل، لعدم الاعتماد على تطبيق خصائص اللمس في view أصلي مخصص وحده. تحكم تشغيل/إيقاف وإعادة المحاولة يبقى في طبقات React Native التفاعلية فوقه.
- عند تعطيل autoplay لتقليل الحركة لا يُنشأ مشغل معاينة متوقف بلا حاجة؛ فتح الفيديو بالضغط يبقى متاحًا. بقية المعاينات تظل مقيدة بالظهور والتركيز. لم تُرفع أعداد المشغلات أو نافذة القائمة.

## الأدلة المنفذة

- 7 مجموعات UI / 27 اختبارًا ناجحًا: home section، preview touch، viewer، playback status، preview activity، tray، preferences.
- اختبارات جديدة تؤكد أن زر التنقل ليس من أبناء الطبقة المرئية، وأنها غير تفاعلية وغير قابلة للـcollapse، وأن التنقل يبقى يعمل بعد ظهور/اختفاء المعاينة، وأن تعطيل autoplay لا ينشئ player ويظل يسمح بالفتح.
- 3 ملفات unit/API / 32 اختبارًا ناجحًا (reelRail/reelTray/social).
- typecheck للهاتف نجح. اختبارات UI شُغلت بـ `--forceExit` بسبب handles باقية في harness (ظهر أيضًا قبل التعديل)، وظهرت تحذيرات act من SessionProvider؛ النجاح لا يثبت أن كل handles/تحذيرات الاختبار عولجت.

هذه محاكاة JS/شجرة UI، لا محاكاة لمس Android الأصلي أو فك فيديو حقيقي. لم يُبن APK أو يُثبّت على هاتف ضمن هذه الدفعة، ولم يُقَس FPS أو زمن أول إطار. تعديل الكود لا يصل تلقائيًا لنسخة مثبتة قديمة.

## قبول الجهاز والمتابعة اللازمة للثقل

بعد تثبيت نسخة تحتوي التغيير، على الجهاز المعني:

1. تجربة فتح/رجوع متكررة (مثل 20 مرة) من الرئيسية أثناء تشغيل المعاينة وقبل اكتمالها، مع السحب الأفقي ثم الضغط، والضغط على الخيارات بشكل مستقل.
2. فحص شاشة Reels: السحب، الإيقاف/التشغيل، الخلفية/العودة، الخطأ وإعادة المحاولة؛ ربط أي عطل بنقطة الدخول والفيديو.
3. فصل زمن استجابة الضغطة/ظهور العارض عن زمن تحميل metadata وزمن الإطار الأول والتقطيع أثناء التشغيل؛ مقارنة شبكة جيدة وضعيفة، وفتح بارد ومتكرر.
4. جمع نوع الجهاز وإصدار APK ومدة/حجم/دقة وترميز فيديو متأثر، وطلبات media (بما فيها Range/206) وسجل المشغل دون tokens أو بيانات حسابات. فحص CPU/RAM متزامن عند الإمكان.

لا يُستنتج أن CPU الخادم هو السبب. أحجام الفيديو وترميزه وموقع moov/faststart ودعم range والشبكة وفك الفيديو على الجهاز مرشحون يحتاجون عينات. لا تُفعّل تحويلًا عامًا أو caching أو شراء خدمات قبل القياس والقرار المناسب. كذلك العارض يجلب صفحة anchor بمفتاح query مستقل؛ زمن API يمكن أن يؤخر ظهور محتواه ويحتاج قياسًا مستقلًا، دون اختراع cursor أو عرض حالة نجاح زائفة.
