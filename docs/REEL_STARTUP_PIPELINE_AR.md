# مسار بدء Reel — الدفعة الأولى

> تحديث لاحق: طلب المالك استبدال كل فيديوات Reels السابقة بخمسة ملفاته من Drive. حزمة الأمثلة والأداة اليدوية المذكورة تاريخيًا هنا أزيلتا؛ المرجع الحالي [فيديوات المالك](REEL_OWNER_COLLECTION_AR.md). لا تُعد إضافة عينات CC0 القديمة.

## الهدف والنطاق

المالك طلب تجربة فيديو خفيفة وموثوقة مثل تطبيقات التواصل. الهدف يشمل زمن الاستجابة للضغط، ظهور أول إطار، السحب والتقطيع واستهلاك الذاكرة، وليس مجرد اختفاء spinner. هذه دفعة أولى للهاتف فقط؛ لا تغيير لواجهة الويب أو backend أو التخزين أو ملفات فيديو المالك. [إصلاح اللمس السابق](REEL_NATIVE_TOUCH_RELIABILITY_AR.md) ما زال يحتاج قبول جهاز.

## 1. تسليم بصري سريع بين الرئيسية والعارض

قبل: الرئيسية تملك بيانات Reel، لكن العارض يستعمل query بمفتاح anchor مستقل؛ عندما تكون هذه query باردة، لا صفوف للعارض حتى يرد طلب API.

الآن: `useReels` يستعمل placeholderData للعنصر المختار فقط من query الرئيسية عندما تكون حديثة (حتى 60 ثانية وفق staleTime الحالي) وغير invalidated. لا تنسخ صفحات كاملة أو cursor الرئيسية، ولا تخزن placeholder كاستجابة خادم. يعرض غلاف/معلومات العنصر المتاحة أثناء الطلب. إذا لا يوجد العنصر أو البيانات قديمة/ملغاة، يبقى سلوك التحميل البارد.

**التحقق لم يُختصر:** طلب anchor الحقيقي يستمر، والمشغل لا يُنشأ لهذا placeholder قبل أن تأتي الاستجابة. `isPlaceholderData` يعطّل active في ReelCard ويُظهر التحميل؛ بالتالي لا view mutation بسبب عرض الغلاف المؤقت. لا تشغيل اعتمادًا على نسخة محلية غير مؤكدة. هذا يحسن الاستمرارية البصرية، **لا يزيل انتظار API قبل التشغيل**. الخطأ يزيل placeholder ويعرض حالة الفشل؛ response فارغة/بديلة تبقى صاحبة القرار. pagination الحقيقية تأتي من استجابة anchor وحدها.

## 2. أول إطار ليس readyToPlay

`ReelPlayback` يراقب `VideoView.onFirstFrameRender`. حالة readyToPlay وحدها لا تخفي التحميل قبل أول إطار. إذا بقي readyToPlay دون إطار أثناء foreground وتشغيل غير متوقف وغير محجوب، توجد مهلة 20 ثانية تنقل إلى خطأ قابل لإعادة المحاولة بدل انتظار بلا نهاية. هذه مهلة منفصلة عن مهلة تحميل المصدر الموجودة؛ الزمن الإجمالي ليس حدًا واحدًا قدره 20 ثانية. تُزال مهلة الإطار عند pause/background/حجب المشغّل أو unmount.

إعادة المحاولة تبدأ محاولة إطار جديدة، دون حلقة retry تلقائية. لم تتغير نافذة القائمة أو أعداد المشغلات؛ ما زال المشغّل للبطاقة النشطة فقط. لا prefetch لفيديو تالٍ أو caching على القرص أو تعديل bufferOptions بالتخمين.

## 3. قياس محلي محدود

`reelPlaybackTiming.ts` يجمع firstFrames / abandoned / totalFirstFrameMs / maxFirstFrameMs داخل العملية فقط، مع snapshot منفصل. يبدأ قبل تحميل المصدر وينتهي عند أول callback إطار، أو يصنف abandoned عند ترك المحاولة قبل الإطار. هذا ليس معدل أخطاء: abandoned قد يعني السحب/الخروج أو استبدال محاولة. callback مكرر لا يحتسب مرتين.

السجل الاختياري `EXPO_PUBLIC_REEL_TIMING_LOGS=true` يحتاج تضمينه في build الهاتف؛ لم نفعّله ضمن الأمر الذي نفّذناه. الحقول فقط event / outcome / durationMs. لا IDs أو URLs أو حسابات أو tokens. فشل sink لا يعطّل التشغيل. لا رفع لسجلات أو endpoint أو persistent storage. القياس monotonic محلي ويشمل أي انتظار أو pause ضمن المحاولة، لا زمن الضغطة أو API قبل mount، وليس FPS أو p95 أو زمن الشبكة وحدها.

## 4. أدلة ما قبل/بعد المنفذة

- اختبار query بشبكة مؤجلة: **قبل وصول response** تظهر الآن بيانات العنصر المختار كـplaceholder، دون cursor؛ ثم تستبدلها البيانات الحقيقية. بيانات أقدم من 60 ثانية/invalidated لا تُسلّم، وفشل الخادم لا يبقيها كنجاح وهمي.
- اختبار العارض يثبت active=false حتى تأكيد anchor، ثم active=true، مع نافذة virtualization السابقة.
- اختبارات أول إطار تثبت بقاء التحميل عند readyToPlay، اختفاءه بعد callback فعلي محاكى، وفشل ready-but-no-frame وإزالة timer.
- 8 مجموعات UI / **34 اختبارًا ناجحًا**؛ 4 ملفات unit/API / **34 اختبارًا ناجحًا**؛ typecheck للهاتف نجح.
- تصدير bundle Android عبر `CI=1 npx expo export --platform android ...` نجح. هذا فحص bundle، **ليس بناء APK أو تثبيتًا على هاتف**.
- UI harness ما زال يعطي تحذيرات act/handles من مزودي الحالة؛ استُعمل `--forceExit` كما في الدفعة السابقة، دون ادعاء إصلاحها.

هذه مقارنة حالة سلوكية تحت طلب مؤجل، **ليست نتيجة زمن أداء على هاتف** ولا نسبة تحسن. لا توجد أرقام حقيقية لزمن أول إطار أو الذاكرة بعد هذه الدفعة.

## 5. فحص عينة الفيديو المتاحة

العينة العامة المحلية `flower-cc0-v1.mp4`: حجم 1,128,375 بايت؛ top-level ftyp عند 0 بحجم 32، moov عند 32 بحجم 4,238، mdat عند 4,270 بحجم 1,124,105. وجود moov قبل mdat يعني أن هذه العينة لا تحتاج إصلاح نقل moov إلى البداية. لم نغيّر ملفها.

اختبار `tests/reel-demo-local-media.test.ts` نجح باختباريه، بما فيه HTTP Range 0–127 الذي يرجع 206 وContent-Range وMIME صحيح عبر express.static على عينة الاختبار. **ليس فحص شبكة الإنتاج أو reverse proxy**، ولا دليل على صحة range/codec لكل upload أو مصدر بعيد. لم يُستخدم ffprobe لقياس codec/dimensions/bitrate، ولم يُفتح محتوى خاص.

## التالي قبل الادعاء بالسلاسة

1. بناء/تثبيت APK به التغييرات وقبول الضغط المتكرر من الرئيسية وReels على الجهاز المتأثر.
2. مقارنة نفس الفيديو والجهاز والشبكة قبل/بعد: زمن الضغطة→العارض، API، المصدر→أول إطار، التقطيع، CPU/RAM بعد سحب متكرر، فتح بارد ومتكرر. لا تخلط المتوسط مع p95 أو التوقيت الاصطناعي مع الإنتاج.
3. فحص عينات فيديوات المالك (الدقة/الترميز/الحجم/bitrate/moov) وتسليمها عبر Range على المضيف الفعلي بإذن مناسب، دون نشر روابط خاصة.
4. بعد القياس فقط، تجربة تحضير فيديو تالٍ واحد بميزانية ذاكرة/شبكة وإلغاء عند مغادرة الشاشة. لا نضيف مشغّلًا ثانيًا أو buffer كبيرًا لأن الهدف «مثل التواصل» دون إثبات كلفة التحسين.

لا ضمان سلاسة نهائي، ولا تشخيص CPU الخادم كسبب وحيد. ما زلنا في دفعات تحسين قابلة للاختبار والتراجع.
