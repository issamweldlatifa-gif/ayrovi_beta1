# ZAYROVI — Connected، نفاذ الفرق، والشحن

## قرار الدفعة

استعملنا من `All_In_One_Enterprise_System_Specs-v2.pdf` مبدأ الإدارة الموحّدة، واجهة RTL، ظهور الأدوات حسب التكليف، الصلاحيات في الـAPI والتدقيق. أخذنا من الصورة فكرة اللوحة الداكنة والعنصر البصري الملوّن للدخول فقط. ما نسخناش IMEI، تقارير أداء الأفراد، تحويل كل تفاعل لصفقة أو selector الفرع الشكلي. ما بدّلناش سياسة قاعدة البيانات أو البنية التحتية أو الملكية الحالية للطلبات.

## شنوّة خدام

| مساحة | خدمات الدليل | من يقرا ويطلب؟ |
| --- | --- | --- |
| CRM | البريد المهني وWhatsApp Business | `commerce:read` وتكليف CRM في Connected |
| العمليات والشحن | ناقل ومزوّد | `orders:write` وتكليف العمليات |
| المالية | بنك، PSP، فاتورة إلكترونية | `reports:read` وتكليف المالية |
| المحتوى | Canva، CapCut، Figma، AI | `content:write` وتكليف المحتوى |
| المنصّة والتطوير | مستودعات، Drive، تخزين وسائط، بيانات | `settings:write` وتكليف المنصّة |

- الدخول في القائمة عبر **Connected → Services** لكل فريق. `SUPER_ADMIN` يقرأ الكل؛ وحده يعيّن/يسحب التكليف من `Affectations` بالإيميل الداخلي الكامل، ويوافق على التحضير أو يغلق الطلب. بقية الحسابات لا ترى شيئًا افتراضيًا. التكليف يخص **Connected** فقط، ولا يوسع وصول الحساب إلى أي شاشة أو بيانات قديمة. تغيير الدور أو تعطيل الحساب يلغي التكليف والجلسات القديمة. تقسيم كل الـ legacy حسب ملكية الحريف/الفرع أو فصل أدوار المبيعات والمحاسبة مشروع لاحق لا يجب محاكاته بإخفاء أزرار فقط.
- الكتابة تتطلب **جلسة دخلت بالتحقّق الثنائي**، موش مجرّد 2FA مفعّلة على الحساب. بعد الإعداد لازم عودة تسجيل الدخول. حالة التحقق محفوظة في جلسة الخادم؛ تفعيل أو تعطيل 2FA يخرج الأجهزة الأخرى، وتعطيلها يسقط علامة التحقّق من الجلسة الحالية. كل كتابة تمرّ عبر CSRF والتدقيق. ما جعلناش 2FA إلزامية للدخول إلى كل الشاشات القديمة قبل خطة تفعيل واسترجاع للحسابات.
- الدليل ثابت في الكود. الطلب يرسل `action` فقط؛ لا API keys، URLs، access tokens أو كلمات مرور. الحالة `APPROVED_FOR_SETUP` تعني موافقة على التحضير وليس «متصل». لا يوجد outbound HTTP ولا OAuth أو صلاحيّة إرسال أو نشر أو تحويل مالي في هذه الواجهة. التعيين والطلب والتعديل والرفض المصادق عليه مسجّلون دون أسرار.
- الدخول: حدّ للمحاولات بالشبكة والحساب، رفض طلبات المتصفح ذات `Sec-Fetch-Site` غير الموثوق عندما تكون المعلومة موجودة، رسائل موحّدة لرفض بيانات الاعتماد و`Retry-After`. حدّ المحاولات داخل نسخة التطبيق؛ حماية عدة نسخ تتطلب مخزنًا مشتركًا أو ضابطًا عند الحافة مع `TRUST_PROXY_HOPS` مضبوط حسب طوبولوجيا النشر. الاختبارات دفاعية ولا تدّعي تدقيق اختراق شامل.
- الشحن: مرجع UPS/DHL يولّد رابطًا لبوابة التتبّع من قالب ثابت؛ يدعم ناقل آخر برابط HTTPS عمومي اختياري. الخادم لا يزور أو يجلب أي رابط. تعديل المرجع بعد الشحن لا يعيد تاريخ الشحن ولا يرسل إشعار شحن مكررًا. يبقى العميل يشوف التتبّع فقط بعد الشحن وفق ملكية الطلب. الفاتورة PDF تبقى خاصة بمن له صلاحية وعلى المسار الموجود، وليست وثيقة شحن أو فاتورة ضريبية إلكترونية.

## بوابة الربط الحقيقي لكل مزوّد

1. مزوّد محدّد، حساب sandbox باسم المؤسسة، صاحب وظيفي، والغرض والبيانات المطلوبة وأقل scopes. بعد الموافقة، secret manager خارج المتصفّح/المحادثة/المستودع. حساب تطوير منفصل على الإنتاج مع سياسة فك الربط وتدوير الأسرار.
2. مزوّد OAuth: صلاحيات ثابتة، `state` مرتبط بالجلسة، PKCE وتحقّق redirect، تخزين مشفّر، تجديد وإبطال، وظائف منفصلة للقراءة والكتابة. مزوّد API: endpoints ثابتة وegress محدود، لا URL يختارو الموظف. سجّل أخطاء منزوعة الأسرار، ولا تعطّل العمليات الأساسية إذا تعطّل المزوّد.
3. **الشحن أولًا:** اختر ناقلًا، وجِب وثائق sandbox وأنواع الشحن والمتابعة المطلوبة. ربط `orderId` بمعرّف الشحنة الخارجي دون إرسال تفاصيل الدفع. اجعل الإنشاء idempotent، واختبر توقيع وتكرار أحداث التتبّع وترتيبها قبل تغيير حالة طلب. طباعة الملصقات، المرتجع، والدفع عند التسليم مراحل مستقلة، كل واحدة بصلاحية وبيانات على قدّها.
4. **الفواتير:** نجرب PDF الخاص، ثبات رقم الفاتورة ونسخة المستند، ثم عيّنات المحاسب. الفاتورة الإلكترونية تحتاج الكيان والنظام القانوني/الضريبي ومزوّدًا معتمدًا وطريقة اعتماد واختبار، ولا تتفعّل من قائمة النقل.
5. **قبل الإنتاج:** مراجعة الصلاحيات لكل مورد، تثبيت خطة استرجاع حساب المشرف و2FA، اختبار HTTPS/Proxy ورفض الطلبات ونسخ واسترجاع القاعدة، مراجعة تدقيق أسرار/اعتمادات، ومحاكاة فشل المزوّد. لا تفعيل أو نقل بيانات إنتاج بهذه الدفعة.

مرجع باقي المسارات: [خارطة عمليات ZAYROVI](ZAYROVI_OPERATIONS_ROADMAP_AR.md).

## تدقيق ما قبل الدفع — موصّل DHL

أضيف موصّل **DHL Express Shipment Tracking – Unified** للقراءة فقط، على [العنوان الرسمي الموثّق](https://developer.dhl.com/tracking?language_content_entity=en). يلزم: جلسة 2FA + حق الطلبات + تكليف Connected للعمليات (أو المشرف العام)، موافقة `DHL Express · Tracking`، و`ZAYROVI_DHL_TRACKING_ENABLED=true` ومفتاح مخزّن في أسرار الخادم. يبقى معطّلًا افتراضيًا. يستعمل مرجع الشحنة الموجود على الطلب فقط. لا يرسل العنوان، الهاتف، اسم العميل أو تفاصيل الدفع، لا يتبع redirects، ويضع timeout وحدّ حجم. يطابق مرجع الشحنة قبل إظهار رمز الحالة والتوقيت فقط، ولا يحفظ رد المزود أو يغيّر حالات الطلب. القراءة اليدوية والرابط الخارجي يبقوا صالحين من غير API. fixture المختبر ما يثبتش نجاح مفاتيح أو شحنة حقيقية.

أغلق التدقيق كذلك تسريب المعطيات التجارية لمستخدم المحتوى من لوحة القيادة والإشعارات، وقلّص بيانات بطاقة الحريف والطلب إلى المعطيات اللازمة (من غير بصمة كلمة السر أو payload وروابط الدفع). رسائل أخطاء AI من المزود ما عادش تتكتب بالحرف في سجلّ الخادم. PDF ينكتب مؤقتًا ثم يتنقل للمسار النهائي، وإعادة الإرسال تستعمل المسار الناتج من نفس العملية؛ تسمية البريد «PDF» لتفادي أي لبس مع الفوترة القانونية.

**الربط المالي معلّق:** لا نرسل مستندات ضريبية أو نعتبر PDF فاتورة إلكترونية. بعد تحديد الكيان والنشاط والبلد، نحتاج مواصفات البيئة الرسمية وحساب اختبار وتوقيع/قبول موثّق. قرار اعتماد الناقل في الإنتاج يتطلب اشتراك المؤسسة وشروط استعمال بيانات التتبع وتجربة شحنة مصرح بها قبل التفعيل؛ لا أسرار في Git أو المحادثة. Connect عام مفتوح لأي URL/Token لا يُعتمد: كل مزوّد يحتاج adapter وقواعد صلاحيات واختبار منفصل.

**التحقق من النشر:** `Verify Back Office rollout` يقارن commit المتوقع بمعلومة `/api/ready` على عنوان Render المحدد، ويختبر الصفحة العربية والـAdmin ورفض API قبل الدخول. لا يغيّر إعدادات البنية التحتية ولا يثبت نجاح تجربة عضو مُسجّل في الإنتاج. للتراجع استخدم إعادة نشر النسخة السابقة من نفس القناة؛ لا تُرجع ملف SQLite أو تحذف الجداول المضافة لمجرد rollback الكود.
