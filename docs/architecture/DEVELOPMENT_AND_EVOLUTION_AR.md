# اتفاق تطوير ZAYROVI والتحضير للتوسّع

**الحالة: توجّه وافق عليه صاحب المشروع وسجّله للمطوّرين اللاحقين.**

## 1. المرحلة والهدف

نحن في مرحلة تصميم التطبيق وإضافة الوظائف وتجربتها، وليس إطلاق تشغيل تجاري. لا نؤخر البناء لشراء خدمات إنتاجية أو لإنشاء microservices. نستخدم بيانات اختبار، ونختبر الوظائف فعليًا دون حذفها أو تبسيط المشروع لإخفاء مشاكل الأداء.

الهدف: **تطبيق واحد بحدود داخلية واضحة الآن، يمكن تطويره ونقل أجزائه تدريجيًا لاحقًا، دون إعادة كتابة من الصفر.** تكلفة الاستضافة وقوة CPU لا تعوّضان تنظيم الكود؛ ولا تُعتبر اختبارات الوظائف وحدها إثباتًا لتحمل الحمل أو سلاسة الهاتف.

## 2. الحقيقة الحالية، لا افتراضات الجاهزية

- الخلفية مقسمة إلى مجالات مثل CRM والكتالوج والمخزون والمشتريات والعملاء، لكنها تشترك حاليًا في عملية خادم وقاعدة SQLite.
- التطبيق الأصلي يفصل API والميزات والتصميم والحالة؛ وتوجد عقود مشتركة في `shared`.
- توجد استعلامات مرتبطة بـSQLite مباشرة داخل مسارات، وملفات كبيرة تجمع مسؤوليات كثيرة؛ ترتيب المجلدات وحده لا يعني استقلال المجالات.
- التخزين في مواضع يعتمد على ملفات محلية، وبعض المسارات مرتبطة بمكان قاعدة البيانات. دعم رفع النسخ الاحتياطية إلى S3-compatible ليس تنفيذًا عامًا لتخزين صور التطبيق على S3.
- الانتقال إلى PostgreSQL أو S3 أو عدة خوادم **ممكن لكنه غير جاهز بمجرد تغيير متغيرات البيئة**. لا تُقدَّم هذه الإمكانات كميزات مكتملة قبل تنفيذها واختبارها.
- إعدادات المستودع لا تثبت خطة الخدمة الفعلية أو النسخة المثبتة. راجع deployment identity والبيئة الحقيقية عند التشخيص.

## 3. قواعد كل وظيفة جديدة

1. **حدود المجال:** ضع السلوك داخل مجاله الحالي. افصل منطق العمل عن HTTP وعن JSX. المسار يتحقق من الطلب والصلاحيات ويستدعي خدمة ويحوّل النتيجة إلى رد، ولا يجمع سير عمل كاملًا في ملف متضخم.
2. **الوصول إلى البيانات:** وجّه العمل الجديد تدريجيًا إلى وحدات وصول للبيانات خاصة بالمجال، بدل زيادة SQL الموزع. أبق تفاصيل SQLite خلف هذه الحدود قدر الإمكان. لا تنشئ abstraction عامة بلا حاجة، ولا تعِد كتابة الاستعلامات القديمة كلها دفعة واحدة.
3. **التخزين:** وجّه العمل الجديد/المعدّل نحو واجهة واضحة للرفع والقراءة والحذف يمكن تنفيذها محليًا ثم بمزوّد خارجي. افصل الملفات الدائمة عن الكاش القابل لإعادة التوليد، والملفات العامة عن الوثائق الخاصة. لا تجعل واجهة المستخدم تعتمد على مسار ملف مطلق على الخادم.
4. **الاعتمادات:** استخدم الاعتمادات الصريحة والعقود الموجودة بدل إنشاء اتصالات قاعدة أو عملاء تخزين أو حالات عامة جديدة داخل كل ميزة. العقود المشتركة تُحفظ في مكان مناسب مثل `shared`، ولا تُنسخ عبر التطبيق والموقع والخادم.
5. **حجم الملفات:** فكّك الملفات الكبيرة بحسب المسؤولية عند العمل عليها. لا توجد حاجة لتقسيم شكلي حسب عدد الأسطر؛ المطلوب تقليل الترابط وتسهيل الاختبار، دون تغيير سلوك غير ذي صلة.
6. **العمليات الثقيلة:** لا تُضف معالجة غير محدودة للصور/OCR أو قوائم بيانات كاملة لمجرد توفر CPU لاحقًا. ضع حدودًا للتوازي والانتظار، واستخدم pagination وvirtualization حيث يلزمان، وحافظ على التصنيف الصحيح للفشل وإعادة المحاولة.
7. **الصلاحيات والنتائج:** أي نقل داخلي يحافظ على المصادقة وCSRF وRBAC والأسعار والمعاملات وحدود إتاحة المحتوى وخصوصية الملفات. لا تُخزّن أسعارًا أو بيانات شخصية في كاش عام لتسريعها.
8. **الاختبار المتواصل:** اختبر الوظيفة والارتدادات ونمو البيانات والأداء مع كل مجموعة إضافات. لا نؤجل اكتشاف اختناقات الأداء إلى اكتمال المشروع، ولا نقدّم نسب تحسن أو وعود سعة بلا قياس.

## 4. التوسّع المستقبلي: متطلبات لا وعود جاهزة

| الخطوة المحتملة | ما يجب تحضيره والتحقق منه |
|---|---|
| CPU/RAM أعلى وخطة مدفوعة | قياس المورد المختنق، والتحقق من الإعدادات والتخزين؛ لا وعد بتسارع خطي |
| S3/CDN للصور | واجهة تخزين، مفاتيح ملفات وروابط مناسبة، ترحيل آمن، فصل العام والخاص وسياسات الوصول |
| PostgreSQL مستقلة | فصل الوصول للبيانات، مراجعة SQL والمعاملات والتحويل إلى I/O غير متزامن، ترحيل وتحقق واسترجاع |
| worker للصور/OCR | طابور وعقود مهام وحدود عمل، retries محدودة وidempotency ومعالجة الفشل |
| عدة نسخ API | حالة مشتركة مناسبة، وعدم الاعتماد على القرص المحلي أو قفل داخل عملية واحدة، ومنع تكرار المهام الدورية |
| فصل CRM أو مجال آخر | دليل على الحاجة وحدود وعقود بيانات وصلاحيات واضحة، لا فصل مبكر لمجرد زيادة عدد الخدمات |

تُنفّذ هذه الخطوات حسب الحاجة المقاسة وموافقة المالك، لا كتحويل شامل أثناء إضافة ميزة عادية. لا نشارك ملف SQLite محليًا بين خوادم مستقلة كاختصار للتوسّع.

## 5. قيود وقرارات المالك حاليًا

- نواصل إضافة الوظائف وتجربتها على الخدمات الحالية إلى حين قرار الترقية.
- Stripe تجريبي فقط، وخطة المالك إزالته قبل الإصدار؛ لا يُفتح مشروع دفع حقيقي من تلقاء المطوّر.
- لا تغيير لإعدادات القرص أو شراء خدمات أو نقل قاعدة/ملفات أو حذف بيانات بلا موافقة منفصلة. هذه الوثيقة ليست إذنًا بالتنفيذ أو الإنفاق.
- حتى بيانات التجربة قد تمثل تعب إعداد CMS؛ لا تُعد تهيئة القاعدة أو تمسح المحتوى لإصلاح مشكلة. قبل أي ترحيل لاحق، تُؤخذ نسخة ويُختبر الاسترجاع وخطة الرجوع.

## 6. قائمة مراجعة التسليم

- هل الإضافة في المجال الصحيح وتستعمل العقود القائمة؟
- هل منطق العمل منفصل بما يكفي عن HTTP والعرض وتفاصيل التخزين؟
- هل زادت SQL أو ملفات محلية أو حالة عامة موزعة بلا ضرورة؟
- هل السلوك والصلاحيات والأسعار والملفات الخاصة محفوظة؟
- هل القوائم والعمل الثقيل محدودة الكلفة مع نمو البيانات؟
- ما الاختبارات والقياسات التي نُفّذت فعلًا، وما الذي بقي غير متحقق؟
- هل تغيّر عقد عام؟ وثّق التوافق والترحيل وخطة الرجوع إن لزم.
- هل التغيير بنية تحتية أو تكلفة أو تغيير بيانات؟ اطلب الموافقة قبل التنفيذ.

أي تغيير جوهري لهذا التوجه يُوثّق كقرار جديد مع السبب والبدائل والأثر وموافقة المالك. لا تُعدّل الاتفاق بصمت لتبرير اختيار جديد.
