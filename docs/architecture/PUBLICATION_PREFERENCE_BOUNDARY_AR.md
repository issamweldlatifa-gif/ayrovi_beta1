# فصل تفضيلات المنشورات ومتابعة الناشرين

## النطاق

نُقل منطق قراءة المتابعة وكتابة المتابعة والتفضيلات من `src/public/routes.ts` إلى `src/magazine/publicationPreferences.ts`. بقي HTTP مسؤولًا عن المصادقة وCSRF وأكواد الاستجابة والرسائل الفرنسية وعقد JSON وضبط التخزين المؤقت. لا تغيير للمخطط أو الفهارس أو الاستضافة أو التخزين أو الأسعار.

- ملكية الكتابة تأتي من الحساب المصادَق عليه، لا من جسم الطلب؛ قراءة المتابعة للضيف تبقى مسموحة.
- قراءة الحالة والتحقق والكتابة داخل معاملة واحدة. الأعمدة في INSERT صريحة.
- الحقول المحذوفة أو null في التفضيلات تحتفظ بالقيمة السابقة؛ المنشور غير المنشور أو المستقبلي أو المفقود لا يقبل التفضيلات.
- تكرار المتابعة لا ينشئ صفًا إضافيًا ولا يستبدل تاريخ إنشائها؛ إلغاء المتابعة المتكرر مسموح.
- رفض الطلب لا يعدّل صفوف التفضيلات/المتابعة؛ قد تحدّث المصادقة وقت آخر استخدام للجلسة كالمعتاد.

## القياس المحدود

`src/analytics/preferenceTiming.ts` يراقب عمليتي `publication_preference_write` و`publisher_follow_write` فقط، قبل مصادقة المسار ولكن **بعد** middleware العام (بما فيه parsing وتحديد المعدل). الوقت monotonic ويشمل انتظار إنهاء الاستجابة من نقطة المراقبة، ولا يقيس الشبكة أو الجهاز أو العمل السابق لها. الطلبات المرفوضة قبل المراقب غير مشمولة.

التجميع داخل العملية محدود باسمَي العمليتين: completed / aborted / http4xx / http5xx / totalMs / maxMs، ويُصفّر بإعادة التشغيل. `snapshot()` نسخة منفصلة للاستخدام الداخلي، وليست endpoint عامة. completed يعني انتهاء استجابة HTTP لا نجاح العمل؛ يجب قراءة status معه. لا histogram أو p95 أو تخزين تاريخي.

التسجيل اختياري عبر `ZAYROVI_PREFERENCE_TIMING_LOGS=true`، **لم يُفعّل ضمن هذه الدفعة**. الحقول الثابتة فقط: event / operation / outcome / status / durationMs. لا أسماء حسابات أو معرّفات أو URLs أو bodies أو tokens أو رسائل أخطاء. فشل سجل التشخيص لا يفشل العملية. لا حاجة لتفعيل debug عام أو تسجيل الطلبات الحساسة لتشغيله.

هذا تجهيز للتشخيص لا إثبات لتحسن السرعة أو لسبب البطء. لاحقًا تُربط العينات بتوقيت CPU/RAM والسجلات المتاحة، مع فصل زمن العميل عن الخادم وتصنيف النتيجة: خلل وظيفي، تكلفة كود، قيد موارد، أو سبب غير محسوم. لم تُجمع قياسات إنتاج ولا يُنسب البطء إلى Render Free 0.1 CPU وحده.

## الأدلة

- `tests/publication-preference-boundary.test.ts`: ستة اختبارات HTTP/مجال بعزل حسابين، تجاهل انتحال الملكية، التحديث الجزئي/null، رفض auth/CSRF والقيم والهدف، ثبات تكرار المتابعة وعزل قراءتها، rollback عند رمي خطأ بعد كتابة SQL فعلية، واحتساب استجابات غير مصادق عليها.
- `tests/preference-timing.test.ts`: ثلاثة اختبارات للاحتساب مرة واحدة، الإجهاض، نسخة snapshot، مخطط الخصوصية، رفض labels غير المعروفة، إيقاف السجلات وفشل sink.
- المجموعة المركزة الأوسع: 11 ملفًا / 83 اختبارًا ناجحًا؛ اختبارات API المحمولة publicationFeed/social: ملفان / 17 اختبارًا ناجحًا.
- `npm run typecheck` و`npm run build` نجحا؛ بقي تحذير حجم حزمة العميل، دون ادعاء إصلاحه هنا.
- رُفع حد TypeScript في helper الاختبار من unknown إلى object فقط؛ مدخل المجال يبقى unknown ويتحقق منه.
- جلسات اختبار الكتابة مستقلة لتجنب استنفاد محدد المعدل أثناء المجموعة؛ لم يتغير محدد المعدل الفعلي.

## ما بقي

كتابات likes/views/comments لم تُفصل بعد؛ تحتاج دفعة مستقلة لحماية المعاملات والتكرار والعقود قبل أي إعادة تنظيم. لا ضمان لسعة المستخدمين، ولا اختبار حمل/جهاز حقيقي في هذه الدفعة. مشكلة ابتلاع أخطاء DDL في runSchema، والقراءات القديمة غير المحدودة، ومراجعات الفهارس السابقة ما زالت مفتوحة.
