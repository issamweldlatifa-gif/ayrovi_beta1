# دفعة تنظيم مجال الكتالوج: قراءة المنتجات العامة

## ما تغير

- وحدة `src/catalogue/publicProducts.ts` تملك قراءة المنتجات للقائمتين العامة والرئيسية، بدل SQL مكرر داخل HTTP. تستقبل اعتماد قراءة `all` فقط؛ لا تنشئ اتصالًا أو تعيد حساب سعر.
- مسارا `/api/public/products` و`/api/public/home` يستعملان هذه الوحدة، مع بقاء mapper وأغلفة JSON وأسماء الحقول وحدود القائمة في مواضعها الحالية.
- الاستعلام يقرأ المنتجات بترتيب مفهرس وحد LIMIT، ويجمع روابط الوصولات باستعلام مرتبط لكل منتج مرجَع، بدل LEFT JOIN وGROUP BY وفرز على كل الصفوف المؤهلة.
- الفهرسان `idx_products_public_catalog(status,visibility,updated_at DESC,id ASC)` و`idx_products_public_home(status,updated_at DESC,id ASC)` يضافان بصورة idempotent بعد وجود الأعمدة، في تهيئة مجال الكتالوج. لا فهارس فريدة جديدة ولا تغيير قيم أو حذف أو نقل قاعدة.
- الترتيب عند تساوي `updated_at` أصبح صريحًا بـ`id ASC`، موافقًا للترتيب المرصود في الاستعلام القديم. لم يكن التعادل ضمانًا صريحًا في SQL السابق.
- أداة تدقيق الأداء أصبحت تطلب EXPLAIN للاستعلام الجديد الحقيقي بدل نسخة SQL قديمة hardcoded.

هذا فصل قراءة فعلي محدود النطاق، لا abstraction جاهزة لـPostgreSQL. SQL ما زال يستعمل SQLite وGROUP_CONCAT، ويتطلب تكييفًا عند الانتقال لاحقًا. لم يُفكك `database.ts` أو كل مسارات CRM في هذه الدفعة.

## الحفاظ على السلوك

اختبارات تقارن صفوف الاستعلام القديم بالجديد عبر حدود 1/12/50، وفلاتر وصولات موجودة ومفقودة ومدخل مشابه لمحاولة حقن، وتواريخ متساوية، ومنتجات DRAFT وCONTENT وCATALOG. عند تصفية وصول واحد، تبقى قائمة كل الوصولات المرتبطة بالمنتج، والسعر المخزّن كما هو. يوجد اختبار HTTP على السعر والرابط وأسماء الحقول، واختبار إعادة إنشاء الفهرسين على بنية موجودة مرتين دون تغيير المنتجات.

**تمييز قديم محفوظ وليس قرارًا جديدًا:** قائمة catalog تستبعد CONTENT، بينما قسم المنتجات في `/home` كان يعرض كل ACTIVE بما فيها CONTENT. لم نغيّر هذا الفرق ضمن refactor متكافئ. تناقضه مع تعليق «CONTENT لا يُدرج» يحتاج مراجعة مستقلة لقاعدة إتاحة محتوى الرئيسية، لا يُعد هنا تصريحًا بأن السلوك التجاري مرغوب.

الفهرسان لا يحلان جميع أنماط البحث: تصفية وصول نادر قد تفحص منتجات أكثر قبل جمع الحد المطلوب. يلزم قياس ذلك ببيانات ارتباطات ممثّلة قبل تقرير فهرس إضافي أو مسار بحث آخر. لكل فهرس كلفة كتابة ومساحة، لذلك لم تُضف بقية فهارس سجل المراجعة آليًا.

## القياس المحلي

ملف النتائج: [public-product-read-benchmark.json](../performance/public-product-read-benchmark.json).

SQLite في الذاكرة، منتجات اصطناعية بتواريخ متساوية، بلا روابط وصولات في اختبار الحجم الكبير؛ توجد اختبارات تكافؤ منفصلة للروابط. 20 تكرارًا لكل استعلام بعد الإحماء وبترتيب تشغيل متناوب، في نفس العملية وبنفس الفهارس الحالية. «القديم» هنا شكل الاستعلام القديم، لا نشر سابق كامل. الأرقام p95 لـSQL وبناء صفوف النتيجة، **ليست API أو هاتفًا أو إنتاجًا أو اختبار قرص**.

| المنتجات الاصطناعية | النطاق | الشكل القديم ms | الجديد ms |
|---:|---|---:|---:|
| 5000 | catalog، حد 50 | 13.196 | 1.606 |
| 5000 | home، حد 12 | 8.617 | 0.591 |
| 50000 | catalog، حد 50 | 74.910 | 1.386 |
| 50000 | home، حد 12 | 105.642 | 0.672 |

EXPLAIN الجديد يستخدم فهرس النطاق المناسب، ولا يظهر USE TEMP B-TREE في المسارين المختبرين. النتيجة لا تعني أن كل الصفحات أو كل الاستعلامات أصبحت سريعة.

## التحقق وإعادة التشغيل

- 9 ملفات اختبارات، 72 اختبارًا ناجحًا: قراءة المنتجات، البنية ومراجعة العلاقات وبقاء إعدادات مختارة والترحيل والكتالوج والسعر والسلة وتفاصيل المنتج وأداة التدقيق.
- TypeScript للموقع والخادم وبناء الموقع والخادم: ناجحة.
- إعادة جرد البنية: 154 جدولًا، 441 فهرسًا، 181 علاقة، صفر مخالفات FK وintegrity_check=ok في القاعدة التجريبية. سجل 75 مرشحًا للفهرسة لم يتغير.
- لم تُشغّل مجموعة الخادم الكاملة أو اختبارات هاتف أو إنتاج في هذه الدفعة، ولم تتغير الاستضافة أو القرص أو Stripe.
