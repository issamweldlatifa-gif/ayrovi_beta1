# الواجهات المستقلّة — عقد بناء ومعاينة، لا تغيير على الاستضافة

الموقع الجديد تعريف بالخدمة وليس نسخة متصفح من التطبيق. الواجهة الفرنسية في `/` والعربية التونسية في `/ar/` (RTL)، مع ملفات CSS وJS وصور وخطوط محلية. لا اتصال بالـAPI لعرض الصفحة الرئيسية، ولا أدوات قياس أو كوكيز جديدة فيها. شاشة Z Lens تعرض ستّ لقطات فعلية من Expo Web في وضع العرض؛ التبديل لا يشغّل بحثًا حقيقيًا. الإيصال حساب تجريبي مؤرخ وليس عرض سعر. لا وعود بوسيلة دفع أو أجل توصيل أو انتشار التطبيق في متجر.

الشعار في المعاينة هو `Za.` الإصدار 9 الموجود في الفرع (`316a783c`)، مع الأسود والبورغندي والخطوط البصرية المستوحاة من المرجع. وثيقة Zebra Z الموجودة في المستودع توثّق الإصدار 8 السابق، وليس الشعار الذي يستعمله التطبيق حاليًا. لم نعد نشر ملفات الإصدار المتقاعد أو نغيّر هوية التطبيق والإدارة في هذه الدفعة؛ يلزم حسم الشعار إن كان المطلوب إعادة v8 للموقع تحديدًا.

## البناء والتشغيل

| الواجهة | بناء | ناتج/تشغيل |
|---|---|---|
| الموقع | `npm run build:landing` | `dist/landing/`، و`npm run serve:landing` لخدمة الصفحات ومسارات المشاركة عند تفعيلها |
| الإدارة | `npm run build:admin` | `dist/admin/`، و`npm run serve:admin`. JS/CSS في `/admin-build/assets/`، وطلبات الإدارة تبقى نسبية كما هي |
| التطبيق | أوامر Expo المعتادة داخل `apps/mobile` | لا استيراد من `web/` أو `dist/landing/`؛ سير عمل APK الحالي لم يتغيّر |
| الخادم والواجهة القديمة | `npm run build && npm start` كما كان | `dist/server.js` و`public/`؛ لم يتغيّر `render.yaml` أو SQLite أو تخزين الملفات |

يُضبط `ZAYROVI_WEB_ORIGIN` على أصل HTTPS الفعلي عند بناء الموقع (الافتراضي `https://zayrovi.com` ليس إثباتًا أن النطاق جاهز). هذا الأصل يحدد canonical وOpen Graph وsitemap، وليس Host القادم من الطلب. لا ترفع نواتج `dist/` إلى Git. الإدارة تحتاج نفس الـAPI ومسارات مواردها الحالية (الخطوط `/fonts/` والشعار/الوسائط `/media/` وغيرها) على نفس الأصل؛ لا حاجة إلى CORS جديد أو نقل الجلسات إلى local storage.

## عقد الموجّه عند التجهيز للإطلاق

لا تستخدم وسيط المعاينة في الإنتاج. تُطبّق القواعد التالية عند نقطة الدخول الموثوقة، من دون redirect للرجوع أو للـAPI، مع تمرير الطريقة وquery string والجسم و`Set-Cookie` وسياسات التخزين كما هي:

1. `/admin` ومقاطعها و`/admin-build/assets/*` إلى خدمة الإدارة. لا يُوسّع prefix ليشمل `/api/admin` أو أسماء مثل `/administrator`. أبق `frame-ancestors 'none'` و`X-Frame-Options: DENY` للإدارة في الإنتاج.
2. الجذر `/?…` الذي يحوي أي مفتاح من `customerAuth`, `cardPayment`, `orderId`, `transaction`, `session_id` إلى الواجهة القديمة؛ امنع تخزينه في الـCDN أو فهرسته. افحص المفاتيح بعد فك ترميز query string. توجيه الصفحة العادية إلى الموقع الجديد **لا** يعني نقل callbacks.
3. `/` و`/ar/` و`/site-assets/*` و`robots.txt` و`sitemap.xml` إلى الموقع. عند اعتماد روابط المشاركة، `/p/:id` و`/r/:id` و`/s/:id` (وأشكال `/ar/`) إليه أيضًا. اختياريًا، مرّر GET/HEAD القديم `/reels-viewer?id=...` إلى الموقع ليحيله إلى `/r/:id` بعد تفعيل صفحات المشاركة. لا توجّه إليه الروابط الإدارية أو الطلبات ذات التأثير على البيانات.
4. الباقي إلى الخادم الحالي: كامل `/api/*` بما فيه JSON 404، `/auth/native-done.html`، `/reset-password` (بما فيها fragment في المتصفح و`no-store` / `no-referrer`)، `/publications?post=…`، السياسات القديمة `/privacy.html` و`/terms.html` و`/data-deletion.html`، `/.well-known/*`، `/uploads/*` و`/media/*` والأصول القديمة. لا تخدم مجلّد uploads كدليل عام؛ بوابة الخادم الحالية تبقى إلزامية للوثائق الخاصة. مرّر عنوان العميل عبر السلسلة الموثوقة نفسها حتى تبقى حدود المعدّل والعناوين سليمة.

ترتيب القواعد قابل للاختبار في `web/runtime/routes.mjs`. لا تطفئ الويب القديم قبل قبول الاختبارات على أصل الإنتاج؛ الرجوع عن التحويل يكون بإرجاع توجيه `/` و`/admin` إلى الخدمة الحالية، من دون تغيير تطبيق الجوال أو قاعدة البيانات. إذا شُغّلت الروابط الجديدة فعليًا قبل الرجوع، أبق مسارات `/p`, `/r`, `/s` عاملة لحماية الروابط التي خرجت فعلاً.

## مشاركة وموافقات

- نقطة قراءة العرض `/api/public/share/:kind/:id` ترجع عنوانًا ووصفًا وصورة للمحتوى المتاح للعموم فقط، بلا سعر أو تفاصيل حساب. العناصر المحذوفة/غير المنشورة/المنتهية ترجع `404`؛ تعذّر الوصول إلى API يختلف ويظهر `503`. معاينة Web تعرض الملخّص وصورة إن وجدت؛ لا تحاول تشغيل الفيديو أو إرسال طلب تلقائي لفتح التطبيق.
- تفعيل الإنتاج يتطلب `ZAYROVI_SHARE_PAGES=1` و`ZAYROVI_API_ORIGIN` (أصل HTTPS) في خدمة الموقع. Media المعروفة على الأصل نفسه تبقى وراء بوابة `/media` و`/uploads`؛ إن لزم CDN خارجي، يُسمح بأصل واحد معتمد عن طريق `ZAYROVI_SHARE_MEDIA_ORIGIN`. لا يحمّل الخادم عناوين الوسائط المدخلة من CMS.
- `EXPO_PUBLIC_SHARE_WEB_ORIGIN` إعداد بناء منفصل للتطبيق. دونه تبقى مشاركة المنتج وReels كما كانت، ولا يظهر زر مشاركة Story الجديد. اضبطه فقط بعد اختبار صفحات الويب على أصلها المنشور: إرسال روابط قصيرة من التطبيق قبل تفعيل الموقع يخلق روابط ميتة.
- أزرار الويب تستعمل `zayrovi://` بنقرة صريحة. المسارات والمنطق مختبرة برمجيًا؛ **الفتح الفعلي على Android/iOS غير مؤكّد**. ملف Android الحالي يبقى تابعًا للخادم ويتطلب بصمات التوقيع الحقيقية. تهيئة iOS اختيارية ومطفأة افتراضيًا، راجع خطوات التفعيل أدناه. قبل الإعلان عن فتح HTTPS المباشر: اختبر النطاق والبصمة مع نسخة Android الموقّعة، وجهّز Associated Domains وAASA بمعرّف Apple الحقيقي ثم اختبر iOS. اختبر التثبيت وعدم التثبيت، الفتح البارد والدافئ، وعنصر Story منتهي.
- المسودات `/confidentialite`, `/conditions`, `/retours`, `/suppression-des-donnees`, `/contact` وترجماتها محلية فقط؛ لا تدخل نسخة الإنتاج. يتطلب البناء والتشغيل التجريبي تعيين `ZAYROVI_LEGAL_DRAFTS=1` في المرحلتين. إلى حين موافقة الفريق القانوني وتأكيد قنوات الدعم، تُستعمل الوثائق الحالية دون تغيير.
- لم يتغيّر دفع Stripe أو النشر. مطابقة عملة Stripe مع قيمة الدينار، قنوات الدعم، وسائل الدفع، آجال الشحن وحقوق استخدام وسائط التسويق: **غير مؤكّدة للإطلاق**. لا إعدادات متجر أو قياس إعلاني في هذه الدفعة.

## وصفة اختبار محلية

1. شغّل خادم API المحلي مع قاعدة اختبار أو نسخة احتياطية **منفصلة** على المنفذ `3000`. لا توجّه المعاينة إلى بيانات الإنتاج.
2. `npm run build` لتجهيز الويب القديم والخادم، ثم `ZAYROVI_LEGAL_DRAFTS=1 npm run build:landing` و`npm run build:admin`.
3. `ZAYROVI_LEGAL_DRAFTS=1 ZAYROVI_API_ORIGIN=http://127.0.0.1:3000 node web/runtime/start.mjs preview`. المنفذ الافتراضي `4173`، والأصل القديم الافتراضي `http://127.0.0.1:3000` (`ZAYROVI_PREVIEW_LEGACY_ORIGIN`). المتصفح يطلب نفس الأصل؛ الخادم في المعاينة وحده يتصل بـloopback.
4. `npx vitest run tests/web-surfaces.test.ts tests/public-share.test.ts`، و`node verify/web-surfaces.mjs` للتحقق بالمتصفح (Playwright Chromium). `ZAYROVI_TEST_WEB_FIXTURES=1` يختبر أمثلة محتوى ملف قاعدة المعاينة (كتالوج، Reel من مجموعة المالك، Story)، و`ZAYROVI_TEST_WEB_OUTPUT=/tmp/zayrovi-web` لكتابة اللقطات خارج المستودع. تستعمل اختبارات الجوال `apps/mobile/tests/links.test.ts` و`tests/ui/reelsViewer.ui.test.tsx` داخل مشروع Expo.


## تفعيل ربط HTTPS بدون خلطه مع إطلاق التطبيق

1. بعد إعداد نقطة الدخول، مرّر `/.well-known/assetlinks.json` و`/.well-known/apple-app-site-association` إلى الخادم الحالي **دون redirect**. بالنسبة إلى iOS، على نقطة الدخول تمرير `Host` المطابق للنطاق الذي اتصل به Apple. إذا لم يستطع مزوّد الاستضافة حفظ `Host`، يلزم نشر نفس بيان AASA عبر نقطة الدخول بدل جعل الخادم يثق بترويسة `X-Forwarded-Host` عشوائية.
2. Android: اضبط `ANDROID_APP_LINK_SHA256` ببصمات توقيع النسخ الموزّعة فعليًا. نسخة Google Play تستعمل بصمة **App signing**، موش Upload key فقط. لا تستعمل بصمة debug لحزمة الإنتاج. عند بناء التطبيق بخيار `share_web_origin` في إجراء Android اليدوي أو `EXPO_PUBLIC_SHARE_WEB_ORIGIN` محليًا، يبقى إعداد النطاقات القديمة كما هو، ويضاف النطاق الجديد — إن لزم — لمسارات المشاركة الستة فقط.
3. iOS: اضبط `IOS_APP_LINK_APP_ID` في الخادم بقيمة `application-identifier` الفعلية من النسخة الموقّعة (App ID prefix ثم `app.zayrovi.mobile`) و`IOS_APP_LINK_HOSTS` بقائمة النطاقات المعتمدة مفصولة بفاصلة. بلا ضبط صحيح يرجع AASA `404` JSON. عند بناء iOS عيّن `ZAYROVI_IOS_UNIVERSAL_LINKS=1` و`EXPO_PUBLIC_SHARE_WEB_ORIGIN=https://…`؛ إعداد Expo يضيف entitlement `applinks` للنطاق المحدد فقط. الملف لا يطالب بمسارات الدخول والدفع أو Admin. لا حاجة لإرسال مفاتيح أو كلمات سر.
4. فحص قراءة فقط بعد تجهيز بيئة HTTPS: `CUTOVER_PRODUCT_ID=… CUTOVER_REEL_ID=… CUTOVER_STORY_ID=… npm run verify:public-cutover -- https://<النطاق>`؛ أضف `IOS_APP_LINK_APP_ID` و`ANDROID_APP_LINK_SHA256` (و`CUTOVER_ANDROID_PACKAGE` إذا كانت التجربة لحزمة مختلفة) لاختبار بيانات الربط أيضًا. من دون القيم يعتبرها الفحص **لم تُختبر**، لا ناجحة. لا يستعمل الفحص حسابات أو عمليات دفع، ولا يصلح مكان اختبار أجهزة فعلية.
5. على Android الموقّع، افحص `adb shell pm get-app-links app.zayrovi.mobile` ثم افتح الروابط من تطبيق رسائل. على iOS الموقّع اضغط الروابط من Messages أو Notes، وليس فقط من شريط Safari؛ قد تبقى روابط نفس النطاق داخل Safari. اختبر الرابط ألّا يعرض عنصرًا آخر، الفتح البارد والدافئ، التطبيق غير المثبّت، وروابط FR/AR. أعد الاختبار عند إعادة التوقيع أو تبديل النطاق. لا تفعل رابط المشاركة في إصدار الجوال قبل أن ينتهي فحص الموقع وملفات الربط.

## استبدال الصفحة الرئيسية على الاستضافة الحالية

بناء الخدمة الحالي (`npm run build`) يجهّز أيضًا أصول الصفحة العامة. على Render في وضع الإنتاج يُخدم الموقع التعريفي على `/` و`/ar/`، ويتحوّل `/index.html` العادي إلى `/`. النسخة القديمة تبقى داخليًا لمسارات الرجوع بمعاملات الدخول أو الدفع وللمسارات الأخرى؛ لا تُحذف من البناء، ولا تتغيّر قاعدة البيانات. النسخة المنشورة لا تُضمّن المسودات القانونية ولا تُفعّل روابط التطبيق الموقّعة أو عرض المشاركة القصيرة تلقائيًا. يمكن الرجوع إلى الصفحة الرئيسية السابقة بتعيين `ZAYROVI_PUBLIC_SITE=legacy` وإعادة تشغيل الخدمة. هذا التحويل متوافق مع الاستضافة الحالية ولا يتطلّب نقل DNS أو فتح خدمة جديدة.
