# فصل كتابات التفاعل الاجتماعي

## النطاق والقرارات

نُقل منطق `/api/public/social/interact` إلى `src/magazine/socialInteractions.ts`؛ بقي HTTP مسؤولًا عن الجلسة والمصادقة وCSRF ومحدد المعدل وتحويل نتائج المجال إلى أكواد الاستجابة والرسائل الفرنسية وJSON السابق. وحدة المجال لا تعتمد على Express، وتتلقى الحساب من سياق موثوق، لا من جسم الطلب. لا تغيير للمخطط أو الفهارس أو البنية التحتية أو إعدادات التخزين.

تشمل الدفعة like/reaction/comment/view/share. أُعيد استخدام فحص ظهور الهدف في قراءة التعليقات أيضًا، دون نقل SQL قائمة التعليقات أو counts المجمعة في هذه الدفعة.

## العقود المحفوظة

- `like` القديم **toggle**: إعادة الطلب قد تلغي الإعجاب؛ لا ندّعي أنه idempotent.
- `reaction` الصريح للمنشورات فقط: like/dislike/null، مع استبعاد متبادل للإعجاب وعدم الإعجاب لكل حساب.
- التعليقات: التنظيف وحد 500 حرف وحد القراءة الحالي 100 محفوظان. معرف clientRequestId مرتبط بالحساب والهدف؛ إعادة نفس النص/الأصل ترجع نفس التعليق، وتغييرهما مع المعرف نفسه يرجع 409. دون المعرف، الإرسال المتكرر ينشئ تعليقات جديدة كما سابقًا. فحص الأصل يسبق فحص إعادة الطلب كما سابقًا.
- view/share: واحد لكل نوع وهدف وحساب أو hash جلسة زائر. هذا ليس عداد أشخاص حقيقيين: جلسة أخرى أو التحول من ضيف لحساب قد يحتسب مجددًا.
- القصص المنتهية/المستقبلية/غير المنشورة والمنشورات/Reels غير الظاهرة لا تقبل الكتابة. ترتيب البحث story ثم publication ثم reel محفوظ، وكذلك target_kind التاريخي.
- تحديث عدادات Reels يبقى مشتقًا من صفوف التفاعل؛ لا عدادات مصطنعة أو تغيير لعقود العميل.

## المعاملة

أصبحت رؤية الهدف والتحقق وقراءة الحالة/التكرار والكتابة وتحديث عدادات Reel وقراءة العدادات النهائية ضمن معاملة واحدة متزامنة؛ لا شبكة أو await داخلها. كان بعض فحص التعليقات والتكرار خارج معاملة الكتابة. الأعمدة صريحة عند كتابة dislikes وروابط الردود أيضًا.

الضمان المثبت هنا هو التراجع عن العملية كاملة عند الاستثناء، وحفظ السلوك في التنفيذ الحالي. لم نضف قيود uniqueness جديدة أو نجرب كتابات متنافسة عبر عمليات/خوادم متعددة؛ لا ندّعي جاهزية multi-instance أو exactly-once عامة. زيادة نطاق المعاملة ليست ادعاء تسريع، وتكلفتها تحت الحمل تحتاج قياسًا.

## التحقق المنفذ

- `tests/social-interaction-boundary.test.ts`: 6 اختبارات تشمل فصل الحسابات وتجاهل انتحالها، الفرق بين toggle والتفاعل الصريح، تكرار المشاهدات والمشاركات للحساب/الضيف، مزامنة عدادات Reels، تكرار التعليق وتعارض النص والأصل، رفض الأهداف المخفية/المستقبلية والقصص المنتهية، والقيم والمصادقة/CSRF دون تعديل صفوف العمل.
- حقن أخطاء **بعد SQL فعلي** في تحديث Reel وإدراج reply/dislike يثبت rollback للصفوف والروابط والعدادات.
- المجموعة الأوسع: 12 ملفًا / 87 اختبارًا ناجحًا (social boundary، social، publication upgrade/content/feed، reel follow، hardening، shoppable، preference boundary/timing، public social reads، database reopen). بعد توسيع fixtures القصص في اختبار الرفض، أُعيد ملف الحدود ونجحت اختباراته الستة.
- اختبارات API للموبايل social/publicationFeed: ملفان / 17 اختبارًا ناجحًا.
- `npm run typecheck` و`npm run build` نجحا. تحذير حجم حزمة العميل باقٍ.

## القياس وما بقي

لم نوسّع timing التفضيلات تلقائيًا ولم نفعّل تسجيله. لا قياس CPU/RAM إنتاجي أو حمل متزامن أو سلاسة جهاز في هذه الدفعة، ولا إثبات لتحسن زمن الاستجابة. الإجراء التالي للتشخيص هو جمع قياسات آمنة متزامنة للعميل والخادم والموارد المتاحة قبل تصنيف سبب البطء.

قراءات التعليقات/counts المجمعة ما زالت في HTTP؛ القراءات القديمة غير المقسمة، مراجعات الفهارس، وابتلاع أخطاء DDL في runSchema ما زالت مفتوحة. تُعالج كل نقطة في دفعة محدودة باختبارات حفظ بيانات، لا إعادة كتابة شاملة أو ترحيل خدمات.

### تحديث لاحق

أُنجز فصل قراءتَي التعليقات/counts المجمعة لاحقًا؛ انظر [سجل قراءة التفاعل](SOCIAL_ENGAGEMENT_READ_BOUNDARY_AR.md). بقية حدود القياس ومشكلات DDL المذكورة أعلاه ما زالت قائمة.
