# حماية دفعات المخطط وتجربة استرجاع SQLite

## نطاق العمل

هذه دفعة أمان محدودة قبل مواصلة الوظائف، لا ترحيل قاعدة ولا شراء خدمات. لم تُفتح قاعدة التشغيل ولم تُسترجع فوقها نسخة ولم تتغير جدولة النسخ أو إعدادات التخزين الخارجي. كل تجربة البيانات استعملت قواعد اصطناعية في مجلدات مؤقتة خاصة، ثم حُذفت ملفات التجربة فقط.

## 1. runSchema: أخطاء ظاهرة ودفعة ذرية

كان `runSchema` يقسم النص عند كل `;` ثم يتجاهل أي استثناء. هذا لا يفرّق بين تكرار مقصود وخطأ syntax أو فهرس فريد مرفوض أو جدول مفقود. أثناء تعديل السلوك ظهر فعلًا أن تعليقًا في مخطط AyWebs يحتوي `;` كان يولد مقطعًا خاطئًا (`editing...`)؛ لم يكن تقسيم SQL القديم آمنًا حتى للتعليقات.

الآن:

- `src/db/schemaStatements.ts` يميّز النصوص والمعرفات المقتبسة والتعليقات السطرية/الكتلية عن فواصل التعليمات. يحتفظ بالـsemicolon داخل النص ويتعامل مع escaped quotes، ويرفض النص/التعليق غير المغلق قبل التنفيذ.
- كل استدعاء `runSchema` ينفذ داخل معاملة SQLite، أو savepoint عندما يكون داخل معاملة. فشل تعليمة يرجع للمستدعي ويلغي **هذه الدفعة**؛ لا يواصل تنفيذ تعليمات تالية كأنها نجحت.
- التكرار يكون عبر IF NOT EXISTS أو فحص العمود قبل ALTER. لم نعد نتجاهل duplicate column كاستثناء عام؛ على المستدعي التأكد منه صراحة. العدد المعاد هو عدد التعليمات المنفذة، بما فيها IF NOT EXISTS الذي لم ينشئ شيئًا جديدًا.
- راجعنا الاستدعاءات الحالية واختبرنا وحدات التأسيس والترقيات. لم تتغير تعريفات الجداول أو الفهارس.

### حدود مهمة

هذا ليس parser SQL كاملًا: helper لدفعات DDL البسيطة الموثوقة، لا أجسام CREATE TRIGGER ذات BEGIN/END، ولا تعليمات تحكم معاملات أو PRAGMA غير قابلة للمعاملة. لا يفسر صحة SQL؛ SQLite هو من يرفضه. لا تمرر إليه مدخل مستخدم. لإنشاء trigger يلزم مسار SQLite exec مدروس واختبار مستقل، لا توسيع parser تخميني.

الذرية تخص الاستدعاء الواحد، **لا جميع constructor/bootstrap**. مسارات init الخارجية لبعض الوحدات ما زالت تمسك الخطأ وتسجله وتسمح بإقلاع المتجر وفق السياسة السابقة؛ لم نحوّل ذلك إلى توقف شامل أو ندّع أن readiness صار يضمن كل وحدات ERP. أعطال جديدة في بيانات تاريخية قد تظهر الآن بدل أن تُخفى؛ تُراجع قبل النشر، ولا تعالج بحذف صفوف أو إعادة catch صامتة. المخططات الأخرى وensureColumn ليست كلها موحّدة بهذه الآلية.

## 2. النسخ: فحص العلاقات أيضًا

`scripts/backup-sqlite.mjs` يواصل استخدام SQLite backup API، وليس نسخ ملف رئيسي مفتوح وحده. حذف كاش Lens الحساس/القابل لإعادة الحساب من **النسخة** محفوظ.

أصبح القبول يتطلب نتيجة quick_check واحدة تساوي ok وغياب مخالفات foreign_key_check. النسخة الجديدة المرفوضة تُحذف ولا يبدأ رفعها أو تنظيف النسخ القديمة؛ لا تُحذف نسخة قديمة بسبب هذا الرفض. لم تتغير إعدادات S3 أو retention أو الجدولة. هذا تشدد مقصود: قد يكشف مخالفات علاقات تاريخية رغم أن فحص البنية السابق نجح، ولا يصلحها تلقائيًا.

## 3. أمر تحقق واسترجاع معزول

```bash
npm run backup:verify -- /absolute/path/to/backup.sqlite
```

الأمر يفتح المدخل readonly مع fileMustExist، يستنسخه عبر SQLite backup API إلى مجلد نظام مؤقت بصلاحية 0700، يفتح المستنسخ readonly، يجري integrity_check كاملًا وforeign_key_check ويقرأ أعداد صفوف الجداول، ثم يغلقه ويحذف مجلد التجربة في finally. لا يُنشئ ملف المدخل المفقود ولا يقبل مسار استرجاع فوق قاعدة أخرى. الخرج إحصائي فقط دون قيم الصفوف أو SQL/أسرار.

نجاحه **ليس إقلاع التطبيق**: الخرج يصرح applicationBootTested=false وuploadsVerified=false. لا يشغّل migrations أو ينقل نسخة إلى التشغيل. تشغيله قد يتطلب وقتًا ومساحة بحجم القاعدة؛ هو أمر صيانة يدوي، لا endpoint ولا فحص كل طلب. مصدره يفترض أنه ملف backup محلي موثوق، وليس ملفًا يرفعه مستخدم عام.

## 4. أدلة الاختبار

- `tests/run-schema-safety.test.ts`: 4 اختبارات لخطأ DDL، رفض uniqueness مع إبقاء الصفوف، rollback للدفعة وsavepoint داخل معاملة، التكرار والتعليقات والـsemicolon المقتبس ورفض النص غير المكتمل.
- `tests/sqlite-backup-restore.test.ts`: اختباران يشغلان سكريبت النسخ الحقيقي والتحقق كعمليتين منفصلتين، مع تعطيل إعدادات BACKUP الخارجية الموروثة **في بيئة الاختبار فقط**.
- قاعدة مصدر ملفية مفتوحة بـWAL يحتوي بيانات ملتزمة؛ مقارنة كل صفوف جداول المستخدم في النسخة مع المصدر باستثناء كاش Lens المقصود تنظيفه. الكاش غير فارغ في fixture ويثبت الاختبار أنه لم يُحذف من المصدر.
- النسخة المسترجعة تُفتح عبر QatafoDatabase مرتين؛ تُقارن إعدادات CMS وعلامات migrations ومنتج بسعر 79.5 وصف متابعة حساب، مع integrity وFK checks. هذا اختبار اصطناعي لإقلاع طبقة البيانات، لا إقلاع HTTP كامل على إنتاج.
- رفض ملف مفقود/تالف أو علاقات FK مكسورة؛ اختبار أن رفض نسخة جديدة لا يحذف النسخة القديمة.
- المجموعة: **17 ملفًا / 220 اختبارًا ناجحًا** تشمل schema inspection/review/reopen، arrival migration، catalogue/inventory/purchasing/CRM/ERP/AyWebs foundations، analytics/funnel وbrand/customer-notification/Facebook migrations. بعد إضافة المنتج والمتابعة لfixture النسخ أُعيد ملفه ونجح اختباراه.
- `npm run audit:database`: 154 جدولًا، 441 فهرسًا، 181 FK؛ integrity ok وصفر مخالفات في القاعدة الاصطناعية. لا تغيير لمرجع مراجعات الفهارس.
- `npm run typecheck` و`npm run build` نجحا؛ تحذير حجم حزمة العميل باقٍ.

## 5. ما لم يُثبت وما يلزم عند استرجاع حقيقي

لم نختبر نسخة الإنتاج أو كل قاعدة تاريخية، ولم نفعّل/نختبر رفعًا خارجيًا أو تنزيلًا منه أو تشفيرًا أو جدول نسخ فعليًا. SQLite وحده لا يحفظ uploads والملفات الخاصة. وجود نسخة محلية على نفس القرص لا يحمي من فقد القرص. لا ضمان RPO/RTO أو تحمل انقطاع أثناء النسخ/الاسترجاع.

قبل أي استرجاع حقيقي: تحقق من مصدر النسخة وتاريخها وصلاحياتها، اختبرها مع إصدار الكود المقصود في بيئة منفصلة ومع ملفاتها المرافقة، احفظ الحالة الحالية وخطة الرجوع، أوقف الكتّاب بالطريقة التشغيلية المناسبة، ثم نفّذ انتقالًا مخططًا واختبارات العمل. لا تنسخ main file وحده فوق قاعدة مفتوحة ولا تتجاهل ملفات WAL/SHM عشوائيًا. هذا التوثيق **ليس إذنًا بالكتابة فوق التشغيل**.

يمكن مواصلة وظائف التطبيق مع هذه الضمانات. تبقى مراجعات الفهارس والقراءات القديمة وحدود readiness والقياسات الإنتاجية مهامًا تدريجية حسب الحاجة، وليست سببًا لترحيل SQLite الآن دون دليل.
