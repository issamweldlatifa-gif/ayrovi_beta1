## 2. خريطة المنصة كما تظهر في الكود

```text
React 19 + Vite + TypeScript
        │ طلبات same-origin
        ▼
Express 4 — API + جلسات + قواعد العمل
        ├── AYROVIX Lens / بحث / استخراج روابط
        ├── الحسابات / الطلبات / السلة / الدفع
        ├── Admin + RBAC + Audit + CMS
        ├── Assistant / AI Core / Voice
        ├── CRM / Arrival / Inventory / Purchasing
        └── Public content / social
        ▼
SQLite (better-sqlite3) + ملفات محلية على قرص دائم
        ▼
Anthropic / SerpApi / بوابة دفع / OAuth / SMS webhook / Mail provider
```

التطبيق Monolith منظّم على شكل وحدات TypeScript، لا مجموعة خدمات مستقلة. هذا يبسط الإطلاق الأولي ويجعل التطوير المحلي مباشرًا، لكنه يعني أن التطبيق وقاعدة SQLite والـ workers والـ scheduler والـ rate limits مرتبطة عمليًا بعملية/نسخة الخادم الواحدة.

## 3. نقاط القوة

### هندسة المنتج والتجارة

- تسعير مركزي في `src/services/pricing.ts` بدل الاعتماد على حسابات الواجهة؛ يتضمن الصرف والجمارك والنقل والخدمة وExpress، مع نسخة سعرية تُحفظ مع الطلب.
- توجد ضوابط تمنع تجاوز حد إجمالي الطلب، وتضع البضائع الثقيلة/المقيدة في حالة تنبيه أو مراجعة.
- OMS ومسارات الطلبات والمدفوعات والتسليم وسجل تغيير الحالة أكثر نضجًا من متجر واجهة فقط.
- فصل واضح بين حساب العميل وAdmin، مع صلاحيات RBAC وسجل تدقيق.
- توجد حسابات وعناوين ومفضلة وسلة محفوظة واسترجاع كلمة المرور وحذف ذاتي للحساب.
- إعدادات تونس حاضرة بوضوح: الدينار، الولايات، الهاتف، وسائل الدفع المحلية، وإمكانية ربط SMS محلي.

### الأمن والخصوصية

- كلمات المرور مخزنة باستخدام `scrypt`، والجلسات تعتمد رموزًا عشوائية تُخزن مجزأة.
- Cookie الجلسة `HttpOnly`، و`SameSite`، و`Secure` في وضع الإنتاج؛ وتُستخدم حماية CSRF للعمليات التي تغيّر البيانات.
- وجود CSP و`nosniff` و`Referrer-Policy` وسياسة منع تضمين Admin في الإطارات بالإنتاج.
- حماية خاصة للملفات الخاصة والفواتير وإثباتات الدفع في `src/documents/fileAccess.ts` و`src/erp-core/storage.ts`، مع منع تقديم المسارات الخاصة من `/uploads`.
- رفع Lens محدود إلى 6MB في Multer، وفحص MIME، وفك/تدوير/إعادة ترميز الصورة بـ`sharp` مع سقف للبكسلات، ما يقلل مخاطر الملفات المزيفة وImage bombs.
- التعامل مع إدخال روابط HTTP(S) يرفض عناوين محلية/خاصة، بيانات URL المضمنة، والتحويلات غير المحدودة؛ وهذه قاعدة جيدة تحتاج استكمالًا كما في النتائج الأمنية.
- مفاتيح الخدمات موضوعة كمتغيرات بيئة في `.env.example` وليست `VITE_*`، ولا توجد مفاتيح حيّة ظاهرة في لقطة الملفات التي فُحصت.

### Lens وAI

- يوجد محرك مركزي `recognizeImage` بدل أن يعيد كل endpoint تركيب سلسلة التعرف بنفسه.
- Vision والبحث البصري وإشارات الصورة تعمل بالتوازي؛ فشل مزود واحد لا يفترض أن يسقط الآخر.
- Lens تقبل صورة أو رابطًا أو QR/باركود/نصًا، وتفصل بين التعرف والبحث والتحويل السعري.
- نتائج السعر غير المؤكدة تحمل `PENDING_MANUAL` ورمز سعر HMAC؛ لا ينبغي أن يُعامل سعر من الصورة أو نتيجة Web كعرض نهائي قابل للشراء مباشرة.
- البحث البصري يفلتر روابط وعناوين وأسعار، ويزيل التكرار، ويضع نتائج بلا سعر في حالة معلّقة بدل تصنيع سعر.
- وجود كاش للتعرف منفصل عن كاش نتائج السوق، مع مدد صلاحية مختلفة، قرار صحيح لأن بيانات المنتج أبطأ تغيرًا من أسعار البائعين.
- سجل أداء Lens وقياسات p50/p95 موجودان في `src/ayrovix/services/lensPerformanceTrace.ts`، ولا يسجلان الصورة الخام حسب العقد الموثق.

### جودة التنفيذ

- النوع والبناء والاختبارات تمر حاليًا، ومجموعة الاختبارات كبيرة نسبيًا وتغطي Auth وCheckout والتسعير وLens وERP وتجارب واجهة.
- CI يشغّل typecheck/build/tests وتحققات المتصفح، لا يكتفي بفحص تجميلي.
- هناك وثائق تفصيلية وخطط مراحل وسجلات تنفيذ؛ قيمتها عالية إذا عُزلت الوثائق الحالية عن التقارير التاريخية المتعارضة.

## 4. نتائج أمنية وأولويات الإصلاح

### A. مرتفع — احتمال SSRF عبر DNS rebinding / فجوة فحص ثم اتصال

**المكان:** `src/services/safeUrl.ts`، الدالتان `resolveSafeHttpUrl` و`fetchSafeRemote`.

الدالة تحلّ اسم النطاق وتفحص كل العناوين أولًا، ثم الاتصال يتم بـ`fetch(safe.url)`. `fetch` يحلّ النطاق عند الاتصال بنفسه؛ أي إن العنوان الذي اتصل به العميل قد لا يكون العنوان الذي جرى فحصه قبل قليل. مع نطاق يسيطر عليه مهاجم ويمكنه تبديل DNS، تنشأ فجوة TOCTOU يمكن أن تتجاوز رفض العناوين الخاصة. فحص كل Redirect خطوة جيدة لكنه لا يغلق فجوة إعادة الحل نفسها.

**الإصلاح المطلوب قبل فتح جلب الروابط للعامة:**

1. اجعل الاتصال يستخدم عنوان IP الذي تم التحقق منه فعلًا (DNS pinning/custom lookup أو Dispatcher/Agent مناسب)، مع الإبقاء على TLS SNI واسم `Host` الصحيحين.
2. أعد التحقق لكل Redirect ولكل عنوان قبل الاتصال، لا قبل الاتصال فقط.
3. اسمح افتراضيًا بالمنافذ 80 و443 فقط، ما لم تكن هناك حاجة موثقة لغيرها.
4. أضف اختبارًا يحاكي DNS يعيد IP عامًا عند الفحص ثم IP داخليًا عند الاتصال، واختبارات IPv4-mapped IPv6 وRedirect إلى loopback/metadata.

### B. مرتفع — تجاوز/ضعف حدود الاستهلاك على Lens وOTP وSocial

**المكان:** `src/server.ts`، `rateLimit` و`rateBuckets` و`socialMutationRateLimit`.

الحدود الحالية محفوظة في `Map` بذاكرة العملية، لذلك تُصفّر عند إعادة التشغيل ولا تتشاركها عدة نسخ. كما أن تفاعلات Social تقسم الحد بحسب `x-session-id` الذي يرسله العميل بنفسه، ويمكن تدوير القيمة لتجاوز الحد المرتبط بكل جلسة. وطلب OTP مربوط بـIP **ورقم هاتف معًا**؛ هذا لا يضع حدًا كليًا جيدًا للـIP إذا بدّل المرسل الأرقام.

**الإصلاح:** Redis/مخزن موزّع أو rate limiting عند الـedge، مع عدّاد IP مستقل بالإضافة إلى عدّاد الحساب/الهاتف. لا تستخدم Header يختاره العميل كهوية موثوقة، وحدد عدد مفاتيح العدادات وحجمها. افحص إعداد `trust proxy` حسب عدد البروكسيات الفعلي؛ الخطأ فيه قد يسمح بتزوير عنوان العميل أو جمع مستخدمين تحت IP واحد.

### C. مرتفع تشغيليًا — كلمة مرور Admin التجريبية عند نسيان NODE_ENV

**المكان:** `src/admin/auth.ts` و`README.md`.

إذا لم يوجد `ADMIN_PASSWORD` وكان `NODE_ENV` **ليس** `production`، ينشئ bootstrap حسابًا تجريبيًا بكلمة مرور معروفة ومعلنة في README (`AyroviBeta2026!`). Blueprint الخاص بـRender يعيّن `NODE_ENV=production`، لكن أي استضافة أخرى أو إعداد ناقص قد يترك التطبيق على الوضع غير الإنتاجي ويُنشئ بيانات الدخول الافتراضية.

**الإصلاح:** اجعل تشغيل الويب في وضع production يفشل مغلقًا إذا لم تُضبط كلمة مرور Admin و`CUSTOMER_AUTH_SECRET` و`PUBLIC_BASE_URL`، واجعل الحساب التجريبي يتطلب علمًا صريحًا محليًا لا يمكن تفعيله بمجرد غياب متغير بيئة. أضف فحص إعدادات قبل النشر.

### D. متوسط — استعادة Admin تتكرر إذا تُرك العلم مفعّلًا

`ADMIN_BOOTSTRAP_RESET=yes` يعيد فرض البريد وكلمة المرور عند كل إقلاع طالما ظل موجودًا. يجب أن يكون إجراءً لمرة واحدة، مع تنبيه startup قوي/إيقاف الخدمة بعد استهلاكه، وخطوة Runbook لإزالة المتغير مباشرة.

### E. متوسط — تخزين وحجم تشغيلي

- قاعدة SQLite وملفات uploads على قرص Render واحد. مناسب لنسخة واحدة، لكنه لا يوفر توسعًا أفقيًا/توافرًا عاليًا بشكل سليم عند تشغيل عدة instances.
- النسخة المحلية اليومية على القرص نفسه لا تحمي من فقد القرص. إعداد S3/R2/B2 اختياري في `.env.example`؛ يجب تفعيله، التنبيه عند فشله، واختبار الاستعادة فعلًا.
- مهام Price Watch والـFX وMail تعمل ضمن عملية الخادم. عند تعدد النسخ قد تعمل المهمة نفسها أكثر من مرة؛ يلزم leader/lease/queue موزعة أو نقل المجدول إلى worker واحد.

### F. متوسط — تسرّب معلومات من Readiness وأخطاء الخدمة

`/api/ready` عام ويعيد رسالة الاستثناء من SQLite/المهاجرات مباشرة عند الفشل. الأفضل أن يبقى JSON عام برسالة ثابتة وRequest ID، وتذهب التفاصيل إلى السجل الداخلي. كذلك لا تعرض تفاصيل إعداد المزودين أو حدود حساباتهم إلا ضمن Admin.

### G. متوسط — مخاطر خصوصية Lens مع مزودين خارجيين

تعليقات الكود تؤكد عدم حفظ الصورة الخام في مسار Lens، وهذا إيجابي. لكن الصورة تُرسل فعليًا إلى مزودي Vision/Visual Search، كما أن طبقة التعرف تحفظ نتائج مستخرجة وإشارات الصورة في كاش محلي. لذلك عبارة «لا نخزن الصورة» لا تعني أن التحليل محلي أو أن الصورة لا تغادر الجهاز.

**المطلوب:** إفصاح واضح داخل Lens قبل أول رفع عن الإرسال إلى مزودي AI/البحث، وصف مدة حفظهم، سياسة حذف/Retention للكاش المستخرج، معالجة صور المستندات ولقطات السلة التي قد تحتوي بيانات شخصية، وعقود معالجة بيانات مناسبة.

### H. منخفض إلى متوسط — إدارة أسرار المستودع

لم يعثر الفحص على مفاتيح حية في ملفات النسخة الحالية؛ `.env.example` يحتوي placeholders وأسماء متغيرات فقط، و`.env` غير موجود. لكن المستودع ضحل بعمق commit واحد، لذا **لم يُفحص تاريخ Git كاملًا**. يلزم إجراء secret scanning على التاريخ الكامل وعلى CI، وتدوير أي مفتاح يظهر في تاريخ سابق حتى بعد حذف الملف.

## 5. تقييم AYROVIX Lens بالتفصيل

### التدفق الحالي

```text
صورة من كاميرا/ملف
  → تجهيز على الواجهة
  → POST /api/ayrovix/analyze-image (حد رفع 6MB، ذاكرة فقط)
  → sharp: تحقق/تدوير/تحجيم وإعادة ترميز
  → recognizeImage:
       ├─ Anthropic Vision: المنتج/العلامة/الوصف/سعر ظاهر بثقة
       ├─ SerpApi Google Lens: نتائج بصرية وبائعون
       └─ إشارات محلية للصورة (OCR/رموز بحسب المسار)
  → سياسة المرشحين + إزالة التكرار
  → محرك التسعير المحلي بالدينار
  → مرشحو منتج مع حالة تحقق/رمز سعر
  → مراجعة رابط التاجر قبل اعتماد السعر للطلب
```

الروابط تمر بمسار استخراج بيانات متجر/JSON-LD وبيانات وصفية ثم يمكن البحث عن بدائل. QR والباركود قابلان للفك محليًا على الجهاز؛ وليس كل نوع QR يعني رابط منتج موثوقًا.

### نقاط قوة Lens

- تصميم fallback جيد: إذا تعطل Vision يمكن مواصلة المسار بنتائج Google Lens، والعكس صحيح.
- الصور لا تُكتب إلى `data/uploads` كملفات عامة ضمن المسار الأساسي.
- التعامل مع السعر أكثر أمانًا من عرض السعر المستخرج باعتباره حقيقة؛ توجد حالة Pending ورابط تاجر مطلوب للتأكيد.
- السعر النهائي يحسبه الخادم من القواعد، ولا يثق بحقل TND يرسله المتصفح.
- فيه تدفق لتحديد منطقة من الصورة/ROI بدل رفع صورة قصّ جديدة في بعض الحالات.
- مدد الكاش تفصل «ما يظهر في الصورة» عن «ما يتغير في السوق».

### نواقص ومخاطر Lens

1. **دقة غير مقاسة على بيانات تونس:** كثرة اختبارات الوحدة لا تثبت دقة التعرف على صور مستخدمين حقيقيين أو جودة نتائج فرنسا/أوروبا بالنسبة لتونس. لا يظهر في هذا الفحص benchmark موحد معلّم من مئات الصور يقيس Top-1/Top-3 واستخراج السعر والعملة.
2. **الاعتماد على مزودين مدفوعين:** غياب مفاتيح Anthropic أو SerpApi يجعل بعض المسارات ناقصة؛ يلزم حدود تكلفة ومراقبة حصص وتدهور أنيق واضح للمستخدم.
3. **سعر الصورة ليس عرض متجر:** حتى لو كانت قراءة Vision واثقة، يجب أن يظل السعر المرئي تقديريًا إلى أن تُقرأ صفحة المتجر/يوافق فريق التشغيل؛ لا تربطوه مباشرة بأمر شراء.
4. **الكاش الجزئي للـpipeline:** `pipelineKey()` في `src/ayrovix/routes.ts` يأخذ مقتطفًا من أول وآخر 2KB وطول الصورة والنية، وليس بصمة كاملة. هذا يخلق احتمال تصادم متعمد أو غير مقصود وإرجاع نتائج Pipeline لصورة أخرى بالحجم نفسه. استخدم SHA-256 كاملًا من `effectiveBuffer` مع intent.
5. **تقييم النجوم:** `candidatePolicy.ts` يولد قيمة fallback من `match / 20` عندما لا يوجد تقييم تاجر، ويضع `ratingKind: 'match'`. يجب أن تعرض الواجهة ذلك كمؤشر تطابق لا كتقييم عملاء/نجوم متجر، حتى لا يلتبس على المشتري.
6. **إشارات OCR/الوثائق تحتاج توحيدًا:** الكود الحالي في `lensEngine.ts` يستدعي `readLensSignals`، بينما وثائق Lens أخرى تقول إن OCR خارج مسار Lens. هذا اختلاف مهم في الخصوصية والسلوك؛ يجب أن تكون الوثيقة والسياسة والواجهة متطابقة.
7. **مصادر الصور الخارجية:** صور النتائج قد تأتي من متاجر/Google عبر روابط خارجية؛ قد تتعطل أو تمنع hotlink أو تتغير. يلزم إظهار المصدر والتعامل مع عدم التوفر، مع Cache/Proxy مضبوطين دون إعادة استضافة غير مرخصة.
8. **تحقق السعر والمخزون لهما صلاحية زمنية:** أي «موجود» أو سعر صفحة متجر قد يصبح قديمًا. اعرض وقت التحقق، ولا تسمح للحالة القديمة أن تبدو آنية.
9. **ميزة مراقبة السعر:** `targetPriceTnd` يُخزّن عند إنشاء watcher، لكن `checkDueWatchers` يقارن السعر الجديد بالسابق فقط ولا يجلب هدف السعر في استعلامه. لذلك إشعار السعر المستهدف المحدد من المستخدم يبدو غير مطبق؛ أصلح منطق المقارنة والواجهة أو احذف خيار الهدف مؤقتًا.
10. **قابلية توسع Price Watch:** كل tick يفحص 8 watchers كحد أقصى وبشكل متسلسل، مرة كل ساعة، والحد الأدنى بين فحص watcher وآخر 6 ساعات. عندما يزيد العدد عن سعة المعالجة سيكبر التأخر؛ قِس throughput وأضف Queue/توازيًا مضبوطًا مع منع تكرار التشغيل بين النسخ.

### تحسينات Lens ذات الأولوية

- مجموعة اختبار ثابتة بموافقة أصحاب الصور، تشمل: منتج منفرد، عدة منتجات، صور منخفضة الجودة، كتابة عربية/فرنسية، أسعار مشطوبة، عملات، سلة، QR/باركود، منتجات مقلدة/غير مطابقة.
- تسجيل نتيجة المقياس مع نسخة النموذج/المطالبة/القواعد، لا الاكتفاء بإحصاء زمن الاستجابة.
- عرض الثقة ومصدر السعر بوضوح: «قراءة من الصورة»، «سعر من صفحة التاجر»، «تقدير AYROVI»، «بانتظار مراجعة».
- تأكد من أن أي طلب/سلة لا يقبل إلا عرضًا موقعًا حديثًا أو مراجعة بشرية؛ اختبر replay وتعديل السعر والعملة والرابط.
- قياس P50/P95 من مستخدمين حقيقيين وشبكات تونس وأجهزة متوسطة، مع ميزانية تأخير لكل مرحلة لا مجرد timeout منفصل لكل مزود.

## 6. النواقص التي تمنع إطلاقًا إنتاجيًا مطمئنًا

### تشغيل وخدمات حقيقية

- لا توجد مفاتيح تشغيل محلية في النسخة التي فُحصت، لذلك لم يُثبت عمل Anthropic/SerpApi أو Konnect/SMS/OAuth/Mail live.
- لا يوجد دليل من هذا الفحص على اختبار مدفوع كامل من إنشاء الطلب حتى webhook/تسوية/استرداد وإشعار العميل.
- خدمة SMS التونسية محددة كـwebhook؛ يلزم اختيار مزود، اختبار Orange/Ooredoo/TT، التسليم الفعلي، الحدود والتكلفة.
- إعداد Konnect ووسائل الدفع البنكية/البريدية يتطلب اعتمادًا ومطابقة مالية حقيقية؛ نجاح الاختبارات الوهمية لا يكفي.
- معدلات الصرف والرسوم الجمركية تقديرية وقابلة للإدارة. يجب اعتمادها تشغيليًا وقانونيًا وتوضيح أنها تقدير إلى أن يؤكد التاجر/الوسيط، لا رأيًا جمركيًا ملزمًا.

### بيانات وسياسات

- تحديد مدة الاحتفاظ لكل من: صور/إشارات Lens، محادثات المساعد، السجلات، بيانات الطلب والفواتير، إثباتات الدفع وملفات CRM.
- مراجعة صفحة الخصوصية والشروط والحذف والاحتفاظ قبل تشغيل OAuth أو جمع بيانات مستخدمين حقيقيين.
- توحيد سياسة التحقق من رقم الهاتف؛ الوثائق والواجهة يجب أن تقول الشيء نفسه الذي ينفذه Backend.
- إعداد استعادة نسخة احتياطية موثقة، لا مجرد نجاح إنشاء ملف backup.

### صيانة الكود والوثائق

- `src/db/database.ts` ملف كبير جدًا يجمع مخططًا وتهيئة وmigrations وseed؛ يلزم فصل migrations المرقمة عن seed وعن استعلامات المجال.
- بعض routers وخدمات Admin كبيرة ومتشعبة، ما يرفع صعوبة المراجعة واحتمال regressions.
- يوجد عدد كبير من تقارير Audit وخطط مراحل تاريخية. بعض مستندات Lens تتعارض مع السلوك الحالي مثل OCR/إشارات الصورة؛ يجب وضع `CURRENT_ARCHITECTURE.md` واحد ووضع التاريخي تحت `docs/archive/` مع تاريخ وحالة superseded.
- CI يعمل على Node 20، بينما Render محدد على Node 22؛ وحزم Native مثل `better-sqlite3` تجعل توحيد نسخة Node بين CI والإنتاج مهمًا. ثبّت Node 22 في CI أو اختبر نسختي 20 و22 صراحة.
- CI يكتفي بـ`npm audit --audit-level=high`، وبالتالي لم يكن يمنع الثغرات المتوسطة التي عُثر عليها هنا. أوصي بـ`--audit-level=moderate` بعد علاج أي تنبيهات قابلة للإصلاح.

## 7. خطة إصلاح وتطوير مرحلية

### المرحلة صفر — قبل أي إطلاق عام (0–3 أيام عمل)

1. **إغلاق SSRF DNS rebinding** مع اختبار regression حقيقي لمحاكاة DNS متغير.
2. **تثبيت حدود API**: Redis/edge limiter أو على الأقل IP + حساب + هاتف، وتحديد حد IP مستقل لطلبات OTP وLens والتفاعل الاجتماعي.
3. **Fail-closed للإعدادات الإنتاجية**: منع كلمة مرور Admin التجريبية، التحقق من `CUSTOMER_AUTH_SECRET` و`PUBLIC_BASE_URL` وHTTPS ومجلد قاعدة البيانات الدائم.
4. **ضبط ميزانيات المزودين**: caps على لوحة كل مزود، حد يومي داخلي، تنبيه عند 70/90%، وإيقاف آمن عند تجاوز الميزانية.
5. **تفعيل secret scanning** على التاريخ الكامل للمستودع وCI، مع تدوير مفاتيح أي تاريخ مكشوف.
6. إضافة فحص إقلاع يقول فقط configured/missing، دون طباعة الأسرار.

**بوابة الخروج:** لا High/Critical في dependency/static security، كل اختبارات SSRF/auth/CSRF ناجحة، production env check يفشل عند حذف secret، ونسخة احتياطية يمكن استعادتها.

### المرحلة الأولى — Pilot مضبوط (الأسبوع 1–2)

1. Stage منفصل ببيانات تجريبية غير حقيقية وحسابات مزودين sandbox.
2. تنفيذ تدفق طلب مدفوع كامل مع webhook متكرر/متأخر/مزيف، ومطابقة سجل الدفع والطلب والفاتورة.
3. اختبار OTP والبريد وOAuth من البداية للنهاية على نطاق داخلي.
4. لوحة تشغيل لـLens: p50/p95، نسبة فشل كل مزود، نتيجة بلا سعر، استهلاك/صورة، معدل cache، وزمن حتى أول نتيجة.
5. توثيق إجراءات: فشل بوابة الدفع، اختلاف السعر، إلغاء، Refund، فقدان مزود AI، مساحة القرص، وفشل النسخ الاحتياطي.
6. تدقيق لغة الأسعار والرسوم والشروط وسياسة الخصوصية واللغة العربية/الفرنسية.

**مقاييس Pilot المقترحة:** 100–300 مستخدم مدعو؛ صفر طلب يُعتمد على سعر Pending؛ معدل فشل تقني أقل من 2%؛ متابعة كل عملية دفع يدويًا حتى التسوية؛ قياس دعم العملاء وأسباب التخلي.

### المرحلة الثانية — تحسين الجودة والتحويل (الأسبوع 3–6)

1. بناء dataset معلّم من 300–500 صورة/رابط بموافقة واضحة، وتقسيم train/validation لاختبار التغيرات.
2. تسجيل: Top-1 وTop-3 للمنتج، دقة العلامة/الموديل، دقة المبلغ+العملة، نسبة السعر الذي تطابقه صفحة التاجر، false-verified، latency وcost per successful search.
3. إصلاح Price Watch: الهدف السعري، تكرار الإشعارات، انتهاء watcher، فشل صفحة التاجر، وعدم عرض «السعر انخفض» بسبب اختلاف عملة أو conversion rule فقط.
4. اختبار أجهزة Android فعلية وشبكات 3G/4G تونسية، صلاحية الكاميرا وإلغاء stream، ذاكرة الصور، قارئ QR، والواجهة العربية RTL.
5. قياس سلة التحويل، الاستفسار، الإتمام، الإلغاء، الاسترجاع، ومدة معالجة الطلب. لا تعتمد على عدد تحميلات Lens وحده.

**أهداف جودة أولية (تُراجع بعد baseline):** P95 لنتيجة Lens أولية أقل من 6 ثوانٍ على شبكة جيدة؛ Top-3 للمنتج ≥90% في مجموعة التقييم؛ صفر false-verified في السعر؛ إظهار «غير مؤكد» كلما غاب دليل التاجر.

### المرحلة الثالثة — توسع هندسي (بعد ثبوت الطلب، 2–3 أشهر)

- نقل بيانات التشغيل الأساسية من SQLite إلى PostgreSQL إذا احتجتم أكثر من نسخة/عامل أو حجم كتابة أعلى؛ لا تنتقلوا لمجرد الحداثة قبل القياس.
- Redis لrate limits والكاش والـleases؛ Queue دائمة للـAI وPrice Watch والبريد والنسخ الاحتياطي.
- تخزين الملفات في object storage مع private/public policies واضحة بدل ربطها بقرص نسخة واحدة.
- فصل Worker المهام المجدولة عن Web، وإضافة idempotency/outbox للإشعارات والـwebhooks.
- إضافة مراقبة أخطاء/Tracing/Alerts وSLOs، مع إخفاء PII من السجلات.
- اختبار ضغط 50/100/250 طلبًا متزامنًا، واختبار restore/rollback/migration على نسخة قاعدة production مشفّرة.

**أهداف تشغيل مبدئية:** توافر 99.5% للـPilot، RPO ≤24 ساعة قبل تفعيل مزود خارجي للنسخ ثم خفضه حسب الحاجة، RTO ≤4 ساعات، وقياس ميزانية المزود لكل طلب ناجح.

## 8. خطة متابعة العمل

استخدموا لوحة واحدة لكل Finding بالحالات: `OPEN → IN_PROGRESS → TESTED → DEPLOYED → VERIFIED`، وتضم الأعمدة:

| الحقل | المطلوب |
|---|---|
| ID/الأولوية | مثل SEC-01 / P1 |
| الدليل | الملف/الدالة/اختبار يثبت المشكلة |
| مالك التنفيذ | مطور/تشغيل/منتج |
| الإصلاح | وصف محدد قابل للمراجعة |
| اختبار رجوع | اسم test أو سيناريو يدوي |
| بوابة نشر | staging/production + مراقبة بعد النشر |
| الحالة/التاريخ | لا تُغلق بالتوثيق فقط؛ تُغلق بعد التحقق بعد النشر |

### ترتيب التذاكر المقترح

- **SEC-01:** DNS pinning لـSSRF + اختبارات rebinding — P1.
- **SEC-02:** rate limit موزع وحد IP لOTP/Social/Lens — P1.
- **OPS-01:** رفض إعدادات production الافتراضية — P1.
- **OPS-02:** اختبار استعادة خارج قرص التطبيق — P1.
- **PRIV-01:** إفصاح وإبقاء/حذف بيانات Lens ومزودي المعالجة — P1 قبل المستخدمين الحقيقيين.
- **LENS-01:** full SHA-256 لـpipeline cache — P2.
- **LENS-02:** dataset وقياس accuracy/false-verified — P1 منتجيًا.
- **LENS-03:** إصلاح الهدف السعري ومقياس سعة Price Watch — P2.
- **DOC-01:** توحيد مستند Lens الحالي وأرشفة التقارير القديمة — P2.
- **PLAT-01:** توحيد Node 22 ورفع CI audit level إلى moderate — P2.

## 9. القرار النهائي

- **ما يصلح الآن:** عرض Demo وPilot مغلق مع بيانات غير حساسة، ومفاتيح Sandbox وحدود واضحة.
- **ما لا أوصي به بعد:** فتح رفع الروابط والصور للجمهور على إنتاج مكشوف قبل إصلاح SSRF، تقوية حدود التكلفة والـrate limiting، ومنع إعداد Admin الافتراضي.
- **الإصلاح المنجز فعليًا هنا:** إزالة تنبيهين Moderate في سلسلة البريد؛ وأُعيدت الاختبارات والبناء والنوع بعد التحديث بنجاح.
- **أهم خطوة تالية:** SEC-01 ثم SEC-02 ثم بوابة إعدادات الإنتاج، وبعدها Pilot مدعو مع مراقبة حقيقية.

هذا المشروع يمتلك أساسًا جيدًا ونطاقًا طموحًا؛ الأولوية الآن ليست إضافة وحدات جديدة بقدر ما هي **تثبيت الثقة، توحيد مصدر الحقيقة، القياس على مستخدمين حقيقيين، وإغلاق مخاطر الروابط والتكلفة والتشغيل**.
