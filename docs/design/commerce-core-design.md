## المرحلة 1 — Architecture Design (المكوّنات والعلاقات)

### 1.1 طبقتان، لا أربع منصات

```text
┌─ طبقة الاكتشاف (استقلالية كاملة — ممنوع توحيدها) ─────────────────────────┐
│ Content: ريلز/ستوريهات/منشورات + كتالوج CRM                              │
│ Z Lens:  بحث صورة/كلمة/رابط → SerpApi (/api/zayrovix)                     │
│ AYWEBS:  تصفّح حيّ + التقاط بأدلة موثّقة + سلّة اختيار                    │
│ S BASE:  بحث سوق الصين (Apify) + بطاقات موسعرة                            │
└──────────────────────────────┬───────────────────────────────────────────┘
                               │ نقطة العبور الوحيدة: «اخترت ⇒ للسلة المركزية»
┌──────────────────────────────▼───────────────────────────────────────────┐
│                 ZAYROVI Commerce Core (طبقة التجارة)                     │
│  Unified Cart · Pricing · Promotions · Deposit · Order · Orchestration   │
└──────────────────────────────┬───────────────────────────────────────────┘
                               │
                    CRM / WHS / تتبّع العميل
```

### 1.2 مكونات Commerce Core الستة وملكية البيانات

| المكوّن | جداوله (موجودة أو جديدة) | مَن يكتب | مَن يقرأ |
|---|---|---|---|
| **Unified Cart** | جداول السلة الحالية + أعمدة جديدة `origin/lane/shippingTND/etaDays` | الخادم فقط عبر نقاط `/api/cart/*` | الأربعة (عرض) + P2 الطلبات |
| **Pricing** | `calculatePrice` + `PricingRules` (موجودة) | الباك-أوفيس (قواعد) | كل الأنظمة — **حتى aywebs تستدعيه داخلياً** |
| **Promotions** | `promotions` (موجودة) + نطاقات جديدة | الباك-أوفيس | checkout + عرض السلة |
| **Deposit** | جديد: `deposit_policy` + `deposit_allocations` | الـcheckout فقط | Master/Sub + CRM |
| **Order** | جداول الطلبات الحالية + `sub_orders` جديد | Order Engine فقط | العميل (Master) + الباك-أوفيس |
| **Orchestration** | بلا جداول — توزيع + ربط مراجع خارجية | الـcheckout فقط | تتبّع + CRM |

**القاعدة المعمارية:** أي كود جديد للتجارة يُكتب في هذه الطبقة؛ الأنظمة الأربعة
لا تُضاف لها جداول سلة/سعر/طلب جديدة أبداً.

### 1.3 فحص المبدأ ضد الكود — مصفوفة الامتثال (بالأدلة)

| المحرّك | الحالة | الدليل في المستودع |
|---|---|---|
| محرك السعر | **مطابَق ✓** | `calculatePrice` واحد (`services/pricing.ts`) — يستعمله الجميع، **بما فيهم aywebs داخلياً** (`aywebs/cart.ts:381,552`) |
| السلة الموحّدة | **مطابَق ✓** | جسر حيّ `POST /cart/bridge-to-zayrovi` (`aywebs/routes.ts:1135`) ينقل أسطر aywebs الجاهزة إلى السلة المركزية بمزامنة كميات (لا تكرار إضافة)، وحجب الأسطر المرفوضة بأكواد صادقة، وإصدار **توكن موقّع VERIFIED** لكل سطر يعبر (`zayroviBridge.ts:149,202`) — أي السطر المُنقَل محميّ بالتوقيع نفسه |
| الطلبات | **انحراف واحد ✗** | aywebs عندها مسار طلبات ومدفوعات مستقل (`POST /orders`, `/orders/:id/submit`, `/payments/*`) — انحراف عن «الطلب مركزي» |

**حل الانحراف دون لمس داخل aywebs (قرار جديد D7 — معتمَد مبدئياً بشروط المالك الخمسة، §5):**
الطلب الرئيسي المركزي يملك التجارة؛ طلب aywebs **يُخفَّض إلى «سجل تنفيذ»** مرتبط
خارجياً بالطلب الفرعي global: الـSubOrder يخزن `external_ref = aywebs order_number`
عبر **رابط الطلبات الموجود أصلاً** `listAyWebsOrderLinks` (`zayroviBridge.ts:379`).
Orchestration تُسوّق التنفيذ عبر واجهات aywebs الموجودة من خارجها — لا دمج
جداول، لا تعديل داخلها، والمشتري لا يرى إلا الطلب الرئيسي.

### 1.4 نقاط التوسّع الجاهزة بالضبط حيث يحتاجها التصميم

واجهات aywebs نفسها تحتوي placeholder بمراحل معلنة — Commerce Core يمتلئ عليهما:
- `GET /warehouse` → **PHASE 7 Warehouse** (تجميع الطرود) — موضع Orchestration للـglobal/china.
- `POST /shipping/quote` → **PHASE 8 Shipping** (تسعير الشحن الدولي) — موضع `shippingTND/etaDays` للأسطر الدولية.

## المرحلة 2 — Business Logic (قواعد التجارة المركزية)

### 2.1 قواعد السلة الموحّدة

**نموذج السطر** (الموجود + الجديد المطلوب):

| الحقل | الحالة | القاعدة |
|---|---|---|
| `store/sourceUrl/sourcePrice/sourceCurrency/quantity/variant/requestedSize/requestedColor/customerNote` | موجود ✓ | كما هو، لا تغيير |
| `priceVerificationStatus/priceTrust/lineTotalTND` | موجود ✓ | FRESH (توكن Lens/الجسر) · MANUAL (S BASE/كتالوج) · STALE (منع الدفع) |
| **`origin`** | جديد | `catalog\|lens\|aywebs\|sbase` — يضعه الخادم عند الإضافة، العميل لا يرسله أبداً |
| **`lane`** | جديد | `local\|global\|china` — مشتق من origin (قاعدة ثابتة، ليس حقل حر) |
| **`shippingTND` / `etaDays`** | جديد | يُحسبه الخادم فقط (§2.6)، يُعرض ولا يُرسل من التطبيق |

**قواعد الدمج:** نفس `referenceUrl + variant` ⇒ رفع الكمية لا سطر جديد (موجود
سلوكاً في الجسر بمزامنته، وُحِّد 04/10/2026). **قاعدة الأسطر الموقّعة:** بعد
الإنشاء لا يعدّل سعرها شيء — لا تخفيض داخل السطر، لا تجديد تلقائي (§2.3، §2.4).
**قاعدة STALE:** `priceTrust=STALE` يمنع الدفع (قائمة `zayroviCartReadiness`
الموجودة) — تُعالَج بتحديث صريح يُنشئ سطراً جديداً بتوقيع جديد.

### 2.2 قواعد التسعير — سياسة لكل مدخل، نتيجة موحّدة

| origin | مصدر السعر | من يحسب | الثقة |
|---|---|---|---|
| catalog | كتالوج CRM (ثمن محلي) | `calculatePrice` | FRESH |
| lens | سعر عالمي مُكتشف | الخادم + quote موقّعة | FRESH/STALE بالـTTL |
| aywebs | سعر مُلتقط من المتجر بأدلة | `calculatePrice` + الجسر يوقّع | FRESH موقّع |
| sbase | سعر سوق الصين بالقطعة | محرك التسعير المحلي (جمارك/TVA/فريت/خدمة) | MANUAL |

**النتيجة الموحّدة لكل سطر:** `{ priceTND, breakdown[], pricingVersion, priceTrust }`
— دينار واحد. **ممنوع:** اختراع سعر/عملة، قنوات تحويل خارج المحرك، أو عرض
«غير متوفّر» بأي صيغة غير الصادقة (بلا قواعد ⇒ `PRICE_UNAVAILABLE`).

### 2.3 قواعد التخفيض — النطاقات ومصفوفة القابلية

النطاقات: الموجودة `DAY/CATEGORY/PRODUCT` + الجديدة **`ORDER`** (سلة كاملة)،
**`SOURCE`** (عروض مرتبطة بمدخل: «خصم على sourcing هذا الأسبوع»)، **`COUPON`** (أكواد).

مصفوفة القابلية `origin × scope` (القاعدة الموجزة: **الخصم على مستوى الطلب/الملخص،
لا داخل السطر الموقّع**):

| scope ↓ / origin → | catalog | lens | aywebs | sbase |
|---|---|---|---|---|
| PRODUCT/CATEGORY/DAY (سطر) | ✓ | ✗ (يكسر التوكن) | ✗ (يكسر التوكن) | ✓ |
| ORDER (سلة كاملة) | ✓ | ✓ **على الملخص** | ✓ **على الملخص** | ✓ |
| SOURCE | ✓ | ✓ | ✓ | ✓ |
| COUPON | ✓ | ✓ على الملخص | ✓ على الملخص | ✓ |

لماذا؟ توقيع السطر يفحص `(price, currency, title, referenceUrl)` — أي خصم داخل
السطر يجعل التوكن كاذباً عند التحقق في `routes.ts`. فالمخفيضات فوق الأسطر
الموقّعة تُطبَّق كسطر خصم على مستوى الطلب (`order_discount`)، والسطر يظل كما وُلّد.

### 2.4 قواعد العربون والدفع

**السياسة المركزية** (`deposit_policy` جديد): `defaultPercent` (قرارك المثال: 30%)
+ استثناءات بترتيب الأولوية: `origin/lane` ثم `product` ثم حملة مؤقتة.

**المعادلة (عربون موحّد — D4):** ⚠️ **[v2] التوزيع النسبي أسفله مُتراجَع — المعادلة الصحيحة في §8** (النسبي يهدم سياسة النسب عند اختلافها بين المسارات).
```text
depositTND = round( Σ subtotal_i × percent(origin_i) … )  ← الاستثناءات تُرجّح على الافتراضي
allocation_i = depositTND × (subtotal_i / total)          ← داخلي فقط، في deposit_allocations
```
العميل يدفع **رقماً واحداً** في صفحة واحدة (D6). **رفض/إلغاء مسار تنفيذ** ⇒
`allocation_i` تُعاد **رصيداً على المتبقي أولاً** (`balance = total − deposit`
الموجود في `invoice.ts`)، والاسترداد النقدي بقرار الباك-أوفيس فقط. حالات ERP
جاهزة أصلاً: `AWAITING_DEPOSIT → AWAITING_PAYMENT_VERIFICATION → CONFIRMED`
و`PARTIALLY_PAID/REFUNDED`.

### 2.5 قواعد الطلب — Master / Sub-Orders

- **Master `ZR-xxxx`** (الرقم من `nextSequenceNumber` الموجودة): يراه العميل،
  مجموعه = مجموع الفرعية، حالته = **أسوأ حالة نشطة** بين الفرعية (العميل يرى
  الطلب متأخراً لأن فرعية واحدة متأخرة — لا وهم اكتمال).
- **SubOrder لكل lane**: حالة خام داخلية + تتبّع مستقل + `external_ref` (رقم
  سجل التنفيذ aywebs للـglobal — §10) + شحنو ومدته. ⚠️ **[v2] Sub-Order ≠ Shipment — الفصل الكامل في §7.**
- **القاموس الموحّد للعرض (D5)** فوق الحالات الخام: `قيد المراجعة / قيد التنفيذ /
  في الطريق / وصل جزئياً / وصل / أُلغي` — mapping ثابت لكل lane.
- **الرفض الجزئي:** إلغاء فرعية لا يلغي الطلب — تُعاد حصتها من العربون رصيداً (§2.4).

### 2.6 قواعد الشحن والمدة (الاختلاف الذي طلبته أن يظهر)

| lane | مصدر الحقيقة للشحن | مصدر المدة |
|---|---|---|
| local | checkout الحالي (بيت/مكتب/نقطة — موجود) | ساعة الخادم |
| global | `POST /shipping/quote` (PHASE 8 placeholder جاهزة) + `checkoutFees` aywebs | قاعدة لكل متجر |
| china | `freightTND` من محرك التسعير (موجود في estimate S BASE) | قاعدة sourcing |

الخادم يحسب ويخزن على السطر؛ التطبيق **يعرض** ويمنع أي حقل شحن من العميل.

## المرحلة 3 — Integration Design (عقود الاتصال — بالأسماء الحقيقية)

| # | المدخل | يدخل السلة عبر | الحالة | أحداثه | أكواد فشله الصادقة |
|---|---|---|---|---|---|
| 1 | **Content** | `POST /cart/catalog` + `/cart/catalog/look` | موجودة ✓ | أحداث القمع الموجودة | أكواد السلة الحالية |
| 2 | **Z Lens** | `POST /api/cart/items` + `priceToken` | موجودة ✓ | funnel موجود | `INVALID_ZAYROVIX_PRICE_TOKEN`, `PRICE_*` |
| 3 | **AYWEBS** | اكتشاف حيّ (`/capture`, `/product/resolve`, `/price-quote`) → سلّة اختيار بأدلة → **الجسر `POST /cart/bridge-to-zayrovi`** (بنقل idempotent حتى عند كل إضافة `routes.ts:992–1001`) | موجودة ✓ | `cart.bridge_to_zayrovi` audit | `PRICE_CHANGED`, `VARIANT_UNAVAILABLE`, `OUT_OF_STOCK`, `PRICE_UNAVAILABLE`, `CART_LOCKED` |
| 4 | **S BASE** | `POST /api/cart/items` بلا توكن ⇒ `PENDING_MANUAL` | موجودة ✓ (26/11) | funnel موجود | `INVALID_CART_ITEM`, `PRICE_*` |

**عقد التنفيذ (الجديد — P2):** عند checkout الموحّد، Order Engine يُنشئ Master +
الفرعية، وOrchestration:
- local → مسار الطلب الحالي كما هو.
- global → تنفيذ عبر واجهات aywebs الموجودة (`POST /orders`…) + ربط
  `external_ref` عبر روابط الطلبات الموجودة — **صفر تعديل داخل aywebs**.
- china → فرعية «قيد المراجعة» — المراجعة اليدوية في الباك-أوفيس؛ الأتمتة قرارك لاحقاً.

**الأحداث الموحّدة (جديدة، فوق `recordFunnelEvent` الموجود أصلاً في الجسر):**
`cart.line.added{origin}` · `order.split{lanes[]}` · `deposit.allocated` ·
`suborder.status_changed{lane,code}` — كلها لأحد القراءة (CRM/تتبّع)، لا قرار فيها.

**ما يُمنع على كل مدخل (نص العقود):** لا جداول تجارة خاصة، لا حساب سعر بديل،
لا عرض منفصل للعربون/الطلب — اكتشافك حر، وتجارتك مركزية أو لست مدخلاً.

## 4. ما بعد اعتمادك

وثيقة التنفيذ (للمطور — أنا) تُكتب بعد توقيعك وتتضمن لكل مرحلة: حِزم عمل
بالملفات، جداول وأعمدة الهجرة، بوابات الاختبار (`tsc` · vitest · jest UI ·
`design:check` · CI من الهاتف)، ومعايير القبول المرتبطة بلقطاتك الحية.
المراحل كما في الدراسة: **P1** وسوم السطر والعرض بأقسام → **P2** Master/Sub +
العربون الموزّع + عقد التنفيذ (D7) → **P3** تخفيضات v2 + مصفوفة القابلية →
**P4** Orchestration + قراءات CRM + القاموس الموحّد.

**بانتظار توقيعك على:** المبدأ (مثبت) · baseline D1–D6 · **D7 الجديد** (طلب
aywebs سجل تنفيذ مرتبط بالفرعي عبر روابط الطلبات الموجودة).

## 5. سجل مواقف المالك (27/11 — بعد المراجعة الأولى)

> **ليست توقيعاً نهائياً بعد.** بعد المراجعة البندية تُصدر الموافقة المؤسسية
> «ZAYROVI Commerce Core – Architecture & Business Logic Approval v1.0» ثم
> تُكتب وثيقة التنفيذ.

| القرار | موقف المالك |
|---|---|
| D1 — جسر AYWEBS | موافقة مبدئية |
| D2 — مراجعة S BASE | موافقة مبدئية |
| D3 — التخفيضات على الملخص | موافقة مبدئية (توزيع الخصم محاسبياً — وثيقة التنفيذ تفصّله) |
| D4 — توزيع العربون | **يحتاج ضبطاً محاسبياً** (دراسة تكميلية بمصفوفة دورة الحياة) |
| D5 — القاموس الموحّد | موافقة |
| D6 — صفحة دفع واحدة | موافقة مبدئية |
| D7 — طلب aywebs سجل تنفيذ | موافقة مبدئية **مع الشروط الخمسة أدناه** |

### 5.1 قرار D7 — الشروط الخمسة المثبّتة من المالك

> «AYWEBS يصبح مسؤولاً عن **تنفيذ** عملية التسوق، لا عن امتلاك تجربة الطلب
> التجارية للعميل» — تحقيق مبدأ *One Commerce Core – Multiple Independent
> Sales Engines*.

1. **AYWEBS لا ينشئ طلب شراء مستقلاً يراه العميل.** في المسار الموحّد، شاشات
   طلبات aywebs في التطبيق تتحول (P2) إلى قراءة الطلب الرئيسي من Core — تغيير
   واجهة تطبيق، لا تعديل داخل aywebs.
2. **Commerce Core هو صاحب الطلب الرئيسي والطلبات الفرعية** — ملكية التجارة
   كاملة فيه (§2.5).
3. **AYWEBS يحتفظ بسجلات التنفيذ التقنية الخاصة به** — جداوله وأدلته وحالاته
   كما هي، بلا دمج (R2 في الدراسة).
4. **لا دفع مزدوج ولا عمليتا دفع لنفس المشتريات.** حاجز المنع قائم بنيوياً:
   الأسطر المنقولة عبر الجسر تسجَّل في خريطة الروابط (`ayWebsCartLinkedMap`)
   فلا تُنقل مرتين؛ والقاعدة الجديدة: السلّة تسلك **مساراً واحداً حصراً** — إمّا
   تُجسَر إلى Core (وتدفع مرة واحدة عند checkout الموحّد) أو تُدفع في وضع aywebs
   المستقل — لا الاثنان أبداً لنفس الأسطر؛ والدفع يجمعه Core، وسجل التنفيذ
   في aywebs يحمل صفر دفع عميل.
5. **CRM يربط الطلب الرئيسي بسجل تنفيذ AYWEBS ويتتبع حالته** — عبر روابط
   الطلبات الموجودة `listAyWebsOrderLinks` + أحداث الحالة الموحّدة (§3).

### 5.2 Commerce Integration Layer (CIL) — طبقة التكامل الموحّدة

> مفهوم المالك: طبقة تكامل موحّدة تستقبل المنتجات والبيانات والأحداث من جميع
> الأنظمة **وفق عقود اتصال موحّدة**؛ كل نظام جديد يلتزم بالعقود ثم يدخل Core —
> **بدون تعديل Commerce Core في كل مرة**. هذا هو التنفيذ البنيوي للمبدأ
> الاستراتيجي A.5 في الدراسة: *Commerce Core مستقل عن مصادر المنتجات*.

**عائلتا عقود الدخول:**
- **عقود تجارية** (منتجات → سلة): `origin` + `lane` + مسار إضافة + سياسة تسعير
  مربوطة بـ`calculatePrice` + أكواد فشل صادقة + أحداث.
- **عقود تشغيلية** (أحداث → Orchestration): عروض شحن (`shipping/quote`)،
  أحداث تتبّع، حالات توريد — لا منتجات.

**عقد الدخول لأي تكامل جديد (سبعة بنود):**
1. قيمة `origin` جديدة مسجّلة (توسّعية — سجل تكوين، لا enum مغلق).
2. mapping إلى `lane` (أو قيمة lane جديدة بنفس الآلية — توريد أوروبا ⇒ `eu`).
3. مسار إضافة للسلة المركزية وفق مخطط السطر (§2.1) أو جسر، بلا سلة خاصة.
4. سياسة تسعير مربوطة بالمحرك المركزي — **بلا محرك ثانٍ أبداً**.
5. مسار تنفيذ مرتبط: تنفيذ محلي / سجل تنفيذ خارجي مرتبط (نموذج D7) / مراجعة.
6. أكواد فشل صادقة موثّقة + أحداث الحالة الموحّدة.
7. **لا يملك** سلة/طلب/دفع/تجربة طلب خاصة.

**أمثلة المالك المستقبلية تُصنَّف آلياً:** متجر محلي جديد (origin جديد، lane
local) · مورد صيني جديد (origin جديد، lane china) · **شركة شحن جديدة** (لا
origin — عقود تشغيلية توسّع جدول الشحن فقط) · **توريد أوروبا** (lane جديد
`eu` بنفس آلية التوسّع) · **بيع عبر التجار** (origin جديد بlane تجاريه).

**النتيجة المقاسة:** تكامل جديد = تسجيل عقود + سطر في سجل التكاملات +
قراءته في نقاط العبور — **صفر تعديل** في المحركات الستة.

## 6. [v2] Commerce Integration Layer — طبقة مستقلة بمحوّلات (Adapters)

> مراجعة المالك: CIL يجب أن تكون **طبقة واضحة بين مداخل البيع وCommerce Core**،
> وظيفتها **توحيد عقود الاتصال لا توحيد محركات الاكتشاف**. مدخل جديد ⇒ **Adapter
> جديد** يترجم بياناته إلى الصيغة التي يفهمها Core — دون تعديل محرك السلة أو
> الطلبات أو الأسعار.

```text
  CONTENT   Z LENS   AYWEBS   S BASE   [مدخل 5]   ← محركات اكتشاف مستقلة (لا تُموَّح)
     │          │         │        │          │
     └──────────┴────┬────┴────────┴──────────┘
                     │
      Commerce Integration Layer (CIL)
      Adapter(مدخل) → عقد السبعة بنود (§5.2) → التحقق → التوجيه
                     │                    ← سجل التكاملات integration_registry
┌────────────────────▼─────────────────────────┐
│            ZAYROVI Commerce Core             │
│  Cart · Pricing · Promotions · Deposit ·     │
│  Order · Orchestration                       │
└──────────────────────────────────────────────┘
```

**قواعد الطبقة:**
1. **المحوّل هو الباب الوحيد**: مدخل لا يستدعي محركات Core مباشرة أبداً —
   محوّله فقط من يترجم إلى مخطط السطر (§2.1) وعقود الأحداث (§3).
2. **المحوّل يعلن ولا ينفّذ**: يصرّح `origin/lane/سياسة التسعير/أكواد الفشل/أحداثه`
   في `integration_registry` (جدول تكوين جديد صغير: origin، mapping الlane،
   وحدة المحوّل، حالة active/suspended) — القيم توسّعية بلا enum مغلق.
3. **المداخل الأربعة الحالية هي المحوّلات v1 نفسها** — ما هو مبنٍ اليوم يُسمّى
   ويُحدُّ ولا يُعاد بناؤه: محوّل الكتالوج (`/cart/catalog*`) · محوّل Lens
   (`/cart/items` + توكن) · محوّل aywebs (الجسر) · محوّل S BASE (`/cart/items`
   بلا توكن).
4. **معيار الاستقرارية (معيار المالك للحكم النهائي):** لو تغيّرت جميع مداخل
   البيع غداً، تبقى المحركات الستة بلا تعديل — تعديل المداخل يُدار حصراً
   بسجل التكاملات وملفات المحوّلات. أي PR يعدّل محرّكاً لتقبّل مدخلاً جديداً
   ⇒ مرفوض بنيوياً.

## 7. [v2] فصل الكيانات: Master Order / Sub-Order / Fulfillment / Shipment

> مراجعة المالك: «كلها Global لكنها ليست بالضرورة عملية تنفيذ واحدة، وقد يكون
> الطلب الفرعي الواحد موزعاً على شحنتين» ⇒ **Sub-Order لا يساوي Shipment**،
> ولا نربط عدد الشحنات بعدد الطلبات الفرعية — مهم عند ربط Core بWHS
> وشركات اللوجستيك.

| الكيان | وظيفته | وحدة الحساب/المال | وحدة الفيزياء |
|---|---|---|---|
| **Master Order** (`ZR-xxxx`) | الطلب الرئيسي الذي يراه العميل | ✓ المجموع والعربون | ✗ |
| **Sub-Order** | **مجموعة تنفيذ تجارية** (لكل lane — وسيط التسعير والتخصيص والعقد) | ✓ تخصيص العربون، صافي الإيراد | ✗ |
| **Fulfillment** | عملية تجهيز وتنفيذ داخل الفرعية (جمع/تحقق/تعبئة) — سجلات تنفيذ aywebs ومراجعات S BASE تتعلق هنا | ✗ | ✓ |
| **Shipment** | **الشحنة الفعلية**: ناقل، تتبّع، تجميع طرود في المستودع | ✗ | ✓ |

**العلاقات (الرسم):**
```text
Master 1──N SubOrder 1──N Fulfillment N──0..N Shipment   (عبر shipment_items)
```

- **فرعية واحدة ⇒ شحنة أو أكثر** (المورّد يقسّم الطلب) — و**شحنة واحدة قد
  تحمل أصنافاً من فرعيتين أو أكثر** (تجميع الطرود في المستودع — نقطة
  `/warehouse/items/:id/consolidate` الجاهزة في aywebs routes PHASE 7 هي
  موضع هذا التجميع).
- **المال يتبع التجارة (Sub-Order)، والفيزياء تتبع الشحنة (Shipment)** —
  لا يُشتق عدد الشحنات من الفرعية ولا العكس أبداً.
- العميل في صفحة Master يرى **بعدين منفصلين**: التقدم التجاري (الفرعية بحالاتها)
  والتقدم الفيزيائي (الشحنات بتتبّعها) — القاموس الموحّد (D5) يظل على الفرعية.

## 8. [v2] دراسة D4 التكميلية — دورة حياة العربون (D4 يبقى مؤجلاً حتى اعتماد هذا القسم)

> ملاحظة المالك الحاسمة: «منتج محلي 20% وصيني 50% — التوزيع التناسبي على
> إجمالي القيمة لا يعكس سياسة العربون الخاصة بكل مسار». **صحيح — المعادلة
> النسبية في v1 تُتراجَع.**

### 8.1 الفصل الرباعي المطلوب (كما حدّد المالك)

1. **حساب العربون المطلوب حسب سياسة كل مجموعة تنفيذ**:
   `required_i = round(subtotal_i × percent(policy(group_i)))` — بقاعدة
   **باقي التقريب للمجموعة الأكبر** حتى يساوي مجموع المطلوب الرقم المعروض
   للعميل بالضبط (لا فلس على الأرض).
2. **المبلغ الإجمالي الذي يدفعه العميل = Σ required_i** — رقماً واحداً في صفحة
   واحدة (D6). لا يوجد «رقم دفع» مستقل عن المطلوب إطلاقاً.
3. **تخصيص المدفوع = المطلوب نفسه لكل مجموعة** — التخصيص **مرآة للسياسة** لا
   توزيع نسبي. الثابت المحاسبي: **Σ تخصيصات نشطة = العربون المدفوع − المحرَّر −
   المسترَدّ** في كل لحظة من عمر الطلب.
4. **الإلغاء والاسترداد وإعادة التخصيص** — جدول دورة الحياة (§8.2).

### 8.2 مثال عددي بمسارات المالك (20% / 50%)

| | محلي (20%) | صيني (50%) | المجموع |
|---|---|---|---|
| subtotal | 300 د.ت | 200 د.ت | 500 د.ت |
| **المطلوب required** | **60** | **100** | **160 = ما يدفعه العميل** |
| **التخصيص allocated** | **60** | **100** | 160 ✓ مرآة السياسة |

- **(v1 التوزيع النسبي كان يعطي 96/64 — مرفوض**: تحرير تخصيص الصين 64 يترك
  للمحلي 96 > مطلوبه 60 ⇒ كسر السياسة. صحيحتها فقط بالمرآة.)
- **رفض المورّد الصيني**: تحرير تخصيصه 100 ⇒ العربون الفعلي 60 = مطلوب المحلي
  بالضبط؛ الرصيد = 300 − 60 = 240. **صفر تسويات يدوية** — الثابت يحمي نفسه.
- إلغاء المحلي بدلاً منه: تحرير 60 ⇒ المتبقي 100 = مطلوب الصيني بالضبط؛
  الرصيد = 200 − 100 = 100. ✓

### 8.3 جدول دورة الحياة (بنود المالك + الميكانيزم)

| الحالة | المعالجة (الميكانيزم الدقيق) |
|---|---|
| **إضافة منتج** | قبل التأكيد: إعادة احتساب المطلوب للمجموعة (وإعادة عرض الرقم الواحد). بعد الدفع: **عربون تكميلي** كسطر مطلوب مستقل على الفرعية — لا يُمزج بالمخصوص |
| **تأكيد الطلب** | تثبيت التخصيص: كل allocation → حالة ACTIVE (مجمَّد القيم) |
| **إلغاء منتج** | قبل التأكيد: إعادة احتساب المطلوب. بعد التأكيد: تحرير تخصيصه → **الرصيد أولاً** (يخفض المتبقي)؛ إن لم يبقَ متبقٍ ⇒ مؤهّل استرداد |
| **رفض مورد صيني** | تحرير المبلغ المخصص **للفرعية كاملة** → رصيد؛ الفرعية تُغلق دون سقوط الطلب؛ استرداد نقدي بقرار الباك-أوفيس فقط (حالة `REFUNDED` موجودة في PAYMENT_STATUSES) |
| **ارتفاع الشحن** | **إعادة حساب الرصيد فقط** — لا يلمس التخصيصات ولا العربون المدفوع (السياسة: فروق الشحن تُسوّى في الرصيد لا في العربون) |
| **استرداد جزئي** | **حركة استرداد موثّقة** (`refund_movements`: المبلغ، التخصيص المرجعي، السبب، الفاعل) — لا حركة نقد بلا سجل |
| **إلغاء كامل** | **تسوية الطلب**: تحرير كل التخصيصات + حركات الاسترداد المقابلة + إغلاق الفرعية + `CANCELLED` على الـMaster |

### 8.4 جداول D4 الجديدة (الأثر البنيوي)

`deposit_policy` (نسبة افتراضية + استثناءات origin/lane/product بترتيب أولوية) ·
`deposit_allocations` (sub_order_id, required, allocated, state
ACTIVE/RELEASED/REFUNDED, event_ref) · `refund_movements`. حالات ERP الحالية
(`AWAITING_DEPOSIT → AWAITING_PAYMENT_VERIFICATION → CONFIRMED`, `PARTIALLY_PAID`)
تظل هي الحالات الأم — التخصيصات تفصيل داخلي تحتها، والعميل لا يرى إلا رقماً واحداً.

## 9. [v2] سجل توزيع التخفيضات (إضافة D3 المحاسبية)

> المالك: «لا يكفي تسجيل order_discount إذا أردنا CRM ومحاسبة دقيقة» —
> النظام يجب أن يعرف: الإجمالي، حصة كل منتج، حصة كل Sub-Order، القيمة النهائية،
> وأثر التخفيض على الأرباح والعمولات.

- **جدول `discount_allocations`**: (discount_id, scope, target: line|sub_order,
  amount, basis) — لكل خصم سطور تخصيصه.
- **قاعدة التوزيع**: تناسبي على صافي قيم الأسطر المؤهّلة + **باقي التقريب
  لأكبر سطر**؛ **Σ التخصيصات = قيمة الخصم بالضبط** (لا فلس مفقود)، ولا سطر
  يتجاوز صافيه أبداً (لا خصم سالب).
- **مثال المالك**: سلة 500 (محلي 300 / صيني 200) + خصم ORDER ب50:
  تخصيص (30 / 20) ⇒ صافي (270 / 180)؛ إيراد الفرعية المحلية 270 والصينية 180؛
  **ربح الفرعية = صافيها − تكلفتها الفعلية** (من WHS/التوريد لاحقاً)، و**قاعدة
  العمولة = الصافي** — والتوقيعات لم تُلمس (R4): أسطر Lens/aywebs الموقّعة
  تُعرض بأسعارها الأصلية والخصم سطر مستقل ظاهر للعميل.
- CRM يقرأ السجل مباشرة: إجمالي الخصومات، توزيعها على المنتجات/الفرعية/المداخل،
  وأثرها على الهوامش — بلا إعادة حساب من النصوص.

## 10. [v2] D7 — تسلسل التنفيذ الدقيق (سؤال المالك التقني: بلا دفع مزدوج)

> سؤال المالك: «بما أن AYWEBS يمتلك مسارات طلبات ومدفوعات مستقلة، كيف يُنشأ
> سجل التنفيذ دون دفع مستقل أو تكرار؟ يجب تحديد تسلسل العمليات بدقة».
>
> **الجواب مبنيّ على اكتشاف موثّق في الكود**: `ayweb_purchase_requests`
> (`src/aywebs/purchaseRequests.ts`) هي **سجلات توريد تشغيلية بلا أي حقول دفع**
> (INSERT بلا payment whatsoever) بآلة حالات كاملة
> (…→ APPROVED → … → ORDER_READY/REJECTED بسبب ومدقّق ووقت) وعمود `order_id`
> **اختياري** يُملأ فقط إذا احتاج التشغيل طلباً داخلياً لاحقاً. أي أن aywebs
> بُنيت أصلاً بسجل «اطلب من الفريق أن يشترى» **منفصل عن مال العميل** — هذا هو
> سجل التنفيذ الطبيعي، لا اختراع شيء.

### 10.1 التسلسل الدقيق (الخطوة بخطوة)

1. **الجسر مرة واحدة** (الموجود): أسطر aywebs الجاهزة تعبر للسلة الموحّدة
   **موقّعة VERIFIED** (`createZayrovixPriceToken` في الجسر)، وخريطة
   `ayweb_cart_zayrovi_links` تسجّل كل زوج (سطر aywebs ↔ سطر Core) فلا نقل
   مزدوج أبداً — حاجز الدفع المزدوج الأول قائم بنيوياً.
2. **checkout الموحّد في Core**: Master + فرعية global + المطلوب للعربون (§8).
   **صفر نداء لأي نقطة دفع في aywebs** (`/payments/*` لا تُستدعى في هذا المسار
   إطلاقاً).
3. **دفع واحد للعميل في Core** — العربون يسجل في Core فقط.
4. **بعد تأكيد الدفع فقط**: Orchestration (وحدة جديدة **خارج aywebs**) تنشئ
   **purchase-request لكل فرعي global** عبر **دوال مجال aywebs المستوردة**
   (نمط الجسر نفسه: `zayroviBridge.ts` يستدعي دوال aywebs كمكتبة لا HTTP) —
   الطلب يحمل: هوية الأسطر (`AyWebs AYWITEM-…` في الملاحظات موجودة أصلاً من
   الجسر)، لقطة السعر والمتغيّرات، و`requirements` من حجم/لون/ملاحظات العميل.
5. **الربط المزدوج الاتجاه**: `sub_order.external_ref = request_number` في Core
   **+** سطر في `ayweb_order_links` (جدول الروابط الموجود على جانب aywebs —
   الجسر يكتب فيه أصلاً بنفس النمط: link_type/external_id/external_number)
   ⇒ CRM يجد الطرفين من أي جهة.
6. **الحالات تتدفق**: آلة حالات purchase-request (`emitAyWebsEvent` +
   `writeAyWebsAudit` الموجودتان) تُترجَم للقاموس الموحّد (D5) — الفرعية في
   Core تتحرك مع سجل التنفيذ.
7. **إذا احتاج التشغيل فعلياً طلب aywebs داخلياً** (ORDER_READY → `order_id`):
   يبقى سجلاً تشغيلياً **للفريق** — بلا مسار دفع عميل؛ الشراء من المتجر
   الخارجي يتم بأداة شراء الشركة (خارج مال العميل الذي تحرك مرة واحدة في Core).
   عمود `order_id` الموجود أصلاً يستوعب هذا دون أي تعديل.

### 10.2 لماذا لا دفع مزدوج بنيوياً (لا بالانضباط)

- المسار الموحّد لا يستدعي أي endpoint دفع في aywebs — لا ثغرة استدعاء أصلاً.
- purchase-request **لا يحمل مالاً** بنيويته (بلا حقول دفع) — لا شيء يدفع مرتين
  لأن الطرف الثاني لا يملك مفهوم الدفع أصلاً.
- قاعدة **المسار الواحد** (§5.1-4): السلّة إمّا تُجسَر للCore أو تُدفع في وضع
  aywebs المستقل (التصفّح المباشر كما اليوم) — الخريطة `ayweb_cart_zayrovi_links`
  تمنع ازدواج الأسطر بين المسارين.
- **أدلة الشراء محفوظة كاملة**: لقطة السعر، snapshot المتغيّرات، evidence hash،
  قفل الأسطر — كلها في أسطر سلّة aywebs التي وُلد منها الpurchase-request.
