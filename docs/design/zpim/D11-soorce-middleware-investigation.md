## A · Data Acquisition — كيف تحصل Soorce على بيانات 1688؟

| نوع التكامل | الأدلة العامة | الحكم |
|---|---|---|
| **Official API (open.1688.com)** | الحمولة تحمل شارات واجهة الويب (`is_super_factory`, `ship_in_48h`, `low_refund_rate`, `is_powerful_seller`) التي لا تعيدها واجهات المنصة المفتوحة + تسريب widget العروض الداخلي `styleType:offer-type-1` في أوصاف المنتجات | **مستبعدة — Probable-high** |
| **Commercial API مُطبِّعة** | مخططان خامان مختلفان يمرّان عبر نفس الـendpoint دون توحيد (بحث كلمي vs تغذية افتراضية: 6 فروق حقول + `item_id` نصي/رقمي) — طبقة مُطبِّعة كانت ستوحّدهما | **مستبعدة لطبقة البحث — Probable-high** |
| **Authorized Data Provider** | لا أي أثر عام (لا اسم، لا ترويسات متاحة لنا، لا نمط ترخيص ظاهر) | **Unknown — غير قابل للإثبات خارجياً** |
| **Scraping / Custom acquisition** | شارات الويب الخام + مرور سلوك المصدر الأصلي حرفياً (سقف 2000 نتيجة/100 صفحة المقاس = سقف 1688 الأصلي) + عدّادات حية وقت الطلب | **الأرجح — Probable-high** (غير مثبت: قد يكون actor خاص غير مدرج أو بنية سحب داخلية) |
| **Hybrid (سحب حي + كتالوج مخزن)** | بحث حي (عدّادات 9972→9977) + تفاصيل/تسعير مخزنة (سعر USD ثابت + sitemap بتاريخ توليد موحّد) | **CONFIRMED بالقياس** |

**إثباتٌ vs مجهول:** نثبت نوع الطبقة (مرور خام + إثراء) وحيّية البحث وسقوف المصدر والهامش الضمني المُقاس. يبقى مجهولاً: هوية المزود، بنية خوادمهم، اتفاقيتهم مع 1688 — وحتى HAR متصفح كامل لا يرى نداءات server→upstream.

## B · Data Processing

- **الاستقبال:** خام متعدد الأشكال (passthrough). دليل: عيّنتا البحث والتغذية محفوظتان في `api-search-probe2-samples.json`.
- **اختلاف المخططات:** لا طبقة توحيد ظاهرة في البحث — الفروق تصل العميل كما هي:

| الحقل | بحث كلمي | تغذية افتراضية |
|---|---|---|
| `item_id` | نصي | رقمي |
| `sale_info` | `orders_count` + `sale_quantity` صيني | `sale_quantity_90days` فقط |
| `shop_info` | بدون `is_powerful_seller` | مع `is_powerful_seller` |
| `delivery_info` | `area_from` فقط | + `ship_in_48h` + `free_shipping` |
| `price_info.origin_price` | رقمي | سلسلة فارغة `''` |
| `quantity_prices` | موجودة | غائبة كلياً |
| الغلاف | بلا `sort` | مع `sort:"default"` وبلا `total_count` |

- **Product/Offer IDs:** معرّف عرض 1688 = المفتاح الوحيد عبر كل الطبقات (الـAPI، صفحات `/fr/product/<id>`، مرآة الصور `product-images/<offerId>/N.jpg`، sitemap). لا دليل على وجود معرّف داخلي موازٍ — **Unknown**.
- **بيانات المورد:** محجوبة عمداً من الطبقة العامة (لا اسم متجر في الـAPI؛ الواجهة تعرض «Usine en Chine + حرف») — قرار وسيط لا قرار مصدر.
- **المتغيرات والأسعار:** سلّم الجملة باليوان الخام يمرّ كما هو (`quantity_prices[{begin_num,price}]`)، ومقاسات المواصفات تُترجم آلياً بلا معجم (فشل موثّق: «90 to 105 kilograms» = 斤) ⇒ المعالجة = إثراء فوق خام، لا تطهير.

## D · Pricing Architecture

- **طبقتان مثبتتان:** سعر المورد (يوان خام في `quantity_prices`) منفصل عن سعر العميل (USD في `price_info` + علم `soorce_priced`).
- **الهامش الضمني — قياس 12 زوجاً** (CNY tier-1 ↔ USD headline): معامل فعلي **4.62–5.64** مقابل سوقي ~7.2 ⇒ هامش مدمج **~28–56% تنازلي** (يقل مع ارتفاع السعر). طريقة القياس والأزواج في `api-search-probe2-samples.json`.
- **العملة والصرف:** USD وحيدة للعميل؛ آلية تحديث الصرف **Unknown**.
- **مخزن vs لحظي:** سعر العميل مخبأ (ثابت بين جلبين)؛ عدّادات البيع حية؛ توفر المخزون غير معروض — **التحقق الحي بعد الطلب** (بلفظهم في /process) هو صمّام العتالة.
- **الفريت:** وزن تقديري لكل قطعة × سعر الكيلو للدولة معروض قبل الدفع؛ الفوترة النهائية على الوزن الفعلي بعد التغليف (llms.txt).

## E · Catalog & Cache

- **كتالوج مخزن مسبقاً:** sitemap فهرس → 26 ملف `products-*.xml` بـlastmod موحّد (2026-11-28) ⇒ إعادة توليد دورية شاملة، وصفحات منتج ثابتة بأسعار مخزنة (كتالوج SEO + سرعة).
- **Search Cache vs Details Cache:** البحث حي/قريب-من-الحي (عدّادات تتحرك بين جلبين)؛ التفاصيل مخبأة بعمر طويل نسبياً (ثبات السعر). ⇒ **نموذج: كاش تفاصيل عميق + بحث شبه حي.**
- **تحديث الأسعار والتوفر:** كتالوج قد يعتدل ⇒ يُصحّح بسير عمل «تحقق حي من السعر والتوفر مع المصنع بعد الطلب» + QC استلام + استرداد (5 أيام شكوى / 30 يوماً استرداد).
- **TTL Policies:** غير معلنة — استنتاج بالسلوك فقط (قياسنا: تفاصيل > ساعات، بحث ~دقائق أو بلا كاش).
- **المنتجات القديمة/غير المتاحة:** لا آلية عامة ظاهرة — يعتمدون التحقق بعد الطلب والاسترداد بدل حذفها. Unknown تفاصيلها.

## خلاصة D11 — النموذج الوظيفي لوسيط Soorce (6 أسطر)

1. استقبال خام من مسارين+ دون توحيد (أرشيفية الصيغة تُلقى بالعرض).
2. ترجمة الاستعلام للصينية قبل النداء (خط مستقل عن السحب).
3. طبقة تسعير خاصة فوق اليوان الخام بهامش مدمج تنازلي غير معلن.
4. كتالوج تفاصيل مخبأ يُعاد توليده دورياً للـSEO والسرعة، وبحث شبه حي.
5. إخفاء المورّد عن الطبقة العامة + مرآة صور على تخزينهم.
6. التحقق الحي بعد الطلب يعوّض عتالة الكتالوج (نفس فلسفتنا v2.5 §14.2).
