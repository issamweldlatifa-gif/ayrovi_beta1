# تدقيق أداء ZAYROVI: التطبيق والموقع والخادم

## الخلاصة التنفيذية

**لا توجد أدلة كافية لنسب البطء إلى Render Free وحدها أو للتوصية بترقية عمياء.** توجد اختناقات كود مثبتة محليًا، وبعضها أُصلح بالفعل؛ وتبقى بيانات الاستضافة والهاتف ضرورية لإغلاق التشخيص.

أهم نقطة قبل المقارنة: `render.yaml` يحدد `plan: starter` وليس Free. هذا وصف المستودع، **وليس إثباتًا للخطة الفعلية في لوحة Render**. كذلك يجب التأكد من أن `/api/ready` يعلن فرعًا وكوميتًا يحتويان الإصلاحات، وأن APK المثبت هو النسخة الجديدة. التطبيق يقبل الخادم القديم أثناء النشر التدريجي، لكنه حينها قد يرجع إلى تحميل المصفوفة الكاملة؛ نجاح تثبيت APK لا يثبت نشر إصلاحات الخادم.

هذه الدفعة أضافت أدوات تدقيق وتقارير فقط. لم تُرقِّ الاستضافة، ولم تغيّر القرص أو Stripe أو سلوك الشراء أو تحذف وظائف.

## نطاق الإثبات وحدوده

**نُفّذ:** فحص إعدادات النشر والكود؛ بناء الموقع والخادم؛ قياسات API وCPU/RAM وتأخر event loop وكلفة SQL؛ خطط SQLite؛ مقارنة مصدر قبل الإصلاحات `e83f6ebf` بالمصدر الحالي `63a3d648`؛ فحص أحجام حزم الويب؛ ومراجعة نتائج اختبارات العرض الأصلية من الدفعة السابقة.

**لم يُنفّذ:** قياس خدمة Render الفعلية أو تحديد خطتها من الحساب، تجربة cold start إنتاجية، فحص قاعدة بيانات الإنتاج، اختبار هاتف مثبت مع FPS/زمن الضغط، Lighthouse/INP/LCP على الموقع الحي، أو قياس CRM مسجَّل الدخول أثناء حمل واقعي. لا يوجد وصول مباشر لخدمة Render من هذه البيئة. محاولة قراءة سجل قياس إنتاجي قديم عبر GitHub لم تنجح بسبب تعذر جلب أرشيف السجل؛ نجاح الـworkflow وحده لا يُستخدم هنا كدليل أداء أو نشر.

**البيئة المحلية:** Linux x64، Node 22.22.3، نواتان منطقيتان متاحتان، ذاكرة مضيف نحو 3.85 GiB؛ ليست موارد Render. Node المحلي مختلف عن 22.23.4 المثبت في ملف النشر.

**البروتوكول:** قاعدة SQLite جديدة في الذاكرة، بيانات اصطناعية لا بيانات مستخدمين. مرحلتان: 1000 ثم 10000 Reel، و10 تفاعلات لكل Reel، و500 ثم 5000 منتج. لكل مسار: طلب أول، طلبا إحماء، ثم 12 طلبًا بتزامن 1 و12 بتزامن 4. CPU وRSS يشملان عميل الاختبار والخادم في العملية نفسها، لا الخادم وحده. لا توجد مهام عمل إنتاجية أو I/O لقرص قاعدة الإنتاج. p95 هنا عينة تشخيصية صغيرة وليس SLO أو اختبار سعة مستمرًا. أحجام الردود JSON بعد فك الضغط، وليست البايتات على الشبكة. RSS عيّنة يمكن أن تفوت قممًا قصيرة، ويحتفظ المخصّص بذاكرة مراحل سابقة. CPU فوق 100% يعني استعمال أكثر من نواة، وليس نسبة استعمال حساب Render.

## 1. نتائج API الحالية ونمو البيانات

عند تزامن 4 طلبات، p95 محلي بالمللي ثانية:

| المسار | 1000 Reel / 500 منتج | 10000 Reel / 5000 منتج | حجم الرد في المرحلة الكبيرة |
|---|---:|---:|---:|
| `/api/ready` | 7.05 | 6.45 | نحو 0.1 KiB |
| `/api/public/home` | 15.92 | 50.27 | 15.5 KiB |
| `/api/public/products?limit=50` | 19.25 | 42.70 | 23.8 KiB |
| `/api/public/social/reels?limit=12` | 9.95 | 9.14 | 3.5 KiB |
| `/api/public/social/reels` القديم | 87.94 | 1181.08 | 2744.5 KiB |

عند تزامن 1 وفي المرحلة الكبيرة: p95 للجاهزية 1.83ms، الرئيسية 14.44ms، المنتجات 11.35ms، صفحة Reels 3.37ms، وReels القديم 210.59ms. زيادة زمن الطلب مع التزامن ليست دليلًا منفردًا على نقص خطة الاستضافة؛ حتى الاختبار المحلي يدير العميل وJSON وSQL في العملية نفسها.

**الاستنتاج:** paging يحد فعلًا من كلفة مسار Reels. المسار القديم ما زال قابلًا للتضخم رغم أن الرد ناجح. وجود LIMIT على المنتجات لا يضمن أن العمل الداخلي محدود بـ50 صفًا.

## 2. مقارنة قبل/بعد الإصلاحات الأخيرة

المصدر القديم شُغّل من لقطة `git archive` داخل `.cache` دون تبديل الفرع أو لمس قاعدة بيانات فعلية. بيانات الاختبار والبروتوكول متماثلان، لكن المقارنتين تشغيلان منفصلان ولا يصح تفسير الفروق الصغيرة كتحسّن مؤكد.

| الحالة | قبل `e83f6ebf` | الحالي `63a3d648` |
|---|---:|---:|
| Reels بطلب `limit=12`، عشرة آلاف عنصر، p95 وتزامن 4 | 1117.63ms؛ المعامل لم يكن مدعومًا والرد كامل | 9.14ms؛ صفحة فعلية |
| حجم الرد لنفس الطلب | 2744.5 KiB | 3.5 KiB |
| 8 طلبات صورة متطابقة باردة، عدد استدعاءات جلب المصدر | 8 | 1 |
| زمن انتهاء دفعة الصورة المتطابقة | 553.03ms | 117.46ms |
| CPU لدفعة الصورة المتطابقة | 1047.62ms | 132.20ms |
| 8 صور مختلفة باردة، زمن الدفعة | 462.91ms | 596.42ms |
| أعلى تأخر event loop في دفعة الصور المختلفة | 87.10ms | 49.97ms |

صور اصطناعية 1600×2400، لا تنزيلات إنترنت. **الصور المختلفة لم تصبح أسرع في هذا الاختبار**: ضبط التوازي يهدف إلى منع الانفجار في العمل الجاري وحماية بقية الخدمة، وله ثمن انتظار. لا نخفي هذه المقايضة ولا نعتبر كل ضبط حدّي تسريعًا.

كذلك لم تتحسن كل API: p95 الرئيسية في التشغيل القديم الكبير 39.73ms مقابل 50.27ms حاليًا. المسار لم يُحسّن في إصلاحات Reels؛ هذه العينة لا تثبت تراجعًا دائمًا، لكنها تمنع الادعاء بأن كل التطبيق صار أسرع.

## 3. CPU وRAM وتأثير مشاركة الموارد

- خلال قياس الصفحة الكبيرة المقسمة: CPU نحو 27.53ms لمجموع 12 طلبًا عند التزامن 4؛ المسار القديم الكامل نحو 2342.61ms. هذه كلفة العملية المشتركة مع عميل القياس وليست CPU production.
- RSS محليًا كان نحو 194MiB في المراحل الصغيرة، ونحو 232MiB قبل اختبارات API في المرحلة الكبيرة، ووصل إلى نحو 318MiB مع الردود الكاملة. لا يُفسَّر هذا كحجم قاعدة الإنتاج أو حد Render المطلوب.
- قبل دفعة الصورة المتطابقة الحالية RSS نحو 338.61MiB، وأعلى عيّنة فيها 374.85MiB؛ في المصدر القديم نحو 332.66→571.62MiB. النتائج متسقة مع إزالة فك صور مكرر، لكنها ليست قياس ذاكرة هاتف أو خدمة مستقلة.
- أعلى RSS في دفعة الصور المختلفة الحالية نحو 498.68MiB؛ الرقم يشمل المراحل السابقة وعميل الاختبار وقاعدة الذاكرة. **ليس مبررًا وحده لاختيار خطة RAM معينة**.
- API غير المقسم أحدث تأخر event loop بلغ نحو 498ms في إحدى الحالات. SQL متزامن وتحويل JSON يعملان في نفس عملية Node؛ عملية ثقيلة يمكن أن تؤخر بقية المستخدمين حتى لو كان طلبهم بسيطًا.

المصدر يجمع routers العامة وCRM وERP مع SQLite ومعالجة الصور في خدمة Node واحدة. توجد مهام دورية للبريد والإشعارات والكاش والنسخ الاحتياطي. هذه **قابلية للتنافس على الموارد**، وليست إثباتًا أن CRM هو الحمل المسيطر الآن؛ اختبارنا لم يشغّل حمل CRM أو العمال الفعليين.

## 4. قاعدة البيانات والاستعلامات والكاش

### مؤكد وجيد حاليًا

- مسار صفحات Reels يستخدم `idx_reels_public_page` في EXPLAIN.
- عدّ التفاعلات يستخدم الفهرس المغطي `idx_story_interactions_target(target_id,type)`، وليس مسحًا كاملًا لكل عداد في العينة.
- صفحات Reels الحالية حافظت على كلفة SQL منخفضة نسبيًا مع زيادة البيانات؛ متوسط SQL المقاس نحو 0.48ms لكل طلب في المرحلة الكبيرة/التزامن 4.
- يوجد WAL وbusy_timeout في تهيئة SQLite. وجود SQLite بحد ذاته ليس تشخيصًا بالبطء.
- الصور الحالية تستعمل single-flight وحدًا للعمل وكتابة ذرية، والأخطاء المؤقتة لم تعد تثبت fallback دائمًا. النتائج الإيجابية المخزنة ومسارات الصور الباردة ما زالت حالتين مختلفتين ينبغي قياسهما منفصلتين.

### اختناق نمو مثبت محليًا — المنتجات والرئيسية

`src/public/routes.ts`، مسارا `/products` و`/home`: تجميع `LEFT JOIN product_arrivals` ثم `GROUP BY` وفرز قبل LIMIT. خطة `/products` أظهرت:

```text
SEARCH p USING INDEX idx_products_status (status=?)
SEARCH pa USING COVERING INDEX sqlite_autoindex_product_arrivals_1 (product_id=?) LEFT-JOIN
USE TEMP B-TREE FOR GROUP BY
USE TEMP B-TREE FOR ORDER BY
```

متوسط SQL للمنتجات ارتفع من نحو 1.48ms إلى 6.96ms لكل طلب مع زيادة المنتجات من 500 إلى 5000. الرئيسية ارتفعت من نحو 1.47ms إلى 7.73ms. ليست أرقامًا كارثية محليًا، لكنها عمل ينمو رغم بقاء الرد صغيرًا.

**الإصلاح التالي المقترح، وليس تغييرًا نُفِّذ في هذا التدقيق:** تحديد المنتجات المطلوبة أولًا بترتيب ثابت وفهرس مركب مناسب، ثم إرفاق arrivals للصفحة فقط. يجب اختبار visibility/arrivalId/ties والمنتجات المخفية قبل التعميم؛ لا يكفي إضافة فهرس عشوائي مع إبقاء التجميع الكامل.

### مخاطر يجب عدم تغطيتها بالكاش بلا ضوابط

المسارات القديمة للمحتوى ما زالت متاحة حفاظًا على العملاء السابقين. توجد دالة ويب قديمة `getReels` تستعمل المسار الكامل، لكن لم يظهر مستهلك حالي لها في البحث النصي؛ لا ننسب لها طلبات فعلية دون Network trace. يجب قياس الاستعمال الحقيقي قبل إغلاق التوافق القديم.

الإعدادات المنشورة تحمل no-cache/no-store في عدة مسارات؛ بعض ذلك مقصود لضمان تحديث المحتوى. لا يُضاف shared cache للعميل أو السعر أو الصلاحيات. أي كاش عام قصير يحتاج invalidation عند نشر المحتوى وقياس hit/miss، لا مجرد TTL طويل يخفي المشكلة.

## 5. الموقع والتطبيق: ما عولج وما بقي غير مقاس

### التطبيق الأصلي

الإصلاح السابق فصل كلفة الواجهة عن الشبكة: catalog FlatList بدل تركيب كل البطاقات، عارض Reels موحد بلا قائمة رأسية متداخلة، cover لملء الفيديو، memo وحدود إعادة رسم، ومصفوفات مستقرة. اختبارات الدفعة السابقة: 1155 unit و321 UI. اختبار 2000 منتج بالكاش ركّب أول 6 بطاقات فقط. هذه أدلة سلوك وعقد عرض، **ليست FPS أو زمن استجابة لمسة على الجهاز**.

إن بقي الضغط بطيئًا في شاشة محمّلة مسبقًا أو دون شبكة، لا نتوقع أن ترقية الخادم وحدها تصلحه. يلزم Android Studio/Perfetto أو React Native profiler على نفس APK والهاتف، مع JS/UI frame time وفك الفيديو والصور والذاكرة قبل/بعد عشر دقائق تمرير. يجب فحص فيديوهات تحتوي أشرطة سوداء داخل الملف نفسه؛ cover لا يزيل إطارًا مخبوزًا في الفيديو.

### الموقع

البناء الحالي يحتوي 25 حزمة JS، وأكبرها:

| الحزمة | خام KiB | gzip تقديري KiB |
|---|---:|---:|
| AdminApp | 531.4 | 131.0 |
| qr | 401.4 | 105.5 |
| index | 236.7 | 77.2 |
| App | 208.7 | 69.6 |

العميل يفصل PublicApp وAdminApp باستيراد lazy، وكذلك عدة شاشات ثقيلة. **لا يصح جمع كل الحزم واعتبارها تحميل الصفحة الأولى**؛ أحجام gzip هنا ضغط محلي وليست شبكة مقاسة. وجود حزمة كبيرة يستحق مراجعة dependency graph، لكنه لا يثبت INP أو LCP سيئين. يلزم waterfall وCoverage وLighthouse/Performance trace على الهاتف أو متصفح بموارد مخفّضة، مع تصنيف الصور والخطوط وJS والـAPI كلٍّ وحده.

## 6. كيف نحسم دور Render قبل الترقية؟

| المشاهدة بعد القياس | التفسير المرجح | القرار |
|---|---|---|
| أول طلب بعد خمول بطيء، ثم طلبات متكررة سريعة، مع سجل إيقاف/إقلاع مطابق | cold start محتمل ومؤكد فقط بربط السجل | خطة لا تتوقف قد تحسن أول فتح؛ تحقق من خصائص الخطة الحالية |
| CPU مرتفع مستمر أو throttling مع API بطيء بعد الإحماء | قدرة حسابية أو عمل زائد | إصلاح الاستعلامات والعمل الثقيل، ثم اختيار موارد بناءً على الحمل |
| RAM تلامس الحد أو OOM/restarts | ضغط ذاكرة أو تسرب أو تزامن مفرط | قياس RSS/heap/external ونوع العمل؛ تعديل الكلفة/التوازي ثم موارد مناسبة |
| SQL بطيء أو busy/lock waits مع CPU غير مشبع | استعلام/قرص/قفل | تحليل الاستعلامات وWAL والعمليات الطويلة؛ زيادة CPU وحدها غير كافية |
| API سريع لكن الضغط والتمرير ثقيلان | واجهة/فيديو/فك صور أو استهلاك جهاز | profiler للهاتف؛ الترقية لا تعالج العمل المحلي |
| `/api/ready` لا يعرض الإصلاحات أو APK قديم | المقارنة على نسخ غير متطابقة | تثبيت ونشر النسخ الصحيحة قبل الحكم |

**الجواب العملي:** الخطة المدفوعة قد تعالج سببًا حقيقيًا إن ثبت النوم أو نقص الموارد، لكنها لن تزيل تجميع SQL غير محدود أو تكرار المعالجة أو إعادة رسم الواجهة. ولا نعرف من المستودع وحده هل الخدمة فعلًا Free.

## 7. القياسات المطلوبة من الخدمة الحية، دون كلمات مرور

1. اسم الخطة الفعلية وحدود CPU/RAM والمنطقة، وصورة metrics لساعة تشمل فترة البطء: CPU، memory، requests/latency إن توفرت، وأحداث restart/OOM/deploy. إخفاء أي أسرار.
2. نتيجة `/api/ready` لتحديد commit/branch، وتحديد إصدار APK المثبت ومصدره.
3. تشغيل المسبار الصغير من جهاز خارج هذه البيئة، مرة بعد خمول ومرة والخدمة دافئة:

```bash
node scripts/performance-probe.mjs --base https://YOUR-SERVICE --runs 3 --output probe.json
```

المسبار لا يختار production افتراضيًا، لا يرسل credentials أو cookies، ولا يضغط الخدمة بتزامن: 4 مسارات GET عامة، بتباعد 750ms، 3 جولات افتراضيًا، مهلة 90 ثانية لأول ready و15 ثانية للبقية، وحد قراءة 1MiB. يجمع توقيت الترويسات والجسم وrequest ID ونسخة النشر، **ولا يقيس CPU/RAM الخادم**. التوقيت يشمل DNS/TLS والشبكة، وأول طلب بطيء لا يثبت sleep وحده. لا ترسل dump قاعدة بيانات أو مفاتيح حساب.
4. سيناريو هاتف ثابت: فتح بارد، انتقال إلى شاشة بالكاش، تمرير الرئيسية، عشر نقلات Reels، والكتالوج، مع trace وتسجيل زمن اللمسة/FPS والذاكرة. نقارن نفس الجهاز ونفس البيانات ونفس حالة الشبكة.

## 8. خطة تحسين قابلة للتوسع بدون حذف وظائف

- **P0 — تحقق النسخة والخطة والقياس:** بيانات البنود السابقة؛ فصل انتظار الشبكة عن JS/UI والعمل على الخادم.
- **P1 — SQL المنتجات:** rewrite + index مبني على EXPLAIN واختبارات تكافؤ، ثم قياس 5k/50k منتج وarrival filters. راجع ضغط CRM أثناءها ببيانات مصرح بها.
- **P1 — مراقبة موارد حقيقية:** قياسات process/container منفصلة، event-loop lag، slow routes ومدة SQL وcache hit/queue time. سجلات مجمعة بأسماء routes فقط، دون tokens أو روابط المستخدمين، وخلف صلاحيات للبيانات الداخلية.
- **P1 — تثبيت تحقق النشر:** الـworkflow الحالي لقياس media يستطيع الاكتفاء بتحذير بعد فشل انتظار النسخة؛ لا تعتبر إشارة success إثبات نشر أو تحسّن. اجعل نتيجة القياس مرتبطة صراحةً بالكوميت المخدوم قبل المقارنة.
- **P2 — حمل واقعي:** تدرج مصرح به 1/4/8 مستخدمين، بحث وكتالوج وCRM وصور باردة ودافئة، مع توقف عند ارتفاع الأخطاء/التشبع، وتحديد هدف p95 وذاكرة متفق عليهما؛ لا يُجرى ضغط كثيف على الخدمة الحية بلا نافذة متفق عليها.
- **P2 — فصل العمل الثقيل عند الحاجة:** إذا أثبتت traces تنافسًا، worker محدود للصور/OCR والمهام الخلفية. لا حاجة لتقسيم كل المشروع أو تبديل SQLite فقط بسبب اسمه.
- **P2 — قرار الخطة:** تجربة موارد أعلى على سيناريو ثابت بعد إصلاح الاختناقات المؤكدة، ومقارنة التكلفة بـp95 ونسبة الخطأ والذاكرة. لا يوجد وعد أن الترقية وحدها ستحل البطء.
